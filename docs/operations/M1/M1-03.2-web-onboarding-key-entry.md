## Goal

Deliver the web first-run experience: BYOK/on-device explanation, OpenRouter preselected and recommended, key entry, inline testing, actionable errors, and transition to a new chat.

## Preconditions

- Provider/model services are available.
- Runtime config gates other providers.
- Do not build provider management or model picker in this task.

## Deliverables

- Welcome screen with BYOK/on-device copy and OpenRouter marked Recommended.
- Provider picker showing OpenRouter enabled and other presets disabled/coming later.
- Key entry with optional label, Connect, testing state, and error area.
- Load public catalog before key validation; keep sending disabled until validation succeeds.
- Preserve typed key and label on failure; never log or echo the key.
- On success, store secret/provider metadata, refresh models, select the default model, set onboarding complete, and navigate to a new chat.
- `cors` and auth error copy that points to the Android app or a future proxy without adding a proxy.
- Component tests for first run, invalid key, valid key, and preserved form.

## Implementation steps

1. Read existing Button, Dialog, Toast, and theme primitives.
2. Build the onboarding container as a route-level feature component.
3. Add the welcome state and provider picker. Keep the other presets visible but non-actionable.
4. Add the key form with validation. Trim the key but do not log it.
5. Start catalog loading when the screen opens. Show a non-blocking loading/error state.
6. On Connect, disable the button, call the provider service, and show inline testing. On failure, re-enable and keep the form.
7. On success, update settings and navigate to the new chat route.
8. Wire the route or redirect from `/settings/providers/new` and the empty state.
9. Add tests with MSW.

- Verification: `make web-lint && make web-typecheck && make web-test &&

- Decisions:
  - The public catalog loads immediately with no key and is non-blocking. A
    catalog failure still allows Connect; models are refreshed after `/key`
    succeeds.
  - `connect` treats only a successful `GET /key` as validation. It creates the
    provider, validates, refreshes models, selects a default, persists
    defaults, creates the first conversation, and only then sets
    `onboardingCompleted`.
  - Any failure before completion deletes the provider (cascading models and
    the secret) and restores the previous default provider/model, so an
    invalid key stores nothing.
  - The key is trimmed, never logged, and redacted from error details. The form
    keeps the typed key and label after a failure.
  - Other presets remain visible but disabled with "Coming later"; only
    OpenRouter is selectable.

## Handoff notes

- Route behavior: `/settings/providers/new` always renders onboarding. `/`
  checks `onboardingCompleted`; first run renders onboarding, and a completed
  setup falls back to the existing no-conversation placeholder until the chat
  screen lands in M1-04. Successful onboarding navigates to
  `/chat/$conversationId`.
- Onboarding-completion semantics: `onboardingCompleted` is set only after the
  provider, key metadata, models, default provider/model, and first
  conversation all exist. A failed attempt leaves it false and rolls back the
  provider and defaults.
- Error copy: auth failures say the key was rejected and to check it. `cors`
  and `network` failures point to the Android app or a self-hosted proxy
  without adding a proxy. Quota, rate-limit, permission, model, timeout, parse,
  and storage failures each have plain-language copy. Raw details are behind a
  "Details" disclosure and are redacted.
- The onboarding service is injectable through `OnboardingServiceProvider`.
  M1-03.3 can reuse the same provider or replace it with a broader app service
  context when provider management lands.
