# M5-02.2 - Android manifest, storage keys, and Room migration

- Milestone: M5
- Status: Not started
- Order: 7
- Depends on: M5-01.3
- Parallel-safe: yes, with `M5-02.1` and `M5-02.3`
- Owns: `android/core/database/`, `android/core/model/`, `android/core/backup/`
- Read first: [M5 plan](../M5-backup-and-sync-implementation-plan.md) sections 3.3 and 5.3; spec sections 6.1, 6.4, and 13.3; `contracts/schema/backup-manifest-body.schema.json`

## Goal

Add the durable data needed for sync on Android: a random conversation
`storageKey`, a monotonic `revision`, tombstones with `deviceId`, a manifest
writer/reader, and a self-contained conversation payload. Migrate existing Room
data without loss.

## Preconditions

- `M5-01.3` is `Complete` and the envelope codec exists.
- `M5-01.1` schemas are the source of truth for manifest and conversation shapes.
- Do not change export/import behavior.

## Deliverables

- Entity updates:
  - `ConversationEntity`: add `storageKey: String` and `revision: Long`.
  - New `TombstoneEntity` with `id`, `conversationId`, `messageId`, `deletedAt`,
    `deviceId`.
- DAO updates:
  - `ConversationDao` queries for storage key and revision.
  - New `TombstoneDao` with insert, list, and delete.
- Database updates:
  - Bump `CHATUI_DATABASE_VERSION` to 2.
  - Add `Migration(1, 2)` in `Migrations.kt`.
  - Add `TombstoneEntity` to `ChatUiDatabase` entities and DAO accessor.
- Model updates in `android/core/model/`:
  - `Conversation` gains `storageKey` and `revision`.
  - New `Tombstone` model.
- Repository updates:
  - `ConversationRepository` sets `storageKey` and `revision` on create/update.
  - New `TombstoneRepository`.
- New `android/core/backup/` manifest and payload code:
  - `BackupManifest.kt` build/parse.
  - `ConversationPayload.kt` build/parse.
- Tests:
  - `MigrationTest` for 1 -> 2 with existing data.
  - `storageKey` is 32 hex chars and unique.
  - Manifest and payload round trips.
  - Tombstone DAO/repository CRUD.

## Implementation steps

1. Read `ConversationEntity`, `MessageEntity`, `AttachmentEntity`,
   `ChatUiDatabase`, `Migrations.kt`, `DatabaseVersion.kt`, and the repositories.
2. Add `storageKey` and `revision` columns to `ConversationEntity`. Use
   `@ColumnInfo(defaultValue = "...")` only if needed for the migration; prefer
   explicit migration SQL.
3. Add `TombstoneEntity` and `TombstoneDao`.
4. Bump the database version to 2 and add `Migration(1, 2)`:
   - `ALTER TABLE conversations ADD COLUMN storage_key TEXT NOT NULL DEFAULT ''`.
   - `ALTER TABLE conversations ADD COLUMN revision INTEGER NOT NULL DEFAULT 1`.
   - Backfill `storage_key` with random 32-hex values. Do this in Kotlin after
     the schema change if SQL cannot generate randomness; document the approach.
   - `CREATE TABLE tombstones (...)` and indexes.
5. Update `ChatUiDatabase` entities and DAO accessors.
6. Update the domain model and mappers.
7. Update `ConversationRepository` create/update to set `storageKey` and
   increment `revision`.
8. Add `TombstoneRepository`.
9. Implement `BackupManifest` build/parse and `ConversationPayload` build/parse
   in `android/core/backup/`. Use the schema field names exactly.
10. Add `MigrationTest` using `MigrationTestHelper` and run the Android gates.

## Acceptance criteria

- [ ] `ConversationEntity` has `storageKey` and `revision`.
- [ ] `TombstoneEntity` and DAO exist.
- [ ] Database version is 2 with a working `Migration(1, 2)`.
- [ ] Existing data survives the migration and new fields are backfilled.
- [ ] `storageKey` is 128-bit random hex and unique per conversation.
- [ ] `revision` starts at 1 and increments on local mutation.
- [ ] Manifest and conversation payload round-trip and validate.
- [ ] No secrets or provider keys appear in the manifest or payload.
- [ ] Existing export/import tests still pass.
