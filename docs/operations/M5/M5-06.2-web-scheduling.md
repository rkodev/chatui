- Milestone: M5
- Status: Complete

## Goal

Provide a web scheduling equivalent that respects browser constraints. Do not
claim background sync that browsers do not support. Document exactly when backup
runs and what the user must do.

## Preconditions

- `M5-05.1` is `Complete` and the backup UI can enable backup.
- The service worker currently handles shell caching only.
- Do not add a server component or a hidden network destination.

## Deliverables

- `web/src/features/backup/scheduler.ts`:
  - Foreground scheduling while the app is open (for example an interval and a
    visibility-change trigger).
  - Optional `Periodic Background Sync` registration behind feature detection.
  - `schedule()`, `cancel()`, and `runIfDue()`.
  - Respect the user's enable/disable setting.
- `docs/operations/M5/web-scheduling.md`:
  - Supported behavior per browser.
  - Why full background sync is not guaranteed.
  - What runs on app open, on visibility change, and on periodic sync when
    available.
  - How the user can force a backup.
- Tests:
  - Scheduler runs when due and skips when not due.
  - Disable cancels the schedule.
  - Feature detection falls back safely.
  - No plaintext path is introduced.

## Implementation steps

1. Read the backup UI, sync engine, and service worker source.
2. Implement `scheduler.ts` with a foreground interval and visibility trigger.
3. Add optional `Periodic Background Sync` registration:
   - Check `'periodicSync' in registration`.
   - Request permission if required.
   - Fall back silently when unavailable.
4. Wire enable/disable in the backup settings flow.
5. Write `web-scheduling.md` with an honest browser support table.
6. Add tests with fake timers and a fake sync engine.
7. Run the web gates.

## Handoff notes

- `BackupScheduler` lives in `web/src/features/backup/scheduler.ts` and exposes
  `schedule()`, `cancel()`, and `runIfDue()`. It depends only on an engine with
  `backupNow()`, so it cannot introduce a plaintext path.
- Foreground scheduling is authoritative: a 5-minute interval plus a
  `visibilitychange` due check, with a 15-minute due window.
- `Periodic Background Sync` is registered behind `'periodicSync' in
  registration` and a permission check. The current service worker only caches
  the shell, so the registration is a forward-compatible hook; it does not yet
  perform a backup on `periodicsync`. This is documented honestly in
  `web-scheduling.md`.
- `BackupSettingsService` now accepts an optional scheduler, starts it on load
  when backup is enabled, schedules on enable, and cancels on disable. The
  production factory wires a scheduler whose engine delegates to
  `BackupSettingsService.backupNow()`.
- Because the passphrase is never persisted, automatic runs after a page reload
  fail until the user re-enters it. This matches the Android handoff note.
- Scheduling starts when the backup settings screen loads in a session. A
  future app-level bootstrap could start it earlier without changing the
  scheduler API.
