- Milestone: M3.5
- Status: Complete
- Order: 9

- Parallel-safe: yes, with M3.5-04.1 and M3.5-05.1

- Read first: [M3.5 plan](../M3.5-rust-desktop-implementation-plan.md) sections 3.3 and 4.5; spec sections 9.5, 10.5, and 10.11

## Goal

Create the SQLite foundation with WAL, foreign keys, a busy timeout, versioned migrations, and a testable database lifecycle.

## Preconditions

- M3.5-00.2 records the SQLite backend decision.
- M3.5-02.1 and M3.5-02.2 are complete.
- Do not implement repositories or export/import in this task.
- Do not issue SQL from UI or provider crates.

## Deliverables

- `chatui-storage` dependency set using the chosen backend (`sqlx` preferred or `rusqlite` with bundled SQLite).
- A database open function that:
  - creates or opens the database under the platform app-data directory;
  - enables WAL;
  - enables `foreign_keys = ON`;
  - sets a busy timeout;
  - runs migrations.
- Versioned migration files that create the schema foundation.
- A migration test from an empty database.
- A test proving the pragmas are active.
- A test proving the linked SQLite exposes FTS5.
- A documented database path and migration policy.

## Implementation steps

1. Read the SQLite decision in `M3.5-decisions.md`.
2. Add the chosen database dependency. If using `sqlx`, enable `runtime-tokio`, `sqlite`, and migration support. If using `rusqlite`, enable `bundled` and FTS5 support.
3. Add `directories` for app-data paths. Provide a test override so tests use a temporary directory.
4. Implement `open_database(path)` and `open_in_memory()` or a temporary-file equivalent for tests.
5. Run the pragmas on every connection:
   ```sql
   PRAGMA journal_mode = WAL;
   PRAGMA foreign_keys = ON;
   PRAGMA busy_timeout = 5000;
   ```
   Use the chosen library's connection options where available and verify the values with a query.
6. Create migration `0001_initial.sql` or the equivalent. Include the tables from section 9.5/plan: conversations, messages, attachments, providers, models, secrets, settings, backup config, sync queue, and FTS support table.
7. Store structured fields as JSON text where they match the Android Room entities. Keep indexed columns typed.
8. Add a test that opens an empty database, runs all migrations, and verifies the expected tables and indexes.
9. Add a test that runs migrations twice and is idempotent.
10. Add an FTS5 availability test. If the chosen SQLite build lacks FTS5, fail with a clear message and record the blocker.
11. Document the app-data path, migration policy, and non-destructive rule.

## Handoff notes

- Backend: `sqlx` 0.8.6 with `default-features = false` and features
  `runtime-tokio`, `sqlite`, `migrate`, and `macros`. The `sqlite` feature uses
  bundled SQLite through `libsqlite3-sys` 0.30.1, which compiles with
  `SQLITE_ENABLE_FTS5`. This satisfies DEC-03 and DEC-04 without a system
  SQLite dependency.
- Other dependencies: `directories` 6.0.0 for app-data paths, `thiserror` 2.0.21
  for the storage error type, and dev-only `tempfile` 3.27.0 and `tokio` 1.54.1.
- Database path: `ProjectDirs::from("", "", "chatui").data_dir()/chatui.sqlite3`.
  Linux: `~/.local/share/chatui/chatui.sqlite3`; macOS:
  `~/Library/Application Support/chatui/chatui.sqlite3`; Windows:
  `%APPDATA%\chatui\data\chatui.sqlite3`. `open_database` creates the parent
  directory when missing. Tests use `tempfile` or `open_in_memory` and never
  touch the real user database.
- Pragmas: every pooled connection is opened with `journal_mode = WAL`,
  `foreign_keys = ON`, and `busy_timeout = 5000`. `open_database` verifies the
  values and fails closed on mismatch. In-memory databases use
  `journal_mode = memory` because SQLite cannot use WAL for `:memory:`; foreign
  keys and the busy timeout are still verified.
- FTS5: `verify_fts5` checks `sqlite_compileoption_used('ENABLE_FTS5')`, creates
  and drops a temporary FTS5 virtual table, and `open_database` calls it before
  migrations so a build without FTS5 fails with `StorageError::Fts5Unavailable`.
  The test suite also inserts into `messages_fts` and runs a `MATCH` query.
- Migration: `migrations/0001_initial.sql` creates `conversations`, `messages`,
  `attachments`, `secrets`, `providers`, `models`, `settings`, `backup_config`,
  `sync_queue`, the `messages_fts` FTS5 table, and the required indexes
  (`idx_messages_conversation_sequence`, `idx_models_provider_remote`,
  `idx_attachments_sha256`) plus supporting indexes. SQLx records versions and
  checksums in `_sqlx_migrations`; re-running the migrator is a no-op.
- Migration policy: every schema change adds a new ordered SQL file; applied
  migrations are never edited. There is no destructive fallback, no
  drop-and-recreate path, and no release-only schema reset. A failed migration
  is surfaced as an error and leaves the database untouched.
- Verification: `cargo fmt --all --check` passed; `cargo clippy -p
  chatui-storage --all-targets -- -D warnings` passed; `cargo nextest run -p
  chatui-storage` passed 8/8 tests.
- Blockers: none.
