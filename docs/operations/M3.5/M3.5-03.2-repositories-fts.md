# M3.5-03.2 - Repositories, schema mapping, FTS5, and pagination

- Milestone: M3.5
- Status: Complete
- Order: 10
- Depends on: M3.5-03.1
- Parallel-safe: yes, with M3.5-03.3
- Owns: `rust/crates/chatui-storage/src/repositories/`, `rust/crates/chatui-storage/src/search.rs`, `rust/crates/chatui-storage/src/mappers.rs`
- Read first: [M3.5 plan](../M3.5-rust-desktop-implementation-plan.md) sections 3.3 and 4.5; spec sections 6.2-6.4, 9.5, 10.5, 11.9

## Goal

Implement repository APIs over the SQLite schema, including FTS5 search and bounded pagination, so UI and export code never issue SQL.

## Preconditions

- M3.5-03.1 is complete.
- Do not put SQL in `chatui-ui` or `chatui-providers`.
- Do not implement attachments, recovery, or export/import in this task.
- Do not use destructive schema changes.

## Deliverables

- Repository traits and SQLite implementations for:
  - conversations;
  - messages;
  - attachments metadata;
  - providers;
  - models;
  - secret metadata;
  - settings;
  - backup config;
  - sync queue placeholders.
- Mapping between domain types and database rows, including JSON columns.
- FTS5 index over message text, synchronized on insert, update, delete, and conversation deletion.
- Conversation search with bounded results and snippets.
- Message pagination by `(conversationId, sequence)` in both directions.
- Tests for CRUD, ordering, pagination, search, cascade deletion, and large conversation bounds.

## Implementation steps

1. Read the migration schema and the Android Room entities for field parity.
2. Define repository traits in `chatui-storage` so `chatui-ui` can depend on abstractions rather than SQLite types.
3. Implement row mappers:
   - `parts`, `usage`, `error`, `params`, and `sync` as JSON text;
   - booleans as integers;
   - `sequence` as a signed integer;
   - timestamps as RFC 3339 text.
4. Implement conversation and message repositories with:
   - create/update/delete;
   - list with pin/archive filters;
   - newest page and older page queries;
   - message insert/update with sequence ordering.
5. Implement provider, model, settings, secret metadata, backup config, and sync queue repositories. Enforce unique `(providerId, remoteId)` for models.
6. Implement FTS5:
   - create the virtual table in the migration;
   - index message text from text parts;
   - update the FTS row in the same transaction as the message write;
   - remove FTS rows on message or conversation deletion.
7. Implement search results with conversation id, message id, snippet, and order.
8. Implement cursor or offset-free pagination that returns bounded pages.
9. Add a large-conversation test with at least 10,000 messages proving queries stay bounded.
10. Add tests for cascade deletion of messages, attachments metadata, and FTS rows.

## Handoff notes

- Repository traits: `ConversationRepository`, `MessageRepository`,
  `AttachmentRepository`, `ProviderRepository`, `ModelRepository`,
  `SecretRepository`, `SettingsRepository`, `BackupConfigRepository`,
  `SyncQueueRepository`, and `SearchRepository`. Each has a `Sqlite*`
  implementation over a cloned `SqlitePool`. All traits are object-safe
  (`Arc<dyn Trait>` is covered by `repository_traits_are_object_safe`) so UI
  code can depend on abstractions. Traits and implementations are re-exported
  from the crate root.
- Integration changes outside the listed `Owns` paths: `src/lib.rs` declares
  and re-exports the new modules, and `Cargo.toml` adds `async-trait`,
  `chatui-domain`, `serde`, and `serde_json`. No other crate was touched.
- Mapping: `src/mappers.rs` owns row structs and conversions. JSON columns are
  serialized with `serde_json`; booleans are integers; `sequence` is a signed
  `INTEGER`; timestamps are RFC 3339 UTC text. The migration declares timestamp
  columns as `INTEGER`, but SQLite's dynamic typing stores the RFC 3339 text
  unchanged because it has no numeric affinity. This matches the Android Room
  entities, which also store ISO 8601 strings.
- `sync_state` only persists the `SyncState` discriminant. The provisional
  `SyncMeta.last_synced_at` and `remote_revision` fields are not persisted
  because the schema has no columns for them; M5 owns the final sync shape.
- Schema parity issue: `providers.browser_cors` is declared as
  `INTEGER ... CHECK (browser_cors IN (0, 1))` in `0001_initial.sql`, while the
  shared contract and Android entity use `supported`/`unsupported`/`unknown`.
  To avoid a destructive migration, the integer column stores `1` for
  `supported` and `0` otherwise, and the exact string is preserved in provider
  metadata under the reserved key `$browserCors`. A follow-up migration should
  correct the column type when a non-destructive table rebuild is acceptable.
- Attachments: the schema requires `attachments.message_id NOT NULL`, so
  `AttachmentRepository::insert` rejects `message_id: None` with
  `StorageError::InvalidInput`. M3.5-03.3 should link metadata to a message
  before inserting.
- Pagination: `newest_page`, `older_page`, and `newer_page` return
  `MessagePage { messages, has_more }` in ascending `sequence` order. Page sizes
  are clamped to 1..=500. `next_sequence` includes soft-deleted rows so a reused
  sequence cannot violate the unique `(conversation_id, sequence)` index.
  `list_all` exists for export/import and tests only; UI code must use the
  bounded page methods.
- FTS5: `messages_fts` indexes only `ContentPart::Text` parts, joined with
  newlines. Inserts use an insert-only FTS write; updates and upserts replace
  the row; deletes and soft deletes remove it; conversation deletion removes
  every row for the conversation before the cascade. Search tokenizes input into
  alphanumeric words, quotes each word, and joins with `AND`, so punctuation and
  quotes cannot produce FTS syntax errors. Results are ordered by FTS5 `rank`
  then `sequence`, capped at 100, and return a plain-text `snippet` with `...`
  ellipses.
- Provider deletion removes the provider (cascading models), clears
  `conversations.provider_id`/`model_id` while preserving `model_label`, and
  deletes the provider's secret. Model uniqueness is enforced by
  `idx_models_provider_remote` and surfaced as `StorageError::Conflict`.
- Settings are stored per camelCase key, matching the web client. `load` merges
  stored values over `default_settings()`; `save` writes every field in one
  transaction. Backup config uses the fixed `default` row. Sync queue is a
  placeholder with enqueue/list/delete/increment/clear.
- Test names: `conversation_crud_round_trips`,
  `conversation_list_filters_and_ordering`,
  `message_crud_and_mapping_round_trips`,
  `message_pagination_is_ordered_and_bounded`,
  `large_conversation_pagination_stays_bounded`,
  `search_synchronizes_on_insert_update_delete_and_cascade`,
  `search_filters_by_conversation_and_limits`,
  `cascade_deletion_removes_messages_attachments_and_fts`,
  `provider_crud_and_delete_cascade`, `model_uniqueness_is_enforced`,
