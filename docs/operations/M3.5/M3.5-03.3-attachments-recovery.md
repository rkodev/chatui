## Goal

Store attachment bytes by content hash under the desktop app-data directory and make startup recovery safe: stale streams become cancelled, partial content is preserved, and orphan attachment files are removed.

## Preconditions

- The SQLite foundation exists.
- Do not implement provider downloads, image decoding, or UI attachment pickers.
- Do not store attachment bytes in the database.
- Do not modify `web/` or `android/`.

## Deliverables

- An attachment store using `attachments/<sha256>` under the app-data directory.
- SHA-256 hashing and deduplication. Writing the same bytes twice returns the same storage key.
- Metadata insert/update/delete through the storage layer.
- Orphan cleanup that removes files not referenced by attachment metadata.
- Startup recovery that:
  - marks stale `streaming` messages as `cancelled`;
  - preserves partial text and reasoning;
  - runs orphan cleanup with a defensible timestamp or reference set;
  - returns a summary of changes.
- Tests for dedup, read/write/delete, missing files, orphan cleanup, and recovery.

## Implementation steps

1. Read `web/src/storage/AttachmentStore.ts`, `web/src/features/conversations/recoveryService.ts`, and the Android `AttachmentService` and `StreamingRecoveryService`.
2. Add `sha2`, `hex`, and path helpers through `directories`. Keep the layout `chatui/attachments/<sha256>`.
3. Implement `put(bytes) -> storage_key`, `get(storage_key) -> bytes`, `delete(storage_key)`, and `exists(storage_key)`.
4. Validate storage keys as 64-character lowercase hex SHA-256 values. Reject path traversal and non-hex keys.
5. Deduplicate: if the file exists, do not rewrite it; still return the storage key.
6. Implement metadata writes through the database layer. Keep `sha256` and `storageKey` aligned with the shared domain.
7. Implement orphan cleanup:
   - collect referenced SHA-256 values from attachment metadata;
   - scan the attachment directory;
   - remove files not referenced;
   - never delete a file while an import or active send is using it.
8. Implement startup recovery:
   - select messages with `status = 'streaming'`;
   - set `status = 'cancelled'`, preserve `parts` and `usage`;
   - set a safe finish reason or error state consistent with the shared domain;
   - update `updatedAt`;
   - run orphan cleanup after recovery.
9. Make recovery idempotent and safe to run before the UI shell renders.
10. Document the recovery ordering and the one-second persistence trade-off.
11. Add tests using a temporary app-data directory and a temporary database.

## Handoff notes

- Attachment layout: bytes live at `<app-data>/attachments/<sha256>`. The
  storage key is the bare 64-character lowercase hexadecimal SHA-256 digest;
  the `attachments/` directory is part of the path, not the key. This differs
  from the web/Android `storageKey` string (`attachments/<sha256>`) but keeps
  the same on-disk layout and makes key validation and path-traversal rejection
  unambiguous. `sha256` and `storageKey` are kept equal by
  `AttachmentService::add` and validated by `AttachmentService::update`.
- Public API: `AttachmentStore::{new, with_app_data_dir, put, get, delete,
  exists, pin, cleanup_orphans, cleanup_orphans_for_repository}`,
  `AttachmentService::{add, update, delete}`, `sha256_hex`, and the `paths`
  helpers. `AttachmentStore::put` returns the storage key and deduplicates
  identical bytes. `AttachmentStore::pin` returns an `AttachmentLease` that
  keeps a key out of orphan cleanup while an import or send is using it.
- Recovery ordering: call `RecoveryService::recover` once during startup,
  before the UI shell renders and before any new send or import. It selects
  non-deleted `streaming` messages, rewrites them to `cancelled` with
  `finishReason = cancelled` and the `INTERRUPTION_NOTE` error, preserves
  `parts` and `usage`, updates `updatedAt`, then removes attachment files not
  referenced by metadata. A second pass is a no-op.
- One-second persistence trade-off: streaming text is persisted at most once
  per second (spec 10.9), so a process kill can lose up to about one second of
  the newest tokens. Recovery preserves exactly what reached the database and
  never invents or truncates partial content.
- Integration changes outside the listed `Owns` paths: `src/lib.rs` declares
  and re-exports the new modules; `Cargo.toml` adds `sha2` and `hex`;
  `src/repositories/messages.rs` adds `MessageRepository::list_by_status` so
  recovery can select streaming messages without SQL outside the repository
  layer. No other crate was touched.
- Tests: `attachments::tests` covers put/dedup/get/delete/exists, unsafe keys,
  orphan cleanup, pinning, stale temp files, metadata alignment, update, and
  last-reference byte deletion. `recovery::tests` covers cancellation with
  preserved parts/usage, idempotence, orphan cleanup, and complete-message
  isolation. `paths::tests` covers key validation and traversal rejection.
- Coordination with M3.5-03.2: the attachment repository already exposes
  `list_storage_keys`, which recovery uses as the referenced set. M3.5-03.4
  export/import should use `AttachmentService::add` and hold an
  `AttachmentLease` while reading bytes so cleanup cannot race an import.
