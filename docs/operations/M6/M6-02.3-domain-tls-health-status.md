## Goal

Document how roksky attaches tenant subdomains and custom domains, issues and
renews TLS, defines tenant health, exposes status to operators and users, and
recovers from domain/TLS/health failures.

## Preconditions

- `M6-02.1` is `Complete` and the edge template is stable.
- `M6-01.1` recorded the external operator and `DEC-M6-14` custom-domain/TLS
  ownership.
- Do not promise TLS automation or status tooling that the external operator
  cannot provide.

## Deliverables

- `docs/hosting/custom-domains.md`:
  - Subdomain naming rules and reserved-name policy.
  - Apex and `www` behavior, including which hostname is canonical and whether
    the other redirects.
  - Required DNS records and ownership-verification method.
  - TLS states: `pending_dns`, `pending_tls`, `active`, `failed`, with user
    messages and operator actions.
  - Certificate issuance, renewal, expiry monitoring, and alert ownership.
  - Failure recovery: wrong DNS target, conflicting records, CAA/proxy issues,
    expired certificate, hostname removed.
  - Rollback: revert to tenant subdomain or previous domain; keep the app
    available without changing user data.
  - Statement that changing the origin requires updating the public config
    `openRouter.attributionOrigin` and bucket CORS origins.
- `docs/hosting/health-and-status.md`:
  - Check definitions: `/`, `/config.json`, `/healthz`, one hashed asset, a deep
    SPA route, TLS certificate validity, exact security headers, and config hash
    match.
  - Expected status codes, bodies, cache/header values, and failure thresholds.
  - Tenant status states: `unknown`, `healthy`, `degraded`, `unhealthy`, with
    definitions and operator actions.
  - Operator visibility: dashboard or status record, alert routing, ownership,
    and escalation.
  - User visibility: owner-supplied status link or message; do not invent a
    public status page.
  - Health check frequency, timeout, retry policy, and false-positive handling.
  - Recovery steps for a failed check, including rollback when needed.

## Implementation steps

1. Read the tenant schema custom-domain and health fields.
2. Read the edge template to confirm the actual header/cache/health behavior.
3. Write the custom-domain runbook with all DNS/TLS states and recovery.
4. Write the health/status runbook with exact checks and thresholds.
5. Link the rollback runbook, one-click flow, and verification script.
6. Confirm every operator action has an owner and every user message is
   actionable.
7. Record any external tooling gap as a blocker, not as a promise.

## Acceptance criteria

- [ ] Both docs exist and cover the required domain, TLS, health, and status
      behavior.
- [ ] DNS records, verification, renewal, expiry, and failure recovery are
      actionable.
- [ ] Health checks match the edge template and section 14.1 contract.
- [ ] Status states have definitions, owners, and operator actions.
- [ ] The origin-change impact on OpenRouter attribution and CORS is documented.
- [ ] The docs do not claim a live status page or TLS automation that the
      operator has not supplied.
- [ ] No backend, proxy, or secret is introduced.
