## Goal

Add a web provider registry that reads provider presets from `contracts/providers.json` or a build-time generated equivalent, validates them, and gates the M1 UI to OpenRouter only.

## Preconditions

- Contracts validate.
- Do not add an adapter, SSE parser, or feature screen in this task.

## Deliverables

- A documented way for Vite/Vitest to consume `contracts/providers.json` without copying provider metadata into hand-written source.
- `web/src/providers/registry.ts` with a typed `ProviderPreset`, `loadProviderPresets`, `getPreset`, and default-preset lookup.
- Runtime validation of required preset fields and duplicate IDs.
- A selector that returns only OpenRouter as fully enabled in M1.
- Updates to `web/public/config.json` and `web/src/app/config.ts` so other presets may remain in contracts but are not exposed as usable M1 flows.
- A React provider or service hook that supplies presets to feature code.
- Tests for loading, validation failure, default lookup, and M1 gating.

## Implementation steps

1. Inspect `contracts/providers.json` and `contracts/schema/provider-preset.schema.json`.
2. Choose and document one loading path. Prefer a Vite JSON import from the repository contracts tree for dev/test/build, with `server.fs.allow` only if required. Do not hand-copy preset objects.
3. Define the TypeScript preset shape without redefining provider metadata values.
4. Implement `loadProviderPresets` with explicit errors for malformed presets.
5. Implement `getPreset(id)` and `getDefaultPreset()`.
6. Implement M1 gating: OpenRouter is selectable; other presets are labelled disabled/coming later; custom creation is false.
7. Wrap the app with the registry provider in `web/src/app/providers.tsx` or a sibling module.
8. Add tests and run the web gate.

## Handoff notes

- Contract loading: `web/src/providers/registry.ts` imports
  `../../../contracts/providers.json` directly. Vite/Vitest transform the JSON
  at import time and the checked-in contracts file remains the only source of
  provider metadata. There is no generated copy or hand-maintained mirror.
- Vite configuration: `web/vite.config.ts` sets `server.fs.allow` to the
  repository root because the contracts tree sits outside the `web/` Vite root.
  This is needed for the dev server; tests and production builds resolve the
  import through the normal module graph.
- Runtime validation: `loadProviderPresets(input)` accepts an explicit value
  for tests while defaulting to the imported contracts document. It validates
  with the Zod schema first, then rejects duplicate IDs. Validation failures
  throw `ProviderRegistryError` with a path-prefixed `issues` array.
- Default lookup: `getDefaultPreset` requires exactly one preset marked
  `default: true` in contracts and throws on zero or multiple defaults. It does
  not silently select the first preset.
- M1 gating: `M1_ENABLED_PRESET_IDS` is the single allow-list. UI code should
  use `getPresetAvailability`/`getEnabledPresets`; non-OpenRouter presets remain
  in contracts and are reported as `coming-later`, not hidden or duplicated.
- Config gating: `validateConfigPresets` and `loadConfig` enforce that every
  enabled preset exists in contracts, is M1-enabled, and that the default preset
  is enabled. `allowCustomProviders: true` is always rejected in M1.
- Test fixture location: `registry.test.ts` reads the real contracts document
  from `resolve(process.cwd(), '../contracts/providers.json')` to assert parity
  with the imported presets. `config.test.ts` reads
  `resolve(process.cwd(), 'public/config.json')`. Malformed preset cases are
  constructed by cloning a real contract preset, so tests do not add fake
  provider metadata to the contracts tree.
- Downstream tasks can import from `web/src/providers` for the provider/hook and
  registry helpers. M1-02.3/M1-03.1 should consume `ProviderPreset` and the
  context rather than re-reading `contracts/providers.json`.
