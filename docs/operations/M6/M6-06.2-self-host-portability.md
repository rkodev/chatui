## Goal

Prove that a tenant can export its public config and app data, then self-host the
same build with the same `config.json` contract. Also exercise the export-before-
teardown path so a tenant is not trapped in managed hosting.

## Preconditions

- `M6-05.3` is `Complete` and the staging tenant is healthy.
- Use synthetic data and disposable credentials only.
- If the tenant teardown cannot be exercised on staging, document the procedure
  and mark the execution item as blocked; do not claim it passed.

## Deliverables

- `docs/operations/M6/evidence/portability.md`:
  - Date, commit, tenant URL, release version, artifact digest, and config hash.
  - Export the tenant public config. Record its hash and confirm it matches the
    deployed config.
  - Build the same release locally or use the published artifact.
  - Run the M4 container with the exported `config.json`:
    - Build with `docker build -f deploy/Dockerfile`.
    - Run with the config mounted or baked exactly as documented.
    - Run `scripts/verify-hosted-deployment.mjs` against the local container.
  - Compare the header/cache/SPA/health/config results with the staging tenant.
  - Confirm the app loads and a synthetic chat still works with the same
    provider setup.
  - Confirm the exported public data (settings/conversations) can be imported
    into the self-hosted instance using the documented export/import path.
  - Result: pass/fail and any difference between managed and self-hosted
    behavior.
- `docs/operations/M6/evidence/export-teardown.md`:
  - The "export everything" checklist: app data export, optional encrypted
    backup, public config export, and self-host instructions.
  - The teardown procedure: export first, revoke/remove DNS and TLS, remove the
    tenant deployment, retain only the agreed public metadata, and confirm the
    exported build remains usable.
  - If teardown is executed on staging, record the steps and result. If not,
    record the exact blocker and keep the exit gate open.
  - Confirm no server-side user data is lost because none is stored.
- Update `docs/operations/M6/evidence/README.md` with both links.

## Implementation steps

1. Export the deployed public config and compute its hash.
2. Record the release digest and compare it with the tenant manifest.
3. Run the same build/config in the local M4 container.
4. Run the hosted verification script and compare results.
5. Export synthetic app data and import it into the self-hosted instance.
6. Confirm the self-hosted app still works with the same public config.
7. Execute or tabletop the teardown flow. Do not delete anything before export.
8. Write both evidence records and update the index.

## Acceptance criteria

- [ ] The exported public config hash matches the deployed config.
- [ ] The same build self-hosts with the exported config.
- [ ] The local container passes the same header/cache/SPA/health/config checks.
- [ ] Synthetic exported data imports into the self-hosted instance.
- [ ] The export-everything checklist covers app data, backup, public config, and
      self-host instructions.
- [ ] Teardown exports first and does not lose user data.
- [ ] Teardown is executed or explicitly blocked with a reason.
- [ ] No secret, real key, passphrase, prompt, or chat content is included.

## Verification

```bash
node scripts/validate-tenant-config.mjs <exported-config.json> --origin <self-host-origin>
make web-build
docker build -f deploy/Dockerfile -t chatui-web:m6-portability-proof .
docker run --rm -d --name chatui-m6-portability-proof -p 8083:80 chatui-web:m6-portability-proof
node scripts/verify-hosted-deployment.mjs http://localhost:8083 --origin <self-host-origin>
docker stop chatui-m6-portability-proof
```

Plus the synthetic export/import and teardown records.

## Out of scope

- Changing the export/import format or self-host deployment contract.
- Final exit-gate verification (`M6-06.3`).
- A new hosting offering or managed storage.
