## Goal

Review the deployed tenant's security boundary and prove there is no server-side
path to provider keys, plaintext chats, storage credentials, or backup
passphrases, and no hidden network destination or prompt proxy.

## Preconditions

- `M6-05.3` is `Complete` and the staging tenant/config evidence exists.
- `M6-04.3` is approved.
- The operator provides edge configuration, log configuration, and support-role
  access for review. If not, mark the missing review item `Blocked`.
- Do not record real keys, prompts, responses, chats, credentials, passphrases,
  or personal data.

## Deliverables

- `docs/operations/M6/evidence/security-review.md` containing:
  - Date, reviewer, commit, tenant URL, release digest, and config hash.
  - A data-flow diagram or ordered list:
    - Browser -> roksky edge for static shell, assets, config, and `/healthz`.
    - Browser -> provider directly for chat and models.
    - Browser -> user storage directly for encrypted backup objects.
    - No browser -> roksky prompt or storage proxy path.
  - "What roksky has" and "what roksky does not have" table:
    - Has: static files, public config, deployment metadata, edge/access logs,
      support records.
    - Does not have: provider keys, prompts, responses, plaintext chats, local
      browser data, storage credentials, backup ciphertext decryption keys, or
      passphrases.
  - Edge configuration review: no reverse proxy to provider/storage, no body
    logging, no third-party script injection, no added network origins, CSP
    unchanged.
  - Log review: confirm logged fields and retention match
    `logging-and-retention.md`; confirm no request bodies or secrets.
  - Support-access review: roles, least privilege, no impersonation, audit
    enabled, no key/chat/passphrase recovery path.
  - Browser network trace summary: list request origins and classify each as
    same-origin, provider, user storage, or unexpected. Do not record headers,
    bodies, tokens, or query strings containing secrets.
  - No hidden network destination or server-side prompt-proxy conclusion.
  - Rollback/teardown safety review.
  - Findings, severity, owner, and follow-up task for every issue.
  - Final sign-off: `pass`, `pass with conditions`, or `fail`.
- Update `docs/operations/M6/evidence/README.md` with the link.

## Implementation steps

1. Read the deployment, privacy, support, and rollback evidence.
2. Draw the data-flow diagram from the actual edge configuration.
3. Inspect the edge configuration for provider/storage proxying, body logging,
   third-party scripts, and header/CSP changes.
4. Inspect the support roles and audit configuration.
5. Capture a browser network trace during the staging smoke. Summarize origins
   only, with no secrets.
6. Compare the actual log fields and retention with the approved docs.
7. List every deviation with severity and owner.
8. Record the sign-off or fail the review. Do not mark complete with an
   unowned high-severity finding.

## Acceptance criteria

- [ ] The security review record exists and includes the data-flow diagram.
- [ ] The has/does-not-have table covers keys, chats, storage credentials, and
      passphrases.
- [ ] Edge configuration review confirms no proxy, body logging, third-party
      scripts, or CSP loosening.
- [ ] Log review matches the approved logging/retention docs.
- [ ] Support-access review confirms no impersonation and no recovery path.
- [ ] The network trace lists only expected origins and no unexpected
      destinations.
- [ ] The sign-off is explicit and all findings have owners.
- [ ] No secret, real key, passphrase, prompt, chat content, or personal data is
      included.

## Verification

Manual review plus:

```bash
test -f docs/operations/M6/evidence/security-review.md
grep -n "Data flow\|Does not have\|support\|network\|sign-off\|pass\|condition\|fail" docs/operations/M6/evidence/security-review.md
```

If the browser trace tool is unavailable, record the exact tool and method used
and the same origin summary. Do not fabricate a trace.

## Out of scope

- Fixing findings. Create follow-up tasks and keep the exit gate blocked if they
  affect the M6 guarantees.
- Self-host/export portability (`M6-06.2`).
- A penetration test or full legal/privacy audit beyond M6's static-hosting
  scope.
