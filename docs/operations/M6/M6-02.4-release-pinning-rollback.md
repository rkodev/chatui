## Goal

Document how a tenant release is pinned to an immutable artifact and public
config, how to roll both back together, and how to verify recovery without a
server-side data rollback.

## Preconditions

- `M6-02.1` is `Complete` and the tenant manifest includes release and rollback
  fields.
- `M6-01.1` recorded rollback ownership.
- Rollback must not require or imply server-side user data. User chats and keys
  stay in the browser; backups stay in the user's storage.

## Deliverables

- `docs/hosting/rollback.md` covering:
  - Rollback triggers: failed deploy, health check failure, header/CSP
    regression, config validation failure, broken provider configuration,
    custom-domain/TLS failure, or a bad release discovered after publish.
  - Preconditions: previous release version and artifact digest, previous config
    hash, and previous tenant manifest are recorded.
  - Artifact and config are pinned together. Never roll back one without the
    other unless the compatibility is explicitly verified.
  - Step-by-step rollback: freeze new deploys, select the previous release and
    config, update the tenant manifest, deploy the immutable artifact, set the
    public config, purge/rewrite edge caches, wait for propagation, run the
    health/header/config checks, and confirm the tenant is healthy.
  - Post-rollback verification: `/`, `/config.json`, `/healthz`, one asset, a
    deep route, TLS, exact headers, config hash, and provider setup.
  - Communication: operator status update, user-facing message, incident record,
    and follow-up owner.
  - Custom-domain/TLS rollback: revert to tenant subdomain or previous domain if
    the domain change caused the incident.
  - Data safety statement: rollback does not restore or delete browser data,
    provider keys, storage credentials, or backup objects.
  - A rollback decision table and a dry-run checklist.
- Update the tenant example if a required rollback field is missing. Do not
  weaken the schema.

## Implementation steps

2. Read the deployment template and M4 deployment contract.
3. Write the rollback triggers, preconditions, and step-by-step procedure.
4. Add the post-rollback verification table.
5. Add the custom-domain/TLS and data-safety sections.
6. Cross-check that every step can be performed with the documented external
   operator access.
7. Record any missing operator capability as a blocker.

## Acceptance criteria

- [ ] `docs/hosting/rollback.md` exists and covers triggers, preconditions,
      artifact/config pinning, steps, verification, communication, and data
      safety.
- [ ] The runbook pins artifact and config together.
- [ ] The runbook verifies headers, CSP, health, SPA fallback, TLS, and config
      hash after rollback.
- [ ] The runbook states that rollback does not restore browser data, keys, or
      backups.
- [ ] The runbook identifies the operator, approver, and incident-record owner.
- [ ] No backend, server-side data store, or secret is introduced.
- [ ] The procedure is executable by a smaller model with operator access.
