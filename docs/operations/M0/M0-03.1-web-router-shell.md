# M0-03.1 - Router and shell state

- Status: Not started
- Parent task: M0-03
- Order: 11
- Depends on: M0-02.5
- Parallel-safe: yes, with M0-03.2
- Owns: `web/src/app/router.tsx`, `web/src/app/App.tsx`, `web/src/app/providers.tsx`, `web/src/app/stores/**`, route placeholder components under `web/src/app/routes/**` or an equivalent router-owned folder, corresponding tests
- Read first: [M0 plan](../M0-foundations-implementation-plan.md) sections 3.2 and 4.4; spec sections 8.3 and 8.4

## Goal

Create the history-routed application shell and Zustand stores for shell state only. Feature routes render placeholders.

## Preconditions

- Config, domain, storage, and secrets are available.
- Do not implement streaming state or feature screens.

## Deliverables

- TanStack Router setup:
  - code-based route tree using browser history
  - routes for `/`, `/chat/$conversationId`, `/settings`, `/settings/appearance`, `/settings/providers`, `/settings/providers/new`, `/settings/providers/$providerId`, `/settings/models`, `/settings/data`, `/settings/backup`, `/settings/about`
  - `/` renders a neutral "no conversation" placeholder in M0 because conversation routing belongs to M1
  - unknown routes render a not-found placeholder
  - settings root redirects to appearance
- `App.tsx` and `providers.tsx` wired to the config loader, router, theme provider, and toast provider when available.
- Zustand stores under `web/src/app/stores/`:
  - `sidebar.ts`: open/closed state only
  - `dialogs.ts`: generic dialog identity/open state only
  - `toasts.ts`: add, dismiss, and clear ephemeral toasts
  - `drafts.ts`: per-conversation draft text keyed by conversation ID
  - no streaming buffer, provider call, or chat runner
- Placeholder route components stay generic and must not become feature screens.
- Tests:
  - each required route resolves
  - unknown route renders the fallback
  - `/settings` redirects to appearance
  - the shell stores update only their documented state

## Implementation steps

1. Create the route tree and placeholders.
2. Wire the router into the app entry point.
3. Add the four shell stores.
4. Add route-resolution tests.
5. Run all web gates.

## Acceptance criteria

- [ ] History routing is used, not hash routing.
- [ ] All required routes resolve.
- [ ] `/settings` redirects to `/settings/appearance`.
- [ ] Unknown routes render a visible fallback.
- [ ] Zustand state is limited to sidebar, dialogs, toasts, and drafts.
- [ ] No streaming, provider, onboarding, or chat behavior exists.
- [ ] Web lint, typecheck, tests, and build pass.

## Verification

```bash
cd web && pnpm lint
cd web && pnpm typecheck
cd web && pnpm test
cd web && pnpm build
```

## Out of scope

- Feature screens, route data loading, conversation sidebar, search, and export/import UI.
- Static-host fallback configuration for production. That belongs to M4; Vite dev behavior is enough for M0.

Record the route tree shape, the placeholder components used, and any route that intentionally redirects or returns a fallback.
