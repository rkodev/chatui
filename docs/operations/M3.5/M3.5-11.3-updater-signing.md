# M3.5-11.3 - Auto-update manifests, signing, and verification

- Milestone: M3.5
- Status: Not started
- Order: 43
- Depends on: M3.5-11.2, M3.5-04.1
- Parallel-safe: yes, with M3.5-10.*
- Owns: `rust/apps/desktop/src/updater.rs`, `rust/dist/manifests/`, `docs/operations/M3.5/update-signing.md`, updater tests
- Read first: [M3.5 plan](../M3.5-rust-desktop-implementation-plan.md) sections 3.7 and 4.13; spec sections 10.10, 12.6, 14.5

## Goal

Implement signed update manifests over HTTPS with pinned public keys, stable/beta channels, signature verification before apply, and a guard against updating during an active stream.

## Preconditions

- Packaging artifacts and the secret store exist.
- Do not commit private signing keys.
- Do not apply an update whose manifest signature fails.
- Do not auto-update during an active stream without asking.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Update-manifest schema containing:
  - app version;
  - channel (`stable` or `beta`);
  - target OS/architecture;
  - artifact URL and checksum;
  - minimum supported version if applicable;
  - signature.
- Manifest signing tooling or documented process. Public keys are pinned in the app; private keys live only in CI secrets.
- Updater client:
  - fetch over HTTPS;
  - verify signature with a pinned key;
  - verify checksum;
  - refuse downgrade or cross-channel surprises;
  - ask before updating during an active stream.
- Stable/beta channel setting.
- Tests for valid/invalid signatures, tampered artifacts, wrong channel, and stream guard.
- `docs/operations/M3.5/update-signing.md`.

## Implementation steps

1. Read spec sections 10.10, 12.6, and 14.5.
2. Define the manifest schema and version it. Keep it independent of the release artifact list.
3. Generate a signing key pair outside the repository. Store the private key in CI secrets only. Pin the public key in the app.
4. Implement manifest signing in the release pipeline or a local script. Do not embed the private key.
5. Implement the updater client:
   - fetch the channel manifest over HTTPS;
   - verify the signature before parsing or applying anything;
   - verify the artifact checksum;
   - compare versions and channels;
   - reject tampered or unsigned manifests.
6. Add a channel setting and persist it.
7. Guard active streams: if a stream is in progress, ask before applying. Never silently restart.
8. Add tests using generated test keys and temporary manifests. Never use production keys.
9. Document the signing process, key rotation, and public-key pinning.

## Acceptance criteria

- [ ] An update-manifest schema exists.
- [ ] Manifests are signed and verified before apply.
- [ ] Public keys are pinned; private keys are never committed.
- [ ] Artifact checksums are verified.
- [ ] Stable/beta channels work.
- [ ] Downgrade and cross-channel surprises are rejected or explicitly handled.
- [ ] Updates during an active stream require user confirmation.
- [ ] Tampered/unsigned manifests fail closed.
- [ ] Tests use test keys only.
- [ ] Signing documentation exists.
