## Goal

Keep the proven bounded-composition behavior after the adaptive-shell and lifecycle changes.

## Preconditions

- M3-05.2 is complete.
- `ChatMessageListTest` currently has a 10,000-message test; reuse it.
- Do not rewrite the message list unless the test exposes a regression.

## Deliverables

- The 10,000-message test still passes after M3 changes.
- A bounded-composition assertion (fewer than a documented threshold of rows composed).
- Assertion that the newest message is visible and stable keys/content types are used.
- A short performance note in the handoff.

## Implementation steps

1. Run the existing `ChatMessageListTest` and record the result.
2. Keep or extend the 10,000-message test:
   - build 10,000 deterministic messages;
   - count composed rows;
   - assert the count is less than a bounded threshold (the current test uses <100);
   - assert the newest message is visible.
3. Add a case with an active streaming row to prove history rows do not all recompose when a token arrives.
4. Add a case with duplicate-prone keys/ids to prove stable identity.
5. If a shell change regressed composition, fix the list/shell with stable keys and content types; do not remove the test.
6. Record the result and any device performance note in the handoff.

## Handoff notes

- Reused the existing `ChatMessageListTest` cases: the 10,000-message bounded-composition test (fewer than 100 rows composed, newest message visible), the streaming-token recomposition test, and the in-place update identity test.
- Added `duplicate-prone ids keep stable identity and do not collide with the streaming row`. It uses three messages with identical text and sequence values but distinct ids, updates the middle row in place, and then starts a stream whose id matches a history id. This proves keys come from `Message.id` and that the streaming row replaces rather than duplicates a history key.
- No production code changed. `ChatMessageList` already uses `key = { it.id }` and `contentType = { it.role.name }` for history rows, and a separate `streaming-<id>` key/content type for the active stream.
- Performance note: the 10,000-message case composes fewer than 100 rows on the Robolectric/JVM path, so composition stays bounded after the M3 shell and lifecycle changes. No device frame-time measurement was taken; this task only gates bounded composition and history recomposition.
