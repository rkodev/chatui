# M5-06.1 - Android WorkManager scheduling

- Milestone: M5
- Status: Complete
- Order: 18
- Depends on: M5-05.2
- Parallel-safe: yes, with `M5-06.2` and `M5-06.3`
- Owns: `android/feature/backup/`, `android/app/`
- Read first: [M5 plan](../M5-backup-and-sync-implementation-plan.md) sections 3.6 and 5.3; spec sections 13.1 and 13.7; `android/gradle/libs.versions.toml`

## Goal

Schedule automatic backup on Android with WorkManager, respecting network and
battery constraints. The worker must call the sync engine and must never upload
plaintext.

## Preconditions

- `M5-05.2` is `Complete` and the backup UI can enable backup.
- WorkManager is already declared in the version catalog and app module.
- Do not add a foreground service or an exact alarm.

## Deliverables

- `android/feature/backup/.../work/BackupWorker.kt`:
  - `CoroutineWorker` that calls `SyncEngine.sync()`.
  - Returns `Result.retry()` on transient failures and `Result.failure()` on
    permanent errors.
  - Never logs secrets or content.
- `android/feature/backup/.../work/BackupScheduler.kt`:
  - `schedulePeriodic()` with `Constraints` for network and battery.
  - `cancel()`.
  - Unique work name so repeated enables do not duplicate work.
  - Minimum interval appropriate for backup (for example 6 hours).
- App wiring:
  - Schedule when backup is enabled.
  - Cancel when backup is disabled.
  - Re-schedule on boot if WorkManager persists work (document behavior).
- Tests:
  - Worker calls the sync engine and maps results.
  - Scheduler enqueues unique periodic work with constraints.
  - Disable cancels work.
  - No plaintext path is introduced.

## Implementation steps

1. Read the backup UI, sync engine, and existing WorkManager dependency.
2. Add `BackupWorker` as a `CoroutineWorker`. Inject the sync engine through the
   existing dependency mechanism.
3. Add `BackupScheduler` with `PeriodicWorkRequestBuilder` and `Constraints`:
   - `NetworkType.CONNECTED`.
   - `setRequiresBatteryNotLow(true)`.
   - `enqueueUniquePeriodicWork` with `ExistingPeriodicWorkPolicy.UPDATE`.
4. Wire enable/disable in the backup settings flow.
5. Add tests using `WorkManagerTestInitHelper` and a fake sync engine.
6. Run the Android gates.

## Completion record

- Added `BackupWorker` as a `CoroutineWorker` in
  `android/feature/backup/.../work/`. It calls `BackupSyncRunner.sync()` and
  maps transient storage/I/O failures to `Result.retry()` and permanent
  failures to `Result.failure()`. It never logs content or secrets.
- Added `BackupScheduler` with a 6-hour unique periodic request,
  `NetworkType.CONNECTED`, `setRequiresBatteryNotLow(true)`, exponential
  backoff, and `ExistingPeriodicWorkPolicy.UPDATE`.
- Added `BackupScheduling`/`NoOpBackupScheduling` so the settings service can
  schedule and cancel without depending on WorkManager in unit tests.
- Wired enable/disable in `BackupSettingsService`: enabling schedules periodic
  work, disabling cancels it. Hilt provides the real scheduler and the worker's
  sync runner through `BackupModule`.
- WorkManager persists periodic work across process death and reboots, so no
  boot receiver, foreground service, or exact alarm was added.
- Added worker, scheduler, and service scheduling tests.

## Handoff notes

- The worker reuses `BackupSettingsService.backupNow()`, which builds the
  `SyncEngine` from the saved config, encrypted credentials, and the in-memory
  passphrase. Because the passphrase is never persisted by design, a worker run
  after process death cannot decrypt or encrypt and returns `Result.failure()`.
  Automatic backup therefore works while the app process (and its service
  singleton) is alive; a future task would need an explicit, user-approved
  passphrase-cache decision to support cold-start background sync.
- WorkManager timing is best-effort. The 6-hour interval is a cadence, not an
  exact schedule; Android may defer work to respect network and battery
  constraints.
- `androidx.work:work-testing` is added as a test-only dependency using the
  catalog's WorkManager version.
