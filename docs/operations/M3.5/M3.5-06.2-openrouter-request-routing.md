## Goal

Serialize normalized chat requests into the exact OpenRouter body and headers, including supported-parameter filtering, routing controls, attribution, and protected-field rejection.

## Preconditions

- Domain types and HTTP client exist.
- Do not implement streaming parsing in this task.
- Do not copy request vectors or provider metadata.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- A request builder from `NormalizedChatRequest`, model `supportedParameters`, and app config.
- System prompt as the first `messages` entry when present.
- Text, image, and file content parts serialized as the shared vectors expect.
- `stream` from `params.streaming`.
- `stream_options = { "include_usage": true }` for streaming.
- Optional controls emitted only when supported:
  - `max_tokens`;
  - `temperature`;
  - `top_p`;
  - `stop`;
  - `reasoning = { effort }`.
- Curated OpenRouter routing under `provider`:
  - `allow_fallbacks`;
  - `sort` (`price`, `throughput`, `latency`);
  - `data_collection` (`allow`, `deny`).
- Advanced JSON passthrough for `order`, `only`, `ignore`, `models`, and `route` only where the plan allows.
- Protected-field rejection for `model`, `messages`, `stream`, and `stream_options`, with `details.protectedFields` sorted ascending.
- Attribution headers `HTTP-Referer` and `X-Title` from `AppConfig`.
- Tests against all OpenRouter request vectors.

## Implementation steps

1. Read `contracts/fixtures/requests/README.md` and every `openrouter-*.json` request vector.
2. Define the serialization API. Keep it independent of HTTP transport so it can be unit-tested.
3. Build the `messages` array:
   - system prompt first;
   - each normalized message in order;
   - concatenate text and file parts as the vectors require;
   - emit image parts as OpenAI-style content parts.
4. Emit sampling controls only when present and supported by the selected model.
5. Emit `reasoning.effort` only when `reasoningEffort` is set and `reasoning` is supported.
6. Emit curated routing only when configured. Do not invent defaults.
7. Reject protected fields in advanced JSON before building the body. Collect offending keys, sort them, and return `invalid_request`.
8. Build attribution headers from `AppConfig`. Never include personal data.
9. Add tests for basic, routing, advanced-protected, attribution, unsupported-parameter, and default-model vectors.
10. Ensure unsupported controls are omitted, never sent.

## Handoff notes

- Request API (`openrouter::request`):
  - `NormalizedChatRequest` / `NormalizedChatMessage` mirror spec 7.3 and use the shared `ChatParams` and `ContentPart` types.
  - `ResolvedAttachment` carries `mimeType`, `name`, and `dataBase64` for image and file parts.
  - `build_body(&NormalizedChatRequest, &[String], &BTreeMap<String, ResolvedAttachment>) -> Result<Value, ChatError>` is transport-independent and is what the shared vectors exercise.
  - `build_request(..., &AppConfig) -> Result<PreparedChatRequest, ChatError>` adds the attribution headers.
  - `attribution_headers(&AppConfig)` resolves the bundled OpenRouter preset mapping (`HTTP-Referer -> app.origin`, `X-Title -> app.name`).
  - `select_default_model(&str, &[DefaultModelCandidate]) -> DefaultModelSelection` implements the deterministic default-model rule used by `openrouter-default-model.json`.
- Supported-parameter rules:
  - `stream` always mirrors `params.streaming`; `stream_options = { "include_usage": true }` is emitted only for streaming requests.
  - `max_tokens`, `temperature`, `top_p`, and `stop` are emitted only when the value is present/non-empty and the model's `supported_parameters` contains the matching name.
  - `reasoning = { "effort": ... }` is emitted only when `reasoningEffort` is set and `reasoning` is supported; otherwise it is omitted.
- Routing behavior:
  - `provider` is emitted only when `params.extra.openrouter.provider` is present.
  - Curated keys: `allow_fallbacks` (bool), `sort` (`price`/`throughput`/`latency`), `data_collection` (`allow`/`deny`).
  - Advanced keys: `order`, `only`, and `ignore` under `provider`; `models` and `route: "fallback"` at the top level.
  - Unknown advanced keys and malformed routing values return `invalid_request`; no defaults are invented.
- Protected fields:
  - `model`, `messages`, `stream`, and `stream_options` are rejected before the body is built.
  - The error is `invalid_request` with `details.protectedFields` sorted ascending and the exact message `Advanced JSON cannot override protected fields: <sorted keys>.`.
- Content serialization:
  - The system prompt is the first `messages` entry when present.
  - Text and file parts concatenate into `content`; file parts use `\n\n[File: <name>]\n<utf-8 content>`.
  - Any image part switches the message to an ordered OpenAI-style content array with `image_url` data URLs.
  - Reasoning and tool parts are not sent back to the provider.
- Tests (`rust/crates/chatui-providers/tests/openrouter_request.rs`):
  - `every_openrouter_request_vector_matches` covers all six OpenRouter request vectors.
  - Named vector tests: `basic_vector_serializes_system_first_and_supported_max_tokens`, `routing_vector_serializes_curated_provider_controls`, `advanced_protected_vector_rejects_sorted_fields`, `attribution_vector_uses_app_config`, `unsupported_parameter_vector_omits_reasoning`, `default_model_vector_matches_selection_rule`.
  - Additional coverage: hidden preset default, text/file concatenation, image data URLs, missing/invalid attachments, non-streaming `stream_options`, reasoning support gating, advanced routing passthrough, unknown/invalid advanced keys, combined body+headers, and no key/personal data.
- Vector ambiguity:
  - There is no `openrouter-attachments.json` vector. Text/image/file behavior is covered by synthetic tests using the shared README rules and the OpenAI-compatible content-part shape.
  - The task lists `default-model` as a request vector even though selection is catalog behavior; the deterministic rule is implemented in `request.rs` so the vector can be exercised without expanding scope into the catalog module.
  - Advanced `reasoning.max_tokens` / `reasoning.exclude` from spec 7.4 are not passed through because this task's deliverable limits advanced passthrough to `order`, `only`, `ignore`, `models`, and `route`.
