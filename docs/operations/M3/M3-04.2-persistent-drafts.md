## Goal

Persist per-conversation draft text so a process death does not discard typed work, while keeping the store bounded and non-secret.

## Preconditions

- M3-04.1 is complete.
- Drafts are non-secret UI text. Do not store attachments, keys, or provider secrets in this store.
- Do not change the `ChatDrafts` call sites unless a nullable/suspend API is unavoidable.

## Deliverables

- A persistent `ChatDrafts` implementation backed by the existing typed settings store or a dedicated DataStore.
- Bounded storage: a maximum number of conversations and a maximum length per draft.
- Drafts restored when a chat opens and cleared after a successful send.
- Tests proving persistence across a new store instance and bounded eviction.
- A handoff note describing the storage key and limits.

## Implementation steps

1. Read `ChatDrafts.kt`, `ChatViewModel` draft methods, `ChatModule.provideChatDependencies`, `SettingsDataStore`, and `AndroidSettings`.
2. Add a non-secret preference key such as `drafts_json` to `SettingsDataStore` and a typed accessor such as `suspend fun setDrafts(map: Map<String, String>)`.
3. Implement `PersistentChatDrafts`:
   - keep an in-memory `ConcurrentHashMap` cache for synchronous `draftFor`/`setDraft`/`clearDraft`;
   - load persisted drafts once at construction or through the settings flow;
   - persist writes with debounce (for example 500 ms) on an application-scoped coroutine;
   - cap each draft (for example 32,000 characters) and the number of stored drafts (for example 50);
   - evict the oldest/least-recently updated drafts when the cap is exceeded.
4. Replace `InMemoryChatDrafts()` in `ChatModule.provideChatDependencies` with the persistent implementation. Keep the interface unchanged.
5. Ensure `ChatViewModel.setDraft("")` clears the persisted entry and that send success still clears the draft.
6. Add tests:
   - set, recreate the store, and read the same draft;
   - clear removes the entry;
   - exceeding the conversation cap evicts old entries;
   - exceeding the per-draft cap truncates or rejects safely;
   - no attachment or provider key is written.
7. Record the storage key and bounds in the handoff notes.

## Acceptance criteria

- [ ] Drafts survive a new store instance or app relaunch.
- [ ] Drafts are restored per conversation and do not leak across conversations.
- [ ] Sending a message clears its draft.
- [ ] Storage is bounded by count and length.
- [ ] No secret or attachment data is stored in the draft store.
- [ ] Existing draft behavior and tests remain green.
