- Milestone: M3.5
- Status: Complete

- Read first: [M3.5 plan](../M3.5-rust-desktop-implementation-plan.md) sections 3.7 and 4.13; spec sections 10.10, 12.6, 14.5

## Goal

Implement signed update manifests over HTTPS with pinned public keys, stable/beta channels, signature verification before apply, and a guard against updating during an active stream.

## Preconditions

- Packaging artifacts and the secret store exist.
- Do not commit private signing keys.
- Do not apply an update whose manifest signature fails.
- Do not auto-update during an active stream without asking.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Update-manifest schema containing:
  - app version;
  - channel (`stable` or `beta`);
  - target OS/architecture;
  - artifact URL and checksum;
  - minimum supported version if applicable;
  - signature.
- Manifest signing tooling or documented process. Public keys are pinned in the app; private keys live only in CI secrets.
- Updater client:
  - fetch over HTTPS;
  - verify signature with a pinned key;
  - verify checksum;
  - refuse downgrade or cross-channel surprises;
  - ask before updating during an active stream.
- Stable/beta channel setting.
- Tests for valid/invalid signatures, tampered artifacts, wrong channel, and stream guard.
- `docs/operations/M3.5/update-signing.md`.

## Implementation steps

1. Read spec sections 10.10, 12.6, and 14.5.
2. Define the manifest schema and version it. Keep it independent of the release artifact list.
3. Generate a signing key pair outside the repository. Store the private key in CI secrets only. Pin the public key in the app.
4. Implement manifest signing in the release pipeline or a local script. Do not embed the private key.
5. Implement the updater client:
   - fetch the channel manifest over HTTPS;
   - verify the signature before parsing or applying anything;
   - verify the artifact checksum;
   - compare versions and channels;
   - reject tampered or unsigned manifests.
6. Add a channel setting and persist it.
7. Guard active streams: if a stream is in progress, ask before applying. Never silently restart.
8. Add tests using generated test keys and temporary manifests. Never use production keys.
9. Document the signing process, key rotation, and public-key pinning.

## Handoff notes

### Result (2026-11-08)

Implemented the signed update-manifest path in
`rust/apps/desktop/src/updater.rs` and documented it in
`docs/operations/M3.5/update-signing.md`.

Manifest schema:

- Versioned envelope: `schemaVersion`, base64 `payload`, base64 Ed25519
  `signature`.
- Signed payload: `schemaVersion`, `appVersion`, `channel`, `target`
  (`os`/`arch`), `artifact` (`url`/`sha256`/`size`), optional
  `minimumSupportedVersion`, optional `publishedAt`.
- JSON Schema and illustrative signed examples live in
  `rust/dist/manifests/` (`schema.json`, `example-stable.json`,
  `example-beta.json`, `README.md`).

Signing and verification:

- The updater parses only the envelope, verifies the signature over the exact
  payload bytes with a pinned key, and only then parses the payload.
- Pinned public keys are `PINNED_STABLE_PUBLIC_KEY` and
  `PINNED_BETA_PUBLIC_KEY` in `updater.rs`. They are development keys generated
  for this task; the private keys were discarded and are not committed.
- Artifact size and SHA-256 are verified in `Updater::apply` before returning
  `VerifiedArtifact`.
- Downgrades, versions below `minimumSupportedVersion`, wrong targets,
  non-HTTPS URLs, malformed checksums, oversized manifests/artifacts, and
  cross-channel manifests are rejected.
- `Updater::check(streaming)` returns `ConfirmationRequired` when a stream is
  active; `apply` refuses without `confirmed == true`.

Channels:

- `Channel::{Stable, Beta}` with default manifest URLs in `ManifestUrls`.
- The channel preference persists through `FileChannelStore` at
  `<config>/chatui/update-channel.json`; `MemoryChannelStore` is used in tests.
- `Updater::set_channel` is the settings-UI integration point.

Tests (all in `updater.rs`, test keys only, no network):

`pinned_keys_parse`, `valid_manifest_verifies_and_parses`,
`beta_channel_uses_beta_url`, `tampered_payload_fails_signature`,
`unsigned_manifest_fails_closed`, `wrong_channel_signature_is_rejected`,
`cross_channel_key_is_rejected`, `tampered_artifact_fails_checksum`,
`downgrade_is_rejected`, `up_to_date_is_reported`,
`minimum_supported_version_is_enforced`, `wrong_target_is_rejected`,
`insecure_artifact_url_is_rejected`, `invalid_checksum_is_rejected`,
`unsupported_schema_is_rejected`, `oversized_manifest_is_rejected`,
`insecure_manifest_url_is_rejected_before_network`,
`stream_guard_requires_confirmation`, `channel_setting_persists_in_memory`,
`file_channel_store_round_trips`, `example_manifests_verify_with_pinned_keys`.

Decisions and notes:

- The updater lives in the desktop binary because it is a desktop-only
  integration concern. `main.rs` only declares `mod updater;`; no UI wiring was
  added because the settings UI is outside this task's scope.
- Added `base64`, `ed25519-dalek`, `hex`, `reqwest` (blocking + rustls),
  `semver`, and `sha2` to the desktop crate; `Cargo.lock` was updated.
- The channel preference is stored in the updater's own JSON file rather than
  the shared `Settings` entity, which is outside this task's owned paths.
- `rust/dist/` is a build-output directory. `.gitignore` now re-includes
  `rust/dist/manifests/` so the schema and examples are tracked while installers
  and checksums remain ignored.
- The pinned keys are development keys. Production key ownership is still
  `unknown` (B-05); the release owner must generate production key pairs, store
  the private keys in CI secrets, and replace the pinned public keys before a
  production release. This is an external credential/ownership decision, not an
  implementation gap.
- The actual installer handoff is release automation (M3.5-11.4); `apply`
  returns verified bytes and does not replace the running binary.
- No private keys, installers, or build outputs were committed.
