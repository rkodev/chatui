- Milestone: M3.5
- Status: Complete
- Order: 13
- Depends on: M3.5-01.1
- Parallel-safe: yes, with M3.5-02.* and M3.5-03.*

- Read first: [M3.5 plan](../M3.5-rust-desktop-implementation-plan.md) sections 3.4 and 4.6; spec sections 10.6, 12.6, 14.5

## Goal

Create a secret-store abstraction and an OS credential-store implementation using `keyring`, with no plaintext fallback.

## Preconditions

- The workspace exists.
- Do not implement the encrypted-file fallback in this task; M3.5-04.2 owns it.
- Do not place keys in URLs, filenames, environment dumps, or provider records.
- Do not log secret values.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- A `SecretStore` trait with operations for:
  - set/get/delete a key by secret ID;
  - forget key;
  - forget all keys;
  - report whether the OS store is available.
- A `KeyringStore` backed by the `keyring` crate.
- Consistent service/account naming that does not leak conversation content or personal data.
- Error types that do not include the secret value.
- Tests using `keyring`'s mock credential builder or an in-memory test double. Do not depend on a real OS store for unit tests.
- A documented OS availability and fallback decision.

## Implementation steps

1. Read spec section 10.6 and the Android `SecretStore`/`TinkSecretCipher` for behavior.
2. Add `keyring` with the appropriate platform features for Linux Secret Service, macOS Keychain, and Windows Credential Manager. Keep the dependency feature set minimal.
3. Define the `SecretStore` trait in `store.rs`. Use `zeroize`-friendly types or explicit ownership rules for values returned to callers.
4. Implement `KeyringStore`:
   - service name: a stable app identifier;
   - account name: a stable secret ID, never the provider key or label;
   - set/get/delete operations;
   - availability probe.
5. Map keyring errors to local error types without including the secret or raw credential material.
6. Implement `forget_key` and `forget_all_keys` using the store API and a local secret ID index. Keep the index non-secret.
7. Add tests with `keyring::mock::MockCredentialBuilder` or an equivalent. Cover set/get/delete, missing key, unavailable store, and no-secret-in-error.
8. Document Linux Secret Service, macOS Keychain, and Windows Credential Manager behavior, including what happens when the store is unavailable.
9. Do not add a silent file fallback. The caller must explicitly select the fallback from M3.5-04.2.

## Handoff notes

- Trait API: `SecretStore` exposes `set`, `get`, `delete`, `forget_key`,
  `forget_all_keys`, and `is_available`. It is object-safe and injectable as
  `Arc<dyn SecretStore>`. `SecretId` validates stable non-secret IDs;
  `SecretValue` wraps a `zeroize::Zeroizing<String>` and redacts `Debug`;
  `SecretError` carries only sanitized categories, never a secret value or raw
  credential material.
- Keyring naming: service is the stable identifier `dev.chatui.desktop`.
  Account names are validated `SecretId` values, never provider keys or labels.
  Two reserved accounts are rejected as secret IDs:
  `__chatui_secret_index__` (non-secret ID index) and
  `__chatui_availability_probe__` (read-only availability probe).
- Index: `forget_all_keys` uses a newline-delimited, non-secret index stored in
  the reserved keyring account. It is updated on set/delete and removed when
  empty. Keys written by another tool are not indexed and are not removed by
  `forget_all_keys`.
- Test approach: `KeyringStore` accepts an injected `EntryFactory`. Unit tests
  use `keyring::mock::MockCredentialBuilder` through a mock factory and a
  shared-mock factory for cross-instance index persistence. No unit test touches
  a real OS credential store.
- OS availability: Linux uses Secret Service over D-Bus, macOS uses Keychain,
  and Windows uses Credential Manager. `is_available` reads the reserved probe
  account; a missing entry means the store is reachable. On this Linux audit
  host, GNOME Keyring exposed `org.freedesktop.secrets` and a read-only probe
  returned `keyring_available=true`. macOS and Windows evidence remains owned by
  the M3.5-12.1 OS matrix (SEC-10).
- Fallback decision: there is no silent plaintext fallback. When
  `is_available` is false, operations return `SecretError::Unavailable` and the
  caller must explicitly select the encrypted-file fallback from M3.5-04.2.
- Dependency decision: `keyring` 3.6.3 with `default-features = false` and
  features `apple-native`, `windows-native`, `sync-secret-service`, and
  `crypto-rust`. Version 3.x is required because the task specifies
  `keyring::mock::MockCredentialBuilder`; 4.x has a different API. `zeroize`
  provides the value buffer. `rust/Cargo.lock` was updated by the dependency
  addition.
- Verification: `cargo fmt --all --check` passed; `cargo clippy -p
  chatui-secrets --all-targets -- -D warnings` passed; `cargo nextest run -p
  chatui-secrets` passed 15/15 tests.
