## Goal

Prove the desktop UI is keyboard reachable, has visible focus, provides accessible names, respects reduced motion, and passes at least one screen-reader smoke test per tier-1 OS.

## Preconditions

- All UI feature tasks are complete enough to navigate.
- Do not claim screen-reader coverage that was not run.
- Do not record personal data or real conversations in evidence.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- `docs/operations/M3.5/accessibility.md` with:
  - keyboard navigation results;
  - focus-visible results;
  - accessible names for icon-only controls;
  - live-region behavior for response start/complete/errors;
  - reduced-motion behavior;
  - contrast notes;
  - one screen-reader smoke test per tier-1 OS, or a precise blocker.
- Automated checks in the UI test harness where the framework supports them.
- Accessibility evidence in `M3.5-verification.md`.

## Implementation steps

1. Read spec section 11.11 and the framework decision's accessibility notes.
2. Audit every interactive element for keyboard reachability and visible focus.
3. Audit icon-only buttons for accessible names.
4. Audit streaming announcements: announce start, completion, and errors, not every token.
5. Verify reduced-motion behavior for transitions and streaming indicators.
6. Check contrast for body text, large text, and UI boundaries against section 11.11 thresholds.
7. Run a screen-reader smoke test on each available OS:
   - Windows: Narrator;
   - macOS: VoiceOver;
   - Linux: Orca or the available screen reader.
   Record the OS, screen reader, build, steps, and result.
8. If an OS or screen reader is unavailable, record a blocker instead of a pass.
9. Add automated semantics/focus tests where possible.
10. Record the evidence in `M3.5-verification.md`.

### Keyboard and focus

- Shell destinations, drawer close, settings sections, data sections, composer,
  message-list actions, providers, models, and onboarding all expose focusable
  controls. Settings and Data sidebars were converted from pointer-only
  rectangles to focusable buttons with Space/Return activation.
- Focus rings come from the token set (2 px, 2 px offset) and appear only for
  keyboard focus (`FocusReason.tab-navigation`).
- AT-SPI inspection of the running shell found the five menu labels, the
  `Navigation` landmark with five named destination buttons, and the `Chat`
  landmark; every destination accepted `grab_focus()` and reported `FOCUSED`.

### Accessible names and live regions

- Every `button`, `checkbox`, `combobox`, and `text-input` in the audited windows
  now has a non-empty accessible name. Icon/compact controls use explicit names
  such as `Toggle navigation`; text buttons inherit the visible text.
- Streaming announcements are bounded to 160 characters, emitted only on start,
  completion, cancellation, and error, and exposed as a polite/assertive live
  region. Token deltas do not change the announcement.
- Reduced motion resolves to zero app-owned transition durations and a static
  streaming indicator.
- Contrast passes: body text is at least 4.53:1, focus rings 5.77:1, and strong
  control boundaries 3.26:1 at their worst measured values.

### Blockers and limitations

- Linux Orca is blocked by the local GNOME schema/Orca incompatibility. Re-run
  the manual Orca smoke test on a compatible host before claiming a Linux
  screen-reader pass.
- Windows Narrator and macOS VoiceOver remain blocked by missing hosts.
- The desktop binary still hosts only the shell. Feature windows are proven by
  their Slint component tests; end-to-end screen-reader navigation of those
  screens needs the desktop composition work tracked by M3.5-10.2 and
  M3.5-10.3.
- The UI crate adds `rust/crates/chatui-ui/build.rs` to emit Slint compiler
  debug info in debug profiles only, so the accessibility-tree tests work
  without affecting release artifacts.
