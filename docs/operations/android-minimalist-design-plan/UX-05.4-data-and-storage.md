# UX-05.4 - Data actions and operation states

- Phase: UX-05 - Settings, data, and backup
- Status: Blocked
- Order: 32
- Depends on: UX-05.1
- Output folder: `docs\operations\android-minimalist-design-plan`
- Parallel-safe: No with DataSettingsScreen/DataSettingsDestination feedback edits.

## Goal

Put ordinary data work before destructive actions and make picker/import/export
feedback truthful without weakening any data-loss safeguards.

## Read first

Read the [execution contract](README.md), source-plan sections 5.7, 6,
and 8, `SettingsUI\DataSettingsScreen.kt`,
`SettingsUI\DataSettingsViewModel.kt`, `SettingsUI\DataControlsService.kt`,
`Shell\DataSettingsDestination.kt`, and existing data/import/export tests.

## Owns

Data-screen ordering/state presentation, required activity-result/operation
feedback wiring in the shell destination/ViewModel, and focused data tests.
Import/export serialization and destructive service semantics stay unchanged.

## Deliverables

Storage-first layout, working export/import/key/backup paths, and distinct
pending/success/error/cancel states with unchanged confirmations.

## Implementation steps

1. Order content: storage total, optional existing breakdown, Export, Import,
   stored API keys, real backup link/status, destructive controls last.
   Use existing statistics; do not add composition-time scans.
2. Preserve secret-free plaintext export and its warning, document pickers,
   merge/replace import, validation, individual-key removal, and every exact
   destructive confirmation/undo behavior.
3. Keep both data and root Settings backup entries routed to the same real
   encrypted-backup feature. Do not treat stale settings copy as lack of backup.
4. Trace picker launch through actual reader/writer/service completion.
   Opening a picker is not export/import success; cancellation is not failure.
   Keep an operation pending only for work actually in progress.
5. Give errors a persistent actionable owner and results one presentation
   path. Avoid duplicate inline/snackbar copies of the same operation outcome;
   UX-05.5 handles the remaining cross-settings feedback/copy reconciliation.
6. Preserve file-validation failures, insufficient permission/storage failure,
   replace cancellation, and existing key/provider/history consequences.
7. Add cases for export success only after write, picker cancel, read/write/
   validation failure, merge versus replace, exact confirmation gates,
   key removal, backup navigation, and small/large-font ordering.

## Acceptance criteria

- [x] Everyday export/import precede destructive controls.
- [x] All data actions retain formats, secret exclusion, and confirmations.
- [x] Picker launch/cancel/completion produce truthful single feedback.
- [x] Backup link works and no new full-data scan runs during composition.

## Out of scope

semantics, database migrations, or loosening typed confirmations.

## Handoff notes

Implemented on 2026-11-17. **Blocked on UX-05.1 and real SAF/permission/
recreation evidence in UX-06.5; owner: Android maintainer.**

- Changed `SettingsUI\DataSettingsScreen.kt`, `DataSettingsRoute.kt`,
  `DataSettingsViewModel.kt`, `Shell\DataSettingsDestination.kt`, and the
  existing `History\export\ExportDocumentWriter.kt` /
  `History\importer\ImportDocumentReader.kt` helpers and focused tests.
  Order is storage total/breakdown, Export, Import, keys, real backup, Danger
  zone. Usage still comes from the existing service, never a composition scan.
- `DataDocumentState` owns SAF state and its ViewModel operation scope.
  Preparation, picker waiting, actual read/write/import, success, cancellation
  and failure are distinct. Export success follows stream close; import
  success follows reader plus validated import completion. Picker launch is
  not success; waiting on the picker does not show a work spinner.
  JSON preparation/import validation and document IO run off the main thread.
- One inline result/error owner replaces duplicate snackbars/dialogs.
  Internal key/clear work and external file results supersede one another;
  active operations disable competing key/file/clear actions and cannot be
  reset through a stale error dismissal. Duplicate launches are guarded.
  Coroutine cancellation is not converted into a success/error message.
- Plaintext export warning/secret exclusion, archive format, merge versus
  separately confirmed replace, inline two-step key deletion and exact
  `DELETE ALL DATA` remain unchanged. Both Settings/Data backup paths resolve
  to the real feature. No new attachment-byte export option was invented.
- The **40 settings**, **108 conversations**, and seven app settings-route
  cases pass. The app cases use a fake ActivityResultRegistry, actual fixture
  files and real import/export services: consent/picker cancel, missing picker,
  write/read/validation failure, export completion, merge and replace cancel.
  Existing import/export/service suites cover actual merge/replace semantics
  and secret exclusion. `DataSettingsScreenTest` also guards concurrent key
  actions and stale results. Lint passes; exact commands/results are in the
  [verification record](README.md#ux-0506-verification-record).
- `integrated_data_storage_360_*` and the affected standalone phone/tablet
  goldens show the intentional hierarchy. Fake results are not evidence of
  Android grant persistence, real document providers or lifecycle recovery.
