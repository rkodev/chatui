## Goal

Deliver the complete web attachment flow from input to provider-specific content parts.

## Preconditions

- Web attachment byte store and metadata repository exist.
- Provider adapters support or reject attachments through shared capability helpers.

## Deliverables

- File picker, drag-and-drop, and clipboard image paste.
- Type and size validation for images and text files.
- Image downscale to 2048 px longest edge, re-encode where appropriate, and metadata stripping.
- Content-addressed storage and transactional metadata persistence.
- Composer chips/thumbnails, removal before send, and message rendering after send.
- Provider-specific content parts: OpenAI data URLs, Anthropic base64 blocks, Gemini `inlineData`, and text-file headers.
- Capability warnings and confirmation when switching to a text-only model with attachments.
- Reload, orphan cleanup, and invalid-file tests.

## Handoff notes

- Size/type limits: images are PNG, JPEG, WebP, and GIF up to 20 MiB; text files are `.txt`, `.md`, `.json`, `.csv`, common source/config extensions, and the supported text MIME types up to 2 MiB. Unknown MIME types are rejected rather than guessed from the extension. File names are sanitized before persistence and display.
- Downscale/re-encode decisions: images are scaled so the longest edge is at most 2048 px and always re-encoded through canvas: JPEG remains JPEG, PNG/WebP/GIF become WebP with a PNG fallback. Re-encoding strips EXIF and other container metadata. If the browser cannot decode an image, the original bytes are stored unchanged so the attachment is not lost. Animated GIFs are flattened to their first frame by this path.
- Provider content-part mapping: OpenAI-compatible requests use ordered `text` + `image_url` data URLs plus `text` file headers; Anthropic uses base64 `image` blocks; Gemini uses `inlineData`; Ollama uses the `images` array. Text files always serialize as `\n\n[File: <name>]\n<body>`. Attachment bytes are read from the local content-addressed store, never from a provider URL.
- Capability warnings: images require the selected model's `image` input modality. Text files remain supported by any text-capable model because they serialize as text. The composer shows the warning and a confirmation dialog before sending unsupported attachments; it can remove them or cancel.
- Persistence and cleanup: metadata is committed in one IndexedDB transaction per add batch. Composer removal deletes metadata and unreferenced bytes; edit-last-user removes attachments for the edited and truncated messages. Startup cleanup deletes draft metadata (`messageId: null`), metadata for missing messages (for example after conversation deletion), and bytes with no metadata row.
