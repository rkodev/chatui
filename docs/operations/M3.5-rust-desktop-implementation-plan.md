# M3.5 Rust Desktop Implementation Plan

- Source milestone: [M3.5-rust-desktop.md](../milestones/M3.5-rust-desktop.md)
- Authoritative spec: [IMPLEMENTATION.md](../IMPLEMENTATION.md)
- Related plans: [M1 plan](M1-openrouter-core-implementation-plan.md), [M2 plan](M2-providers-and-content-implementation-plan.md), [M3 plan](M3-android-depth-implementation-plan.md)
- Current parity: [contracts/parity.md](../../contracts/parity.md)
- Status: Proposed
- Prepared: 2026-11-07
- Scope: Rust desktop client only: Windows, macOS, and Linux. Includes the headless core, shared UI shell, thin desktop shell, conformance, packaging, signing, and release evidence.
- Platforms: Windows x86_64, macOS Apple Silicon (and Intel if supported), Linux x86_64 (and aarch64 if supported).
- Planning assumption: M0 and M1 are complete. M2 is the behavior reference for the full desktop parity target. M3 is in progress and is not a dependency. Rust is optional and parallel; it must not delay web or Android work.
- Out of scope for this plan: web/Android implementation changes, Android/iOS/WASM Rust targets, backup/sync (M5), managed hosting (M6), and phase-2 work.

## 1. Summary

M3.5 is greenfield. The repository contains only `.gitkeep` placeholders under `rust/`; there is no Cargo workspace, toolchain pin, Rust source, test harness, desktop shell, CI workflow, packaging, or release evidence. The shared contracts and the web/Android reference implementations are mature, so the risk is execution breadth rather than unspecified behavior.

The largest missing areas are:

- The workspace itself, including `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, crate manifests, and the desktop app.
- The UI framework spike and a locked decision before feature UI.
- The Rust domain, contract loader, strict serde types, and fixture-driven conformance harness.
- SQLite storage, migrations, FTS5 search, attachments, recovery, and export/import.
- `keyring`, the encrypted-file fallback, session-only mode, redaction, and zeroization.
- The shared `reqwest` transport, bounded SSE/NDJSON parsers, retry policy, and all provider adapters.
- The complete desktop UI: onboarding, providers/models, chat, composer, Markdown, attachments, conversations, settings, and export/import.
- Desktop OS integration, accessibility evidence, packaging, signed updates, and the cross-platform CI matrix.
- An honest Rust implementation-status section in `contracts/parity.md` and an M3.5 verification report.

The milestone's 3-4 week target is optimistic for a single implementer. The plan keeps the workstreams parallelizable so a small team can land a credible first release, and it explicitly separates the core/OpenRouter slice (M3.5a) from the UI/release slice (M3.5b).

                        |
                        +--> M3.5-07 Additional providers
                                   |

   |
M3.5-09 Chat, composer, Markdown, attachments, conversations
   |
M3.5-10 Settings, export/import UI, desktop integration, accessibility
   |
M3.5-12 Conformance, parity, release gate, evidence

The hard path is `00 -> 01 -> 02 -> 05 -> 06 -> 08 -> 09 -> 10 -> 12`. Storage and secrets can run beside networking after the domain lands. Packaging can start once the UI shell exists and must finish before the final gate.

### 2.3 Foundation-to-feature gaps that are easy to miss

- **The contracts are rich but unowned by Rust.** `contracts/fixtures/expected/` is the conformance oracle, but there is no Rust crate, no fixture loader, and no test target. A workspace that does not consume every expected vector can pass `cargo test` while failing the milestone.
- **The Makefile targets are not the milestone gate.** `make rust-test` runs `cargo test`, while the milestone requires `cargo nextest run --workspace`. There are no targets for `cargo fmt --check`, `cargo deny`, `cargo audit`, fixture conformance, packaging, or UI tests. The gate will be under-enforced unless the Makefile is extended.
- **The placeholder target tree includes forbidden targets.** `rust/apps/wasm`, `rust/apps/android`, and `rust/apps/ios` exist even though the milestone says desktop only. They must not become workspace members; removing them is cleaner than documenting an exception.
- **Tauri cannot be a production choice under the current boundary.** The milestone asks the spike to compare "a Tauri shell", but also forbids a WebView-based production client. Tauri can be a comparison/reference point only. Choosing it requires an explicit milestone/spec change.
- **FTS5 is a Rust-specific requirement, not a copy of Android.** Android deliberately uses FTS4 because of minSdk constraints. Rust must use FTS5 and must guarantee the bundled SQLite exposes it. That depends on how `sqlx` or `rusqlite` links SQLite.
- **`Settings.rememberKeysOnWeb` is a shared schema field with no desktop meaning.** Rust must round-trip it for export compatibility without pretending it controls desktop secret storage. The desktop behavior needs a separate policy or a documented mapping.
- **Provider `browserCors` is irrelevant on desktop but part of the provider record.** Rust should preserve it for contract/export compatibility and ignore it for transport decisions.
- **The web/Android conformance baseline is not a code-sharing baseline.** Adapter behavior, fixture expectations, and UI semantics can be reused; TypeScript and Kotlin code cannot. The Rust implementation is a reimplementation against the vectors.
- **The Rust UI must be designed to the shared token and accessibility bar, not just "compile on Linux".** Screen-reader smoke tests, high-DPI behavior, and native menus are manual evidence.
- **M3.5 completion implies Rust is enabled for release.** While the track is optional, the milestone's exit gate requires signed artifacts and signed update manifests. A "we built the core but did not package it" result cannot be marked complete without an approved scope reduction.
- **The release matrix in the milestone is narrower than the tier-1 target.** CI requires Linux x86_64, macOS Apple Silicon, and Windows x86_64; section 10.1 also lists macOS Intel and Linux aarch64. Confirm whether those are required for M3.5 or documented as manual/future.
- **OS credential stores and signing are environment-bound.** `keyring` on Linux needs a Secret Service provider, macOS needs Keychain access, Windows needs Credential Manager; signing needs Apple and Windows certificates. CI and local environments cannot manufacture these credentials.
- **The updater is a supply-chain boundary, not a convenience.** Signed manifests, pinned public keys, stable/beta channels, and no update during an active stream are security requirements, not release polish.
- **No "enabled" flag exists in the repository.** `contracts/parity.md` uses "Required when enabled" but nothing records whether Rust is in the scope of the current release. The preflight decision must create that record before packaging and parity claims.

### 6.4 Enablement definition

M3.5 can be marked complete only when one of these is true:

1. Rust is explicitly enabled for release, the full exit gate is satisfied, signed artifacts and update manifests exist, parity reflects the delivered behavior, and M4 includes Rust.
2. Rust is explicitly deferred or declined, the work is not claimed as complete, `contracts/parity.md` remains honest (`Optional` / not implemented), and M4 does not depend on it.

Partial implementation cannot be reported as M3.5 completion.

## 7. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| UI framework is immature or cannot meet accessibility/packaging needs | Blocked UI or poor desktop UX | Time-box the spike, keep core crates UI-agnostic, and choose a fallback early |
| Framework spike turns into feature work | Schedule slip before any user value | Gate feature UI on the decision; keep the spike to a prototype and criteria |
| Tauri comparison is mistaken for a production option | Violates the no-WebView boundary | Document the disqualification in the decision record |
| SQLite FTS5 is unavailable in the chosen build | Search fails on some platforms | Verify FTS5 at startup and in CI; use bundled SQLite where needed |
| Secret stores differ by OS/desktop environment | Insecure fallback or failed startup | Detect availability, require explicit encrypted fallback, and test each OS |
| Signing/notarization credentials are unavailable | No shippable artifacts | Provision CI secrets early; fail the release job when absent |
| Update signing keys are mishandled | Supply-chain compromise | Pin public keys, verify manifests before apply, and keep private keys only in CI secrets |
| Binary size/build time exceed budget | Slow CI and large installers | Tune the release profile, gate features, and cache targets |
| Cross-platform CI runners are slow or unavailable | Schedule risk | Use native runners, cache aggressively, and split OS jobs |
| Rust work distracts from web/Android | Missed phase-1 gate | Keep Rust optional, parallel, and out of web/Android build paths |
| Contract changes leak into Rust tasks | Cross-milestone conflict | Require a separate approved shared-contract task; do not edit web/Android |
| Markdown/math rendering introduces XSS-equivalent risks | Security issue | No raw HTML, sanitize links, block remote images, fall back to raw source |
| Export/import accepts hostile input | Data loss or path traversal | `jsonschema`, size limits, safe attachment names, no content execution |
| Retrieval/model drift makes fixtures stale | False confidence | Keep fixtures shared and regenerate expected vectors only through contract tasks |
| The 3-4 week target is treated as a commitment | Overrun and poor quality | Publish the staffing-based estimate and checkpoint after the spike |

## 8. Out of Scope

- Any change to `web/` or `android/` from M3.5 tasks.
- Rust targets for Android, iOS, or WebAssembly.
- A WebView-based production client.
- Replacing the web or Kotlin Android client.
- Backup/sync (M5) and managed hosting (M6).
- A second streaming event model or provider-specific serialization in the UI.
- Live payloads, real API keys, personal data, or production conversation content in fixtures, screenshots, logs, or CI artifacts.
- Store distribution beyond GitHub Releases for the Rust desktop client unless M4 broadens it.
