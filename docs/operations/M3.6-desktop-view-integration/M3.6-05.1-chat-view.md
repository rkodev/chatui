## Goal

Add the Chat view and controller that compose the existing message list and
composer windows into one destination, wire send, stop, regenerate, retry, and
attachments to `ChatService`, and render live streaming state.

## Preconditions

- `M3.6-02.1` provides the shared runtime, repositories, and streaming store.
- `M3.6-03.1` provides the Chat message and composer host containers.
- Do not duplicate chat business logic; call `ChatService`, `ChatRunner`, and
  the existing composer/message-list controllers.
- Do not block the Slint thread on network or streaming work.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- `chat/view.rs` with:
  - a `ChatWindow` Slint component that stacks the message list and composer,
    or embeds them through `ComponentContainer` using the proven pattern;
  - `sync_window`/controller methods for empty, loading, error, streaming, and
    announcement states;
  - `ChatController` owning `ChatService`, `ChatRunner`, `MemoryStreamingStore`,
    `MessageListController`, `ComposerController`, and a runtime handle.
- Behavior:
  - load a conversation's newest page;
  - send a message through `ChatService`;
  - stop an active stream;
  - regenerate and retry;
  - poll `MemoryStreamingStore` for the live row;
  - attach and remove files through the existing composer flow;
  - persist and restore drafts;
  - copy message/code payloads through the existing clipboard helpers.
- Exports from `chat/mod.rs` and `lib.rs`.
- Tests with a temporary database and a fake stream adapter.

## Implementation steps

1. Read the chat runner and message-list controller integration points.
2. Define the Chat view layout and properties/callbacks.
3. Build `ChatController` with a runtime handle and the shared repositories.
4. Wire send, stop, regenerate, retry, load-older, copy, and composer actions.
5. Start streaming on the runtime; surface start/complete/error announcements
   through the existing helpers.
6. Poll the streaming store and update only the live row and scroll offset.
7. Reload persisted messages on terminal events.
8. Wire attachments, paste, drag-and-drop, and draft persistence.
9. Add tests: send, stop, regenerate, retry, streaming row, empty/error states,
   attachments, and drafts.
10. Export the controller and window from the crate root.

- Decisions:
  - Added `chat/view.rs` with `ChatWindow`, `sync_window`, `ChatViewState`,
    `ChatRuntime`, `ChatControllerDeps`, and `ChatController`.
  - `ChatController` composes `ChatService`, `ChatRunner`, `MemoryStreamingStore`,
    `MessageListController`, and `ComposerController`; it does not duplicate
    chat business logic.
  - All async work (page loads, send, stop, regenerate, retry, older pages)
    runs through the injected `ChatRuntime`. Results return over a
    `std::sync::mpsc` channel and are applied by `ChatController::poll` on the
    Slint thread. This matches the History controller and works under
    `init_no_event_loop`.
  - `ChatWindow` hosts the message list and composer with
    `ComponentContainer` factories. The shell may instead embed the two
    controller handles directly; a host must use one approach or the other, not
    both, because both embed the same handles.
  - Streaming reloads history once when a new live row appears (to show the
    persisted user message) and once on the terminal event. Token updates only
    replace the isolated streaming row and scroll offset.
  - Terminal reloads clear the streaming snapshot before applying the newest
    page, so the persisted assistant row is not filtered out by the streaming
    row's message ID.
  - The composer owns attachments, validation, paste/drop input, and draft
    persistence; the chat controller exposes thin pass-through methods and
    handlers for the native file picker, clipboard paste, removal, and copy.
  - Announcements reuse the existing bounded announcement helpers and remain
    polite for start/complete and assertive only for errors.

## Handoff notes

- `ChatController` constructor:
  `ChatController::new(deps: ChatControllerDeps) -> Result<Self, slint::PlatformError>`.
  `ChatControllerDeps` carries the `ChatService`, shared `ChatRunner`,
  `MemoryStreamingStore`, conversation/message/model repositories, `DraftStore`,
  `SendKey`, `ChatRuntime`, `MessageListConfig`, and an optional
  `initial_conversation_id`.
- Open/load method:
  `ChatController::open(conversation_id: impl Into<String>)` switches the active
  conversation, restores its draft, resets the list, and loads the newest page.
  Passing `initial_conversation_id` to `new` calls `open` automatically.
- The current conversation ID lives in `ChatController`; callers supply it to
  `open` and read it back with `conversation_id()`. `send`, `stop`,
  `regenerate`, `retry`, and `load_older` always target that active
  conversation, so the desktop should call `open` when navigation changes.
- Streaming polling cadence: call `poll()` from a Slint timer every 50-100 ms
  (the plan starts at 50 ms). `poll()` drains completed async events, reads the
  live row from `MemoryStreamingStore`, and returns immediately, so it is safe
  on the Slint thread.
- Public methods for `M3.6-06.1`:
  - `messages_window()` and `composer_window()` for the shell's
    `chat-messages-factory` and `chat-composer-factory`.
  - `standalone_window()` when using the bundled `ChatWindow` host instead.
  - `state()`, `sync()`, `poll()`, `open()`, `conversation_id()`,
    `is_streaming()`, `send()`, `stop()`, `regenerate()`, `retry()`,
    `load_older()`, `add_attachment()`, `remove_attachment()`,
    `validate_files()`, `set_attachment_error()`, and `set_model()`.
  - `set_on_copy()`, `set_on_attach()`, `set_on_paste_image()`, and
    `set_on_remove_attachment()` for host-owned native actions.
- Implement `ChatRuntime` over the shared `ServiceRuntime`/`tokio` handle:
  `fn spawn(&self, future: Pin<Box<dyn Future<Output = ()> + Send + 'static>>)`.
  Do not create a second runtime, and keep the controller alive for the shell's
  lifetime.
