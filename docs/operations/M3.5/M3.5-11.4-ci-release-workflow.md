- Milestone: M3.5
- Status: Complete

- Depends on: M3.5-11.2, M3.5-11.3
- Parallel-safe: none; needs packaging and updater
- Owns: `.github/workflows/rust.yml`, `.github/workflows/rust-release.yml` (or equivalent), `docs/operations/M3.5/ci.md`

## Goal

Add a Rust CI matrix and tag-driven release workflow that enforce fmt, clippy, tests, release builds, deny/audit, packaging, signing, notarization, checksums, and update-manifest publication.

## Preconditions

- Packaging and updater configuration exist.
- Do not commit signing keys or certificates.
- Do not use a debug or self-signed substitute for release signing.
- Do not modify web or Android workflows except for a shared runner/cache if explicitly required.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- `.github/workflows/rust.yml` triggered on pull requests, pushes to `main`, and relevant tags:
  - install pinned toolchain;
  - cache Cargo registry and targets;
  - `cargo fmt --all --check`;
  - `cargo clippy --workspace --all-targets -- -D warnings`;
  - `cargo nextest run --workspace`;
  - conformance suite;
  - `cargo build --release --workspace`;
  - `cargo deny check`;
  - `cargo audit`.
- Matrix: Linux x86_64, macOS Apple Silicon, Windows x86_64.
- A tag-driven release workflow that:
  - builds and packages artifacts;
  - signs/notarizes where credentials exist;
  - generates checksums;
  - signs update manifests;
  - publishes a GitHub Release.
- A documented list of required CI secrets (names only).
- `docs/operations/M3.5/ci.md`.

## Implementation steps

1. Read spec sections 10.11, 16.3, and 14.5, plus the existing web/Android workflows for style.
2. Create the CI workflow with a matrix for the required OS/architectures. Use native runners where possible.
3. Install the pinned toolchain from `rust-toolchain.toml`. Install `cargo-nextest`, `cargo-deny`, and `cargo-audit` in CI only.
4. Cache Cargo registry and target directories per OS. Do not cache secrets.
5. Run fmt, clippy, nextest, conformance, release build, deny, and audit.
6. Create the tag release workflow. Build packages, sign/notarize when credentials exist, generate checksums, sign update manifests, and attach artifacts to the GitHub release.
7. Fail the release job when required signing/notarization credentials are absent. Do not fall back to unsigned production artifacts unless the decision record explicitly allows an unsigned preview.
8. Document required secret names and which job uses them. Do not include values.
9. Run the workflow locally with `act` or a dry-run if available; otherwise record the CI-only blocker.
10. Update `docs/operations/M3.5/ci.md` with the matrix, jobs, secrets, and artifact names.

## Handoff notes

### Result (2026-11-08)

Added the Rust CI matrix and the tag-driven release workflow.

Workflow paths:

- `.github/workflows/rust.yml`
- `.github/workflows/rust-release.yml`
- `docs/operations/M3.5/ci.md`

CI matrix:

| Name | Runner | Rust target |
| --- | --- | --- |
| Linux x86_64 | `ubuntu-latest` | `x86_64-unknown-linux-gnu` |
| macOS Apple Silicon | `macos-14` | `aarch64-apple-darwin` |
| Windows x86_64 | `windows-latest` | `x86_64-pc-windows-msvc` |

CI commands:

- `cargo fmt --all --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo nextest run --workspace`
- `cargo nextest run -p chatui-conformance`
- `cargo build --release --workspace --locked`
- `cargo deny check`
- `cargo audit`

The toolchain channel is read from `rust/rust-toolchain.toml` at run time.
`Swatinem/rust-cache` caches the Cargo registry and `rust/target` per OS.
`cargo-nextest`, `cargo-deny` (0.20.2), and `cargo-audit` (0.22.2) are installed
in CI only.

Release workflow:

- Runs only on `v*` (stable) and `beta-*` (beta) tags.
- `verify` runs the same gates before packaging.
- `build` runs on the three matrix runners, builds the release workspace,
  signs the Windows binary with `signtool`, imports the Apple certificate and
  configures the notarization profile, packages with
  `python rust/packaging/package.py --skip-build --target <target>`, writes
  per-target `SHA256SUMS-<target>`, signs a per-target update manifest, and
  uploads the artifacts.
- `publish` combines the checksum files into `SHA256SUMS` and publishes a
  GitHub Release with `softprops/action-gh-release`.
- The `Verify required signing credentials` step exits non-zero when a required
  secret is absent. There is no unsigned production fallback.

Required secret names (values are never committed or printed):

`UPDATE_SIGNING_PRIVATE_KEY_STABLE`, `UPDATE_SIGNING_PRIVATE_KEY_BETA`,
`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`,
`APPLE_NOTARY_PROFILE`, `APPLE_NOTARY_APPLE_ID`, `APPLE_NOTARY_TEAM_ID`,
`APPLE_NOTARY_PASSWORD`, `WINDOWS_CERTIFICATE`,
`WINDOWS_CERTIFICATE_PASSWORD`.

Artifact and manifest names are documented in
[ci.md](ci.md#artifact-names) and [ci.md](ci.md#update-manifests).

Blockers:

- **CI-only execution:** `act` is not installed, and macOS Apple Silicon and
  Windows x86_64 runners are not available locally (B-01, B-02). No GitHub
  Actions run link exists for this task.
- **Signing credentials:** Apple signing/notarization and Windows Authenticode
  credentials are absent (B-03, B-04). The release workflow is expected to fail
  closed until they are provisioned.
- **Update-signing key ownership:** production key ownership is `unknown`
  (B-05). The workflow expects `UPDATE_SIGNING_PRIVATE_KEY_STABLE` and
  `UPDATE_SIGNING_PRIVATE_KEY_BETA`.
- **Deny config:** `rust/deny.toml` uses the pre-0.16 advisories schema. A
  follow-up task that owns `rust/deny.toml` must migrate it to the current
  cargo-deny schema before the deny gate can pass.
- **Audit advisory:** `rsa 0.9.10` is affected by RUSTSEC-2023-0071 with no
  fixed upgrade. A follow-up task that owns the dependency graph must replace
  or isolate the crate, or record an approved, narrowly scoped exception.

Decisions:

- The CI workflow triggers on both `main` and `dev` because the specification
  names `main` while the repository currently uses `dev` as its default branch.
- The release workflow publishes per-target update manifests
  (`update-<channel>-<target>.json`) because a manifest describes one target.
  The updater's default channel URL must be pointed at the target-specific
  manifest or a hosting redirect before production use.
- `cargo-deny` and `cargo-audit` are pinned in CI for reproducibility. The
  pinned versions expose the pre-existing config and advisory blockers above.
- No signing keys, certificates, installers, or build outputs were committed.
