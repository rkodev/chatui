## Goal

Implement the settings surfaces and wire every setting to real behavior: appearance, chat defaults, provider/model defaults, data entry points, backup placeholder, and about/privacy.

## Preconditions

- The shell and chat runner exist.
- Do not add dead controls.
- Do not expose secrets or hidden network destinations.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Settings layout and routes for:
  - appearance: theme, density, chat font size, reduced motion;
  - chat defaults: send key, show token usage, remote images, default system prompt, default params;
  - providers/models entry points;
  - data entry point;
  - backup placeholder;
  - about/privacy.
- Behavior wiring for every setting that already has a consumer.
- Persistence through the settings repository.
- Tests for each setting affecting the relevant UI or behavior.
- No dead controls; unsupported future settings are labeled clearly.

## Implementation steps

1. Read spec sections 3.8 and 6.2 (Settings), plus `web/src/features/settings/*`.
2. Build a settings view model over the settings repository. Load defaults when no row exists.
3. Implement appearance settings and apply them to the shell/chat font/theme.
4. Implement chat defaults: send key, token usage visibility, remote images, default system prompt, and default parameters.
5. Wire provider/model defaults and onboarding completion status.
6. Add data and backup entry points. The data screen itself is M3.5-10.2; the backup screen is a placeholder only.

## Handoff notes

### Routes

- `/settings` redirects to `/settings/appearance`.
- `/settings/appearance`, `/settings/chat`, `/settings/providers`, `/settings/models`, `/settings/data`, `/settings/backup`, `/settings/about`.
- `SettingsRoute::destination` maps appearance/chat/backup/about to `Destination::Settings`, providers/models to `Destination::Providers`, and data to `Destination::Data`.

### Persistence

- The complete `Settings` object is loaded and saved through `chatui_storage::SettingsRepository`; defaults are merged when no row exists.
- `RepositorySettingsPersistence` is the async adapter over `SettingsRepository` for startup and tests.
- `SettingsService` uses the synchronous `SettingsStore` trait so the Slint controller can persist on each control change. The desktop app can implement `SettingsStore` with a blocking adapter over `SettingsRepository`; `MemorySettingsStore` is the test/startup cache.
- `settings_persist_across_repository_instances` proves values survive a new repository instance over the same SQLite database.
- `settings_persist_across_database_reopen` proves values survive closing and reopening a file-backed database.

### Wiring decisions

- Appearance -> `ShellState.theme` through `ThemeSettings` (theme, density, chat font size, reduced motion).
- Send key -> `ComposerState::set_send_key`.
- Token usage -> `MessageListState::set_show_token_usage`.
- Remote images -> `RenderOptions::load_remote_images`.
- Default system prompt and parameters -> `DefaultConversationFactory` reads the same persisted settings; `default_prompt_and_params_seed_new_conversations` proves new conversations inherit them.
- Provider/model defaults -> persisted settings consumed by the model picker and conversation factory; `set_default_provider_model` validates provider/model ownership.
- Onboarding completion -> persisted settings consumed by `OnboardingService::is_onboarding_complete`.
- Provider/model/data entry points -> `SettingsController::set_on_open_providers`, `set_on_open_models`, and `set_on_open_data` let the app open the real management screens. Without a handler the section remains selected so the window is still usable.

### Display-only and future settings

- Reduced motion follows the operating-system preference; it is not stored separately because the shared `Settings` contract has no reduced-motion field.
- `rememberKeysOnWeb` is web-only; desktop keys use the OS keyring or encrypted fallback store.
- `lastActiveConversationId` is internal resume state, not a user control.
- `onboardingCompleted` is set by the onboarding flow and shown as status.
- `backup` is a placeholder for M5; the backup section has no active controls.

### Tests

- `settings::route::tests::*` cover routes, paths, and shell destinations.
- `settings::service::tests::*` cover defaults, persistence, normalization, provider/model validation, onboarding completion, and catalog degradation.
- `settings::state::tests::*` cover appearance resolution, provider/model indices, display-only/future labels, about/privacy, and combo-box round trips.
- `settings::view::tests::*` cover the Slint window, every control callback, entry-point handlers, and consumer wiring.
- `settings::tests::*` cover SQLite persistence across instances, new-conversation seeding, token-usage metadata, remote-image rendering, and secret-free view models.
