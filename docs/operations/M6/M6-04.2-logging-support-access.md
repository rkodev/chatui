## Goal

Define and document the tenant logging, retention, and support-access policy. The
docs must be enforceable by the external operator and must state that support
cannot recover keys, read chats, restore a passphrase, or access encrypted
backups.

## Preconditions

- `M6-02.1` is `Complete` and the edge/logging model is known.
- `M6-01.1` recorded the privacy reviewer, logging fields, retention periods, and
  support model.
- Do not document log fields, retention periods, or support tooling that the
  operator has not confirmed.
- Do not record actual log samples containing real IPs, keys, or user content.

## Deliverables

- `docs/hosting/logging-and-retention.md`:
  - Log categories: edge/access logs, deployment/control-plane logs, error logs,
    and security/audit logs.
  - Allowed fields: timestamp, tenant, hostname, path, status, response size,
    latency, IP address, user agent, request ID, and deployment/actor ID where
    applicable.
  - Prohibited fields: request bodies, provider keys, authorization headers,
    prompts, responses, plaintext chats, storage credentials, backup
    passphrases, and decrypted content.
  - Why provider and storage bodies are not in ChatUI logs: those requests go
    browser-direct and bypass the ChatUI edge.
  - Retention periods for each log category, who can access them, deletion
    process, and legal/security holds.
  - Redaction rules for headers and diagnostic output.
  - Incident/log-access procedure and notification ownership.
  - Region note for log storage and residency.
  - A short verification checklist the privacy reviewer can use.
- `docs/hosting/support-access.md`:
  - Purpose and scope of tenant support.
  - Support roles and permissions. Least privilege by default.
  - No impersonation of the user's browser, no remote-control access, no local
    database access, no provider-key access, and no backup-object decryption.
  - Support cannot recover provider keys, read plaintext chats, restore a
    deleted conversation, recover a lost passphrase, or decrypt a user's backup.
  - What support can see: tenant/deployment status, public config, edge/access
    logs, and operator-side metadata.
  - Audit requirements: who accessed what, when, why, and the review owner.
  - Escalation and user-verification process for account/tenant requests.
  - Incident response and law-enforcement/legal-request handling, with an owner
    and policy placeholder where legal review is required.
  - Subprocessor/third-party list only if the operator confirms it; otherwise
    mark as a legal-review blocker.
  - Link data-processing, logging, provider-terms, and privacy docs. Forward
    links to `privacy.md`/`data-processing.md` are allowed because `M6-04.1`
    owns them; `M6-04.3` rechecks them.

## Implementation steps

1. Read the recorded decisions for logging, retention, support, and region.
2. Confirm which log categories and fields the external operator actually has.
3. Write the allowed/prohibited field lists and retention table.
4. Write the redaction and incident procedures.
5. Write the support roles, permissions, audit, and no-recovery statements.
6. Add the legal/subprocessor placeholders and mark unconfirmed items as
   blockers.
7. Cross-link the privacy docs and provider terms.
8. Review for any statement that implies support can access user data.

## Acceptance criteria

- [ ] Both docs exist and are consistent with the recorded decisions.
- [ ] Log categories, fields, exclusions, retention, access, and deletion are
      documented.
- [ ] Prohibited fields include keys, prompts, responses, chats, storage
      credentials, and passphrases.
- [ ] The docs explain why provider/storage bodies bypass ChatUI logs.
- [ ] Support roles, least privilege, no impersonation, audit, and escalation
      are documented.
- [ ] No-recovery for keys, chats, passphrases, and backups is explicit.
- [ ] Unconfirmed operator/legal items are recorded as blockers.
- [ ] No real log sample, IP, key, or user content is included.

## Verification

Manual review against the recorded decisions and the edge template. The dated
privacy/legal approval and support-access enforcement check are part of
`M6-04.3` and `M6-06.1`.

## Out of scope

- Implementing log retention or support tooling.
- Legal approval (`M6-04.3`).
- A full subprocessor list without operator confirmation.
- Changing app logging behavior.

## Handoff notes

Record confirmed log fields, retention periods, access owners, support roles, and
all unresolved operator or legal dependencies here.
