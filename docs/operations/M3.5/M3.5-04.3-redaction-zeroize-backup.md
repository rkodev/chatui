## Goal

Prevent secret leakage through logs, panics, errors, and cloud backup, and prove the sensitive-buffer lifecycle is intentional.

## Preconditions

- Keyring and fallback secret stores exist.
- Do not log request or response bodies in release builds.
- Do not add telemetry, analytics, or remote logging.
- Do not record real keys in tests or evidence.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- A `tracing` redaction layer that scrubs:
  - `Authorization`;
  - `x-api-key`;
  - `x-goog-api-key`;
  - `anthropic-dangerous-direct-browser-access` if it ever carries a secret;
  - custom header values marked secret;
  - bearer tokens and API-key-shaped strings.
- A panic hook that does not print secrets.
- A release logging policy with debug-only subscriber setup.
- `zeroize` use for keys, passphrases, derived keys, and temporary secret buffers.
- Backup/exclusion implementation or documented procedure for macOS, Linux, and Windows.
- A source audit for key use in URLs, filenames, environment dumps, and error messages.
- Tests for redaction, panic safety, and no-plaintext behavior.
- Security evidence recorded in `M3.5-verification.md`.

## Implementation steps

1. Read spec sections 10.6, 12.1, and 12.6.
2. Add `tracing`, `tracing-subscriber`, `zeroize`, and any small redaction helpers. Keep the subscriber debug-only.
3. Implement a redaction layer or formatting wrapper that replaces known secret header values and token-shaped strings. Do not rely on log-call discipline alone.
4. Install a panic hook that omits secret values and request bodies. Keep enough context for diagnostics.
5. Audit every `Debug` implementation on secret-bearing types. Implement custom `Debug` that prints `[redacted]` or omit the type from logs.
6. Audit `zeroize` on secret buffers and add it where missing.
7. Implement or document backup exclusion:
   - macOS: mark the app-data directory or database as excluded from backups where supported;
   - Linux: document the expected backup behavior and, if available, use an appropriate exclusion mechanism;
   - Windows: document the expected backup/OneDrive behavior and the database path policy.
8. Audit for keys in URLs, filenames, environment dumps, and error messages.
9. Add tests with sentinel values such as `sk-test-not-a-real-key` to prove redaction. Never use a real key.
10. Record the audit and per-OS evidence in `M3.5-verification.md`.

## Acceptance criteria

- [ ] The logging layer redacts the required headers and token shapes.
- [ ] Panic output does not contain secrets.
- [ ] Release builds do not configure verbose request/response logging.
- [ ] Secret-bearing `Debug` implementations are redacted.
- [ ] Sensitive buffers use `zeroize` or an equivalent documented lifetime policy.
- [ ] Backup exclusion is implemented where supported or documented with an explicit limitation.
- [ ] No key appears in URLs, filenames, environment dumps, or errors.
- [ ] Redaction tests use sentinels only.
- [ ] Security evidence is recorded.
