## Goal

Document the complete "Deploy to ChatUI" flow and its external operator handoff
contract without implementing a control plane or backend. A user or smaller
model must be able to follow the flow, know which inputs are required, and know
what happens on each failure.

## Preconditions

- `M6-02.1` is `Complete` and the template tree exists.
- `M6-01.1` recorded the external operator and the one-click ownership decision.
- Do not invent a live ChatUI URL. Use the owner-supplied URL as a documented
  placeholder.
- Do not add a server component, proxy, key custody, or server-side storage.

## Deliverables

- `docs/hosting/one-click.md` covering:
  - Audience and scope: optional managed static hosting for the web client.
  - Preconditions: web build available, tenant owner identified, optional custom
    domain ready.
  - Step 1: user chooses "Deploy to ChatUI" from the owner-supplied entry point.
  - Step 2: user selects subdomain and region, with validation rules.
  - Step 3: optional custom domain entry and DNS/TLS state.
  - Step 4: operator serves the static app and manages TLS.
  - Step 5: user configures providers and keys in the browser after deployment.
  - Step 6: optional BYO object storage onboarding for encrypted backups.
  - Step 7: user receives the permanent tenant URL, status link, and
    "export everything" guidance.
  - Inputs and outputs table, including tenantId, subdomain, region, custom
    domain, release pin, public config path, and config hash.
  - Failure states with user-facing recovery: subdomain taken, invalid region,
    DNS not verified, TLS pending/failed, deploy failed, config validation
    failed, health check failed.
  - Explicit statement: ChatUI never receives provider keys, plaintext chats,
    storage credentials, or backup passphrases.
  - Explicit statement: there is no server-side prompt proxy or key custody.
  - Post-deploy checklist linking provider setup, BYO storage, export, privacy,
    and support docs.
  - Owner/operator responsibilities and support escalation, leaving the actual
    support contact to the owner-supplied value.
- A short entry-point section that identifies the external URL placeholder, for
  example `<CHATUI_DEPLOY_URL>`, and says the operator owns it.

## Implementation steps

1. Read the template README, tenant schema, public config templates, and M5
   backup onboarding.
2. Write the user flow in ordered steps.
3. Add the inputs/outputs table and the external-operator responsibility table.
4. Write the failure-state matrix and recovery steps.
5. Link the custom-domain, health/status, BYO storage, backup/restore, privacy,
   export, and support docs.
6. Confirm every claim against the actual template and config behavior.
7. Check for a live URL; if none exists, leave the placeholder and record the
   operator dependency in `Handoff notes`.
