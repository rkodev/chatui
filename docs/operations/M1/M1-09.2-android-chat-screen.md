## Handoff notes

### State hoisting

`ChatRoute` owns the `ChatViewModel` and collects both the chat state and the
typed `SettingsDataStore`; `ChatScreen` and every child composable are
presentational and forward intents. The composer draft lives in
`ChatDrafts`, keyed by conversation id, so leaving and reopening a conversation
restores typed text. `ChatViewModel` mirrors the draft into `ChatUiState` and
clears it only after the user message is persisted. Provider/model/key
availability is resolved on load and before each send; it is exposed as
`ChatAvailability` and disables the composer for no provider, missing key, or
unavailable model. Offline state comes from a validated default-network
callback and disables send while keeping history readable.

### Paging cursor

The first page is `messages.latest(conversationId, 50)`; its oldest sequence is
the paging cursor. `onLoadOlder` asks the store for messages before that
sequence and prepends them, updating the cursor to the oldest loaded row.
`hasOlder` is true while any row remains below the cursor. The live conversation
flow is filtered to the loaded window so streaming/persisted updates stay
bounded and older pages are only fetched on demand.

### Streaming isolation and announcements

While a response is active, the persisted assistant placeholder is filtered out
of history and a dedicated streaming row, keyed by the stream message id, is
rendered from `StreamingState`. Token updates change only that row; history
items keep their message id keys and content types. `ChatViewModel` updates
`announcement` only when the stream status changes: "Response started",
"Response complete", "Response cancelled", or a plain-language failure. Token
deltas never change it. `ChatScreen` exposes the announcement through a 1 dp
semantics node with `LiveRegionMode.Polite`.

### Scope

Plain text is rendered in this task. Markdown, code blocks, copy, regenerate,
edit-last-user, and the full action row remain M1-09.3.
