## Goal

Write an accurate tenant-facing data-processing summary and privacy overview that
states exactly what ChatUI can and cannot see, how browser-direct provider and
storage traffic works, and what the user controls. This is a technical summary
for review, not a substitute for the privacy reviewer's sign-off.

## Preconditions

- `M6-02.1` is `Complete` and the edge/flows are known.
- `M6-03.1` is `Complete` and the BYO storage onboarding exists.
- `M6-01.1` recorded the privacy/legal reviewer and region/data-residency
  decision.
- Do not publish claims that the external operator cannot enforce. Mark
  unverified statements as review blockers.

## Deliverables

- `docs/hosting/data-processing.md`:
  - Audience and scope: the optional ChatUI-hosted web service.
  - Data-flow summary:
    - ChatUI serves static shell, assets, `config.json`, and `/healthz`.
    - The browser fetches the app from the tenant origin.
    - Provider requests go from the browser directly to the selected provider.
    - BYO storage requests go from the browser directly to the user's bucket.
    - ChatUI is not in the provider or storage request path.
  - "What ChatUI can see" table: tenant origin, requested static paths, IP/user
    agent/edge metadata according to the operator's log policy, public tenant
    config, and deployment records. No request bodies from provider/storage
    traffic.
  - "What ChatUI cannot see" table: provider API keys, prompts, responses,
    plaintext chats, local IndexedDB/OPFS data, storage credentials, backup
    objects, and backup passphrases.
  - Encryption note: backups are encrypted client-side before upload; ChatUI has
    no decryption key or passphrase.
  - No analytics, telemetry, third-party scripts, hidden network destinations, or
    server-side prompt proxy.
  - Link logging/retention and support-access docs. Forward links are allowed
    because `M6-04.2` owns those files; `M6-04.3` rechecks them.
  - Link to the provider catalog and provider-terms doc.
  - Region/data-residency summary from the recorded decision, with the limit
    that region controls static edge location only and no server-side user-data
    store exists.
  - A short "user controls" section: keys, local data, export, backup, BYO
    storage, and passphrase.
- `docs/hosting/privacy.md`:
  - A plain-language summary that links to `data-processing.md`,
    `logging-and-retention.md`, `support-access.md`, and `provider-terms.md`.
  - The local-data warning, provider-direct traffic, no analytics, BYO storage,
    passphrase loss, and export path.
  - Contact/support link placeholders owned by the external operator.

## Implementation steps

1. Read the M6 plan privacy section, M4/M5 verification summaries, and About
   screen copy.
2. Write the data-flow summary as a simple diagram or ordered list.
3. Write the "can see" and "cannot see" tables. Keep them factual and testable.
4. Add the encryption, no-analytics, no-hidden-destination, and no-proxy
   statements.
5. Add region/data-residency wording from the recorded decision.
6. Write the plain-language privacy summary and link the detailed docs.
7. Mark any statement that requires operator confirmation as a review blocker in
   `Handoff notes`, not as published fact.

## Acceptance criteria

- [ ] Both docs exist and are internally consistent.
- [ ] The data-flow summary clearly places ChatUI outside provider and storage
      request paths.
- [ ] The "can see" and "cannot see" tables cover all required items.
- [ ] The no-key/no-chat/no-passphrase and no-proxy statements are explicit.
- [ ] The encryption, no-analytics, and no-hidden-network statements are
      explicit.
- [ ] The region/data-residency wording matches the recorded decision.
- [ ] Privacy docs link logging, support, provider terms, and the export path,
      with forward links recorded for recheck by `M6-04.3`.
- [ ] Unverified operator claims are recorded as review blockers.
- [ ] No secret, real key, passphrase, prompt, or chat content is included.
