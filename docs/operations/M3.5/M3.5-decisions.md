# M3.5 Decisions and Release Enablement

- Milestone: M3.5
- Status: Recorded 2026-11-07 by M3.5-00.2
- Owner: Product/release owner for enablement; named area owners for each decision
- Source plan: [M3.5 Rust Desktop Implementation Plan](../M3.5-rust-desktop-implementation-plan.md) sections 5, 6.4, and 10
- Authoritative spec: [IMPLEMENTATION.md](../../IMPLEMENTATION.md) sections 10.1-10.12, 12.6, 14.5, 15.1, 18, and 19
- Evidence baseline: [M3.5-verification.md](M3.5-verification.md)

This file records the decisions that would otherwise be made implicitly during
implementation. Each decision names a recommendation, an owner, and the task it
unblocks. A recommendation is not a substitute for owner sign-off where the
owner is outside the implementation team; those cases are marked explicitly.

No secret values, credentials, signing material, prompts, or personal data are
recorded here. Credential availability is recorded only as `available`,
`unavailable`, or `unknown`.

## 2. Enablement decision (DEC-01, DEC-15)

**Decision: `defer` for the current release.**

The plan's DEC-01 recommendation is to proceed only when a small team and
OS/signing access exist; otherwise defer and keep parity `Optional`. The
preflight baseline records that:

- macOS Apple Silicon and Windows x86_64 runners or machines are `unknown`
  (B-01, B-02).
- macOS notarization credentials and Windows code-signing certificates are
  `unknown` (B-03, B-04).
- Update-signing key ownership is `unknown` (B-05).

Without those, the full exit gate in plan section 6.4 cannot be satisfied:
signed artifacts, signed update manifests, and per-OS smoke evidence cannot be
produced. Recording `proceed` would create a completion claim the repository
cannot support.

Consequences recorded now:

- M3.5 is **not complete** and must not be reported as complete.
- `contracts/parity.md` stays honest: the Rust column remains
  `Required when enabled` and no Rust implementation status is claimed.
- M4 does not depend on Rust while this decision stands.
- Implementation tasks may still run as a parallel preview. A preview build is
  not a release and does not change the parity claim.
- The decision is revisited when B-01 through B-05 are resolved. A later
  `proceed` decision must record that the full exit gate applies and that M4
  must include Rust if it ships.

Owner: Product/release owner. The implementation team records the recommendation
and evidence; the owner confirms or changes the release decision.

## 3. Platform and architecture matrix (DEC-02)

Spec section 10.1 lists Windows x86_64, macOS (Apple Silicon and Intel), and
Linux (x86_64 and aarch64) as tier 1 when enabled. The first enabled release
recommendation is narrower because no Intel or aarch64 runner is available.

| OS | Architecture | Spec tier | First enabled release | Evidence / condition |
| --- | --- | --- | --- | --- |
| Windows | x86_64 | Tier 1, required when enabled | Required | Needs a Windows x86_64 runner or machine (B-02) and a code-signing certificate (B-04). |
| macOS | Apple Silicon (aarch64) | Tier 1, required when enabled | Required | Needs a macOS Apple Silicon runner or machine (B-01) and notarization credentials (B-03). |
| macOS | Intel (x86_64) | Tier 1, required when enabled | Manual/future | No Intel host or runner is available. Revisit before enablement if universal binaries are required. |
| Linux | x86_64 | Tier 1, required when enabled | Required | This host is Linux x86_64; CI must add a native Linux job. |
| Linux | aarch64 | Tier 1, required when enabled | Manual/future | No aarch64 host or runner is available. Revisit before enablement if aarch64 artifacts are required. |

The macOS Intel and Linux aarch64 rows are a documented narrowing of spec
section 10.1, not a silent change. The Product/release owner must approve the
narrowing before a `proceed` decision, or provision the missing runners and
restore both rows to required.

Owner: Product/release owner with Verification/OS owner. Unblocks: M3.5-11.2
(packaging), M3.5-11.4 (CI matrix), and M3.5-12.2 (final gate).

## 4. Storage decisions (DEC-03, DEC-04)

### 4.1 SQLite backend

Recommendation: `sqlx` with the `runtime-tokio` and `sqlite` features and a
bundled SQLite build, if that build preserves FTS5 and works offline in CI.
Otherwise use `rusqlite` with the `bundled` feature and FTS5.

Required behavior either way:

- WAL mode, `foreign_keys = ON`, and a busy timeout.
- Versioned migrations tested from an empty database.
- All writes through repositories; UI code never issues SQL.
- No network access during build or test.

The backend choice is confirmed by the M3.5-03.1 spike. If `sqlx` cannot prove
FTS5 and offline builds, the task switches to `rusqlite` without reopening this
decision.

Owner: Storage owner. Unblocks: M3.5-03.1 and M3.5-03.2.

### 4.2 FTS5 provisioning and proof

Recommendation: require a SQLite build with FTS5 and prove it in three places:

1. A startup capability check that fails closed with a clear error if FTS5 is
   absent.
2. A migration test that creates the FTS5 virtual table from an empty database.
3. A repository/search test that inserts messages and runs a `MATCH` query,
   including the shared search fixtures where applicable.

The `sqlite3` CLI is unavailable on this host (B-08), so proof must come from
Rust tests and the bundled library, not manual CLI inspection.

Owner: Storage owner. Unblocks: M3.5-03.1 and M3.5-03.2.

## 5. Contract decisions (DEC-05, DEC-06, DEC-16, DEC-17)

### 5.1 Contract loading

Recommendation: compile `contracts/providers.json` into `chatui-contracts` with
`include_str!` and deserialize it with strict `serde` types. Load JSON Schemas
and fixtures at runtime from the repository `contracts/` directory for tests and
conformance. Do not copy provider presets into Rust source.

Strict export validation uses `jsonschema` plus strict `serde` deserialization
before applying an import. Catalog parsing stays tolerant so a provider catalog
change does not break the client.

Owner: Contracts owner. Unblocks: M3.5-02.2 and M3.5-02.3.

### 5.2 Unknown-field policy

Recommendation:

- **Catalog and provider metadata:** ignore unknown fields. Preserve raw
  metadata where the spec requires it, but do not fail on additive fields.
- **Export/import:** reject unknown fields through the shared schema and strict
  deserialization. Do not silently drop user data.

Owner: Contracts owner. Unblocks: M3.5-02.2 and M3.5-03.4.

### 5.3 `rememberKeysOnWeb` on desktop (DEC-16)

Recommendation: round-trip the field in settings and export/import for contract
compatibility. It does not control desktop secret storage. Desktop secret policy
is DEC-08: OS credential store, explicit encrypted fallback, or session-only
mode.

Owner: Contracts/domain owner. Unblocks: M3.5-02.1 and M3.5-02.2.

### 5.4 `browserCors` on desktop (DEC-17)

Recommendation: round-trip the field in provider metadata and export/import for
contract compatibility. It is informational only on desktop and must not change
transport, retry, or error behavior. Desktop transport follows the shared HTTP
client and cleartext policy in M3.5-05.1.

Owner: Contracts/domain owner. Unblocks: M3.5-02.1 and M3.5-02.2.

## 6. Networking decision (DEC-07)

Recommendation: implement a hand-written bounded SSE parser in
`chatui-providers` that matches spec section 7.6 and the shared stream fixtures.
It must handle CRLF normalization, multi-line `data`, comments, keep-alives, a
bounded buffer, and a final flush, and it must not parse JSON in the transport
layer. Do not use an opaque dependency whose behavior cannot be matched to the
shared vectors.

The NDJSON parser for Ollama follows the same bounded, fixture-driven approach
in M3.5-05.3.

Owner: Networking owner. Unblocks: M3.5-05.2.

## 7. Secrets decisions (DEC-08, DEC-13)

### 7.1 Keyring and fallback policy

Recommendation:

1. Use the OS credential store through `keyring`: Linux Secret Service
   (libsecret), macOS Keychain, and Windows Credential Manager.
2. If the store is unavailable, offer an explicit, documented encrypted-file
   fallback using AES-256-GCM or XChaCha20-Poly1305 with an Argon2id-derived key
   and a random salt.
3. Offer a session-only mode that holds keys in memory and clears them on exit.
4. Never store plaintext and never fall back silently.
5. Redact `Authorization`, `x-api-key`, `x-goog-api-key`, and custom secret
   headers in logs and panic messages; zeroize sensitive buffers.
6. Provide "Forget key" and "Forget all keys".

The Linux runtime Secret Service is available on this host, but the
`libsecret-1` development package is missing (B-06). The fallback path must be
buildable and testable without that package; the keyring path is proven on a
host or CI image that has it.

Owner: Secrets/security owner. Unblocks: M3.5-04.1, M3.5-04.2, and M3.5-04.3.

### 7.2 Desktop backup exclusion

Recommendation: exclude the database, attachment store, and secret stores from
cloud backup where the OS supports exclusion. Record the mechanism and its
limits per OS; do not claim exclusion where the platform has no supported
mechanism. This is a defense-in-depth measure, not a substitute for the
encrypted fallback.

Owner: Secrets/security owner with Desktop/UI owner. Unblocks: M3.5-04.3 and
M3.5-10.3.

## 8. Updater decision (DEC-09)

Recommendation:

- Host signed update manifests on GitHub Releases, or a dedicated HTTPS endpoint
  if the release owner provides one.
- Pin update public keys in the application; private keys live only in CI
  secrets and are never committed.
- Provide `stable` and `beta` channels.
- Verify the manifest signature before applying an update.
- Never auto-update during an active stream without asking the user.
- Fail the release job when signing material is absent rather than publishing an
  unsigned artifact.

Update-signing key ownership is `unknown` (B-05). The Release/security owner must
name the key owner and hosting location before M3.5-11.3 can complete.

Owner: Release/security owner. Unblocks: M3.5-11.3 and M3.5-11.4.

## 9. Math decision (DEC-10)

Recommendation: use a sanitized raw-source fallback for the first release. Do
not execute scripts and do not render untrusted HTML. A Rust typesetter may be
adopted later only if it is proven safe, renderable in the chosen UI framework,
and covered by tests. This matches the Android M2 deferral recorded in the
verification baseline.

Owner: UI owner. Unblocks: M3.5-09.4.

## 10. Desktop integration decisions (DEC-11, DEC-12)

### 10.1 Multi-window

Recommendation: single window for the first release. Multi-window is allowed
only if the chosen UI framework makes it low-risk and the Desktop/UI owner
accepts the additional state, deep-link, and accessibility testing. Do not let
multi-window expand the first-release scope.

Owner: Desktop/UI owner. Unblocks: M3.5-10.3.

### 10.2 Deep links and single instance

Recommendation: register `chatui://chat/<id>` per OS and forward links to one
running instance for both cold and warm starts. A second launch must not create
a duplicate instance that competes for the database or secret store.

Owner: Desktop/UI owner. Unblocks: M3.5-10.3.

## 11. Parity and M4 policy (DEC-14, DEC-15)

Recommendation:

- Keep the Rust column at `Required when enabled` and record no Rust
  implementation status while the enablement decision is `defer`.
- Do not change `contracts/parity.md` to claim Rust behavior before
  implementation evidence exists.
- If the owner later records `proceed`, every required Rust row must meet the
  same contracts, conformance, security, accessibility, packaging, and
  performance bar as web and Android before release.
- M4 does not depend on Rust while the decision is `defer`. If Rust is enabled
  and ships, M4 must include it.

Owner: Product/release owner. Unblocks: M3.5-12.2 and M4 planning.
