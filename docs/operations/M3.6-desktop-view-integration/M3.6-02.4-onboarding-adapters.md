- Parallel-safe: yes, with M3.6-02.3

- Read first: [M3.6 plan](PLAN.md) section 3; `rust/crates/chatui-ui/src/onboarding/service.rs`; `rust/crates/chatui-providers/src/openrouter/catalog.rs`; `rust/crates/chatui-providers/src/openrouter/key.rs`; `rust/crates/chatui-storage/src/repositories/settings.rs`

## Goal

Implement the production onboarding service adapters so first-run onboarding can
load the public OpenRouter catalog, validate a key, persist the provider and
models, and record onboarding completion.

## Preconditions

- `M3.6-02.1` and `M3.6-02.2` are complete.
- Tests must not call the network; inject fake catalog and validator sources.
- The key is passed only to the validator and the secret store.
- Do not log or render the key.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Production implementations of:
  - `onboarding::CatalogSource` backed by the OpenRouter catalog;
  - `onboarding::KeyValidator` backed by the provider validation functions;
  - `onboarding::ProviderStore`, `onboarding::ModelStore`, and
    `onboarding::SettingsStore` backed by SQLite.
- A constructor that wires `OnboardingService` over the adapters.
- Tests with fake catalog/validator plus a temporary database for persistence
  and completion.

## Implementation steps

1. Reuse the provider/model adapters from `M3.6-02.2` where the trait shapes
   match; otherwise add thin wrappers.
2. Implement the catalog source with the shared HTTP client and a bounded
   timeout.
3. Implement the key validator with the same mapping used by
   `providers::ProviderKeyValidator`.
4. Implement provider and model persistence with upsert semantics.
5. Implement settings completion persistence through `SqliteSettingsRepository`.
6. Add tests for catalog errors, validation errors, provider/model persistence,
   completion, and a skipped onboarding path.
7. Document network boundaries, timeouts, and error copy.

## Acceptance criteria

- [ ] Onboarding can load a catalog through the production source.
- [ ] Key validation returns non-secret metadata and never exposes the key.
- [ ] Provider and model records persist across reopen.
- [ ] Completion persists and reloads.
- [ ] Catalog and validation failures produce user-safe copy.
- [ ] Tests are offline and use temporary databases.
- [ ] No key material appears in logs or tests.
