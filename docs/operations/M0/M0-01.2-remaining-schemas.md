# M0-01.2 - Model, settings, export, and backup schemas

- Status: Not started
- Parent task: M0-01
- Order: 2
- Depends on: M0-01.1
- Parallel-safe: yes, with M0-01.4
- Owns: `contracts/schema/model-info.schema.json`, `contracts/schema/settings.schema.json`, `contracts/schema/chat-export.schema.json`, `contracts/schema/backup-manifest.schema.json`
- Read first: [M0 plan](../M0-foundations-implementation-plan.md) sections 3.1 and 4.2; spec sections 5.3, 6, 21.4, 21.5

## Goal

Create the remaining four contract schemas so fixtures, exports, settings, and future backup metadata have a stable shape.

## Preconditions

- `provider-preset.schema.json` exists and defines the shared conventions for `$schema`, `$id`, `title`, `contractVersion`, and `additionalProperties`.

## Deliverables

- `contracts/schema/model-info.schema.json`
  - Describes the normalized `Model` fields from spec section 6.
  - Uses a top-level `oneOf` or equivalent so raw provider catalog envelopes with a `data` array can be validated as fixtures while normalized model objects remain documented.
  - Preserves optional fields such as `canonicalSlug`, pricing, modalities, supported parameters, metadata, hidden, pinned, and source.
- `contracts/schema/settings.schema.json`
  - Matches spec section 6 `Settings` field names exactly.
  - Includes `BackupConfig` fields and defaults where the spec defines them.
  - Rejects unknown top-level fields for imported settings.
- `contracts/schema/chat-export.schema.json`
  - Matches spec section 21.4.
  - Requires `format: "chatui.export"`, `formatVersion`, `exportedAt`, `appVersion`, `conversations`, `messages`, `attachments`, `providers`, `models`, and `settings`.
  - Rejects unknown top-level formats and excludes secrets by design.
  - Defines attachment bytes as optional `dataBase64`.
- `contracts/schema/backup-manifest.schema.json`
  - Describes manifest metadata only, not encrypted bytes.
  - Includes `contractVersion`, object type/key, encryption algorithm, KDF, iterations, salt, and timestamp fields needed by spec section 21.5.
  - Uses `additionalProperties: false` at the top level.
- Every schema is Draft 2020-12 with a title and a `contractVersion`.

## Implementation steps

1. Read spec section 6, 21.4, and 21.5.
2. Write `model-info.schema.json` with a documented normalized shape and a raw catalog envelope variant.
3. Write `settings.schema.json`, including nested `ChatParams` and `BackupConfig` definitions.
4. Write `chat-export.schema.json` and `backup-manifest.schema.json`.
5. Run `jq empty` on each file.
6. Confirm no schema embeds secrets or provider-specific request payloads.

## Acceptance criteria

- [ ] All four schemas parse as JSON.
- [ ] Each declares Draft 2020-12, a title, and `contractVersion`.
- [ ] `chat-export` rejects an unknown top-level `format`.
- [ ] `settings` mirrors the spec section 6 field names.
- [ ] `model-info` validates both the documented normalized object and the raw catalog envelope used by fixtures.
- [ ] No schema requires a secret value.

## Verification

```bash
jq empty contracts/schema/model-info.schema.json
jq empty contracts/schema/settings.schema.json
jq empty contracts/schema/chat-export.schema.json
jq empty contracts/schema/backup-manifest.schema.json
jq -r '.$schema' contracts/schema/*.schema.json
```

Every `$schema` value must be `https://json-schema.org/draft/2020-12/schema`.

## Out of scope

- Fixture data, parity, validator, and package tooling.
- Import/export implementation in either client.
- Backup encryption implementation.
