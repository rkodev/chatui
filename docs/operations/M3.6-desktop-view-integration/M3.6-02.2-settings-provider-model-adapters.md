## Goal

Implement the synchronous UI service traits for settings, provider management,
and model management over the shared SQLite runtime and the provider crate.

## Preconditions

- `M3.6-02.1` is complete and exposes `ServiceRuntime`.
- Do not add a second runtime or database pool.
- Do not call real provider endpoints in tests.
- Do not store API keys outside the secret store.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Settings adapters:
  - `settings::SettingsStore` over `SqliteSettingsRepository`;
  - `settings::ProviderModelCatalog` over the provider and model repositories.
- Provider adapters:
  - `providers::ProviderStore`, `providers::ModelStore`,
    `providers::ConversationStore`, and `providers::SettingsStore`;
  - `providers::ProviderKeyValidator` that maps a provider kind to the matching
    `chatui-providers` validation function and returns non-secret
    `ProviderKeyInfo`.
- Model adapters:
  - `models::ModelRepository`, `models::ProviderRepository`,
    `models::SettingsStore`;
  - `models::ModelDiscovery` backed by the provider catalog/discovery layer.
- Tests using an in-memory or temporary database plus fakes for network
  validation and discovery.

## Implementation steps

1. Reuse `ServiceRuntime` to build the settings store and catalog.
2. Implement the provider management traits over the SQLite repositories.
3. Implement the key validator:
   - select the validator by `Provider.kind` or preset;
   - pass the key only to the validator;
   - map provider errors to `ChatError`;
   - never persist or log the key.
4. Implement the model management traits and default-provider/default-model
   settings.
5. Implement model discovery with injected transport, keeping tests offline.
6. Add tests for settings round-trip, provider CRUD, delete cascade, key
   presence without key disclosure, model listing, pin/hide, and default
   model selection.
7. Document the network boundary and any blocking behavior.

## Acceptance criteria

- [x] All listed UI traits have production implementations.
- [x] Settings persist and reload through SQLite.
- [x] Provider create, edit, enable, delete, and key metadata work.
- [x] Deleting a provider removes its models and does not delete unrelated data.
- [x] Key validation returns non-secret metadata and never exposes the key.
- [x] Model list, pin, hide, and default selection persist.
- [x] Model discovery is offline-testable.
- [x] Tests use temporary databases and fake network transports only.

## Completion record

- Status: Complete
- Commands and results:
  - `cd rust && cargo fmt --all --check` - passed.
  - `cd rust && cargo clippy -p chatui-desktop --all-targets -- -D warnings` -
    passed.
  - `cd rust && cargo nextest run -p chatui-desktop` - 86 tests passed, 0
    skipped.
- Decisions:
  - The adapters reuse `ServiceRuntime::bridge()` and the shared repositories;
    no second runtime or pool is created.
  - `settings::SettingsStore` and `settings::ProviderModelCatalog` are new
    wrappers with `new` and `from_runtime` constructors. The provider and model
    adapters follow the same pattern.
  - `ProviderKeyValidator` and `ProviderModelDiscovery` select the
    `chatui-providers` adapter from the provider preset, falling back to the
    provider kind (`custom`, `anthropic`, `google`) when the preset is unknown.
  - Both network adapters block on the shared runtime with a 30 second total
    timeout (`DEFAULT_NETWORK_TIMEOUT`). The shared HTTP client also has a 30
    second connect timeout and no total request timeout, so the adapter timeout
    is the bound for these synchronous calls.
  - `ProviderModelDiscovery` reads the stored key from the injected
    `SecretStore` only to build the request context. The key is never persisted
    or logged by the adapter.
  - `services/mod.rs` gained `pub mod models; pub mod providers; pub mod
    settings;` so the new adapters are part of the crate. This is the only
    change outside the three owned files and is required wiring.
  - Tests use temporary SQLite databases and `SessionStore` plus fake
    validator/discovery implementations. The production network adapters are
    exercised offline through the shared URL policy (public cleartext is
    rejected before any request).

## Handoff notes

- Concrete adapter types and constructors for `M3.6-06.1`:
  - `services::settings::SettingsStore::from_runtime(&runtime)` and
    `services::settings::ProviderModelCatalog::from_runtime(&runtime)`.
  - `services::providers::ProviderStore::from_runtime(&runtime)`,
    `ModelStore::from_runtime(&runtime)`,
    `ConversationStore::from_runtime(&runtime)`, and
    `SettingsStore::from_runtime(&runtime)`.
  - `services::providers::ProviderKeyValidator::from_runtime(&runtime)` returns
    `Result<Self, ChatError>`; it needs an `Arc<dyn SecretStore>` only through
    the service, not directly.
  - `services::models::ModelRepository::from_runtime(&runtime)`,
    `ProviderRepository::from_runtime(&runtime)`, and
    `SettingsStore::from_runtime(&runtime)`.
  - `services::models::ProviderModelDiscovery::from_runtime(&runtime, secrets)`
    returns `Result<Self, ChatError>` and requires the selected
    `Arc<dyn SecretStore>`.
- Network-blocking trait methods:
  - `providers::ProviderKeyValidator::validate_key` blocks on the shared
    runtime for at most `DEFAULT_NETWORK_TIMEOUT` (30 seconds).
  - `models::ModelDiscovery::discover` blocks on the shared runtime for at most
    `DEFAULT_NETWORK_TIMEOUT` (30 seconds).
  - Neither method may be called on the Slint thread. `M3.6-06.1` must run them
    on a worker task and marshal results back with `upgrade_in_event_loop`.
- The secret store is selected separately by `M3.6-02.1`'s
  `default_secret_store` / `session_only_secret_store`; pass the selected
  `Arc<dyn SecretStore>` to `ProviderModelDiscovery` and to
  `ProviderManagementService`.
