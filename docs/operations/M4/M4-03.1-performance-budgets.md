# M4-03.1 - Performance optimization and budget measurement

- Milestone: M4
- Status: Not started
- Order: 4
- Depends on: M4-01.1, M4-02.1
- Parallel-safe: yes, with `M4-04.1`
- Owns: web build/code-splitting config and message-rendering performance under `web/`; Android startup/list/image performance under `android/`; Rust startup/size work under `rust/` only if shipping; `docs/operations/M4/M4-performance.md`; `docs/operations/M4/evidence/performance/`
- Read first: [M4 milestone](../../milestones/M4-polish-and-release.md) workstream 3; spec sections 8.8, 9.11, 10.9, 11.6, and 11.11; `M4-baseline.md` from `M4-00.1`

## Goal

Optimize the enabled clients to the phase 1 budgets and record actual measurements, hardware, and methodology. Document deviations with a follow-up plan and owner instead of hiding them.

## Preconditions

- `M4-01.1` and `M4-02.1` are `Complete` so measurements reflect the polished, PWA-enabled build.
- Do not change product behavior to hit a number.
- Rust work is required only if `M4-00.1` says `shipping`.

## Deliverables

- Web:
  - Code-split settings, provider management, and Shiki languages.
  - Lazy-load Markdown below the fold where practical.
  - Confirm message virtualization and memoized message components.
  - Keep the streaming message isolated from the rest of the list.
  - Reserve image aspect ratios.
  - Measurements against: initial JS under 250 KB gzip, Lighthouse mobile performance and accessibility at least 90, and a 10,000-message conversation scrolling at 60 fps on a mid-tier device.
- Android:
  - Cold-start measurement; stable `LazyColumn` keys/content type; no history recomposition during streaming; image decode sizing; Coil thumbnail cache; baseline profile.
  - Targets: debug APK under 20 MB, release APK under 15 MB if feasible, and a recorded cold-start budget.
- Rust (only if shipping):
  - Cold start under 1.5 s on mid-tier desktop and installer under 40 MB.
- `M4-performance.md` with a per-client table: metric, target, measured value, hardware, method, pass/fail, deviation/follow-up owner.
- Evidence: Lighthouse JSON/HTML, bundle analyzer output, Android macrobenchmark/logcat output, and Rust timing/size output.

## Implementation steps

1. Re-read `M4-baseline.md` and confirm the measurement commands and target device(s).
2. Web bundle:
   - Run the production build and analyze the bundle (for example `vite build` plus a bundle visualizer or the existing analyzer).
   - Code-split settings, providers, and Shiki language chunks; verify the initial route does not import them.
   - Lazy-load below-the-fold Markdown only where it does not break streaming.
   - Re-measure initial JS gzip. Budget: under 250 KB gzip.
3. Web runtime:
   - Confirm virtualization for long conversations and memoization of message components.
   - Ensure token streaming updates only the streaming message subtree.
   - Reserve image aspect ratios to avoid layout shift.
   - Measure a 10,000-message conversation scroll on the recorded mid-tier device/browser; target 60 fps. Record frame drops and method.
4. Web Lighthouse:
   - Run mobile Lighthouse on the main chat route against the production build (or the container from `M4-04.1` if available).
   - Record performance and accessibility scores. Target at least 90 each.
5. Android:
   - Measure cold start with the project's baseline-profile/macrobenchmark setup or a documented `am start -W` method; record device and method.
   - Verify `LazyColumn` keys/content types are stable and history does not recompose during streaming.
   - Verify image decode sizing and Coil thumbnail cache.
   - Ensure the baseline profile exists and is used in the release build.
   - Measure debug and release artifact sizes. Targets: debug APK under 20 MB; release APK under 15 MB if feasible.
6. Rust (only if shipping):
   - Measure cold start on the recorded mid-tier desktop; target under 1.5 s.
   - Measure installer/binary size; target installer under 40 MB.
7. For every miss, record the measured value, likely cause, follow-up task owner, and whether it is an accepted deviation. Do not mark a budget met with an unmeasured claim.
8. Write `M4-performance.md` and save raw evidence.

## Acceptance criteria

- [ ] Web initial JS is under 250 KB gzip, or a deviation with owner/plan is recorded.
- [ ] Lighthouse mobile performance and accessibility are at least 90, or deviations are recorded.
- [ ] A 10,000-message web conversation scrolls at 60 fps on the recorded mid-tier device, or a deviation is recorded.
- [ ] Web settings, provider management, and Shiki languages are code-split; Markdown is lazy-loaded where practical.
- [ ] Web virtualization, memoization, isolated streaming, and image aspect ratios are verified.
- [ ] Android cold start is measured; `LazyColumn` keys/content type, streaming recomposition, image decode sizing, Coil cache, and baseline profile are verified.
- [ ] Android debug APK under 20 MB and release APK under 15 MB if feasible, or deviations recorded.
- [ ] Rust cold start under 1.5 s and installer under 40 MB if shipping, or deviations recorded.
- [ ] Measurements include hardware and methodology; `M4-performance.md` exists.

## Out of scope

- New features, provider protocols, or visual redesign.
- Deployment container/headers (M4-04.1) and CI workflows (M4-05.1).
- Changing budgets; if a budget is infeasible, record a deviation with owner and plan.
- M5/M6 performance work.
