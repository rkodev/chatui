# M2-05.2 - Android preset enablement and Custom providers

- Status: Complete
- Parent task: M2-05
- Order: 21
- Depends on: M2-05.1
- Parallel-safe: yes, with M2-01.2
- Owns: `android/core/network/ProviderRegistry.kt`, `android/core/providers/`, `android/feature/providers/`, provider config/tests

## Goal

Enable the launch OpenAI-compatible presets and Custom provider creation on Android without bypassing contract validation.

## Preconditions

- M2-05.1 generic transport works.
- Contracts already contain every preset.

## Deliverables

- M2 preset enablement replacing the M1 OpenRouter-only gate.
- Custom provider creation with base URL, auth type, and non-secret headers.
- Validation and rollback behavior for provider creation.
- Secret storage remains separate from provider records.
- Provider tests for valid/invalid Custom providers and preset availability.

## Implementation steps

1. Read the M1 gating in `ProviderRegistry.kt` and provider services.
2. Replace the M1 enablement set with M2 enablement.
3. Add Custom provider creation through `ProviderService`/management facade.
4. Validate URL, auth shape, and non-secret headers.
5. Ensure provider persistence and secret writes roll back together.
6. Add tests for valid/invalid Custom providers.
7. Run Android gates.

## Acceptance criteria

- [x] All launch OpenAI-compatible presets can be enabled from contracts.
- [x] Custom providers require base URL and auth style.
- [x] Non-secret headers are stored separately from keys.
- [x] Invalid Custom input is rejected with actionable copy.
- [x] Failed provider writes do not leave orphan secrets.
- [x] OpenRouter remains default/reference/required.
- [x] Android gates pass.

## Handoff notes

- M2 enabled preset list: `openrouter`, `openai`, `groq`, `mistral`, `deepseek`,
  `xai`, `together`, `fireworks`, `lmstudio`, `llamacpp`, `custom`. Anthropic,
  Google Gemini, and Ollama remain in contracts but are `coming-later` until
  M2-06 adds their native adapters. Ollama is intentionally excluded here even
  though its contract kind is `openai-compatible`, because its native discovery
  and chat adapter belong to M2-06.3.
- Custom provider fields: `label` (optional), `baseUrl` (required http(s) URL
  without credentials, query, or fragment), `authType` (`bearer`, `x-api-key`,
  or `none`; `query-key` is rejected), optional `apiKey`, and optional
  non-secret `headers`. The provider record stores `presetId: "custom"`, the
  base URL, auth type, headers, and `secretId`; it never stores the key.
- Rollback behavior: the secret is written first. A failed secret write leaves
  no provider record. A failed provider write deletes the newly written secret
  and surfaces `ProviderServiceErrorCode.STORAGE`. Invalid input is rejected
  before any write.
- Validation: base URL scheme/host/credentials/query/fragment, auth style,
  key presence/absence, duplicate labels (case-insensitive), header name
  syntax, forbidden authentication headers, blank values, and line breaks.
- UI: `ProviderListScreen` now shows the M2 availability list and a Custom
  provider form wired through `ProviderListViewModel`. Full provider UI and
  shell wiring remain for M2-05.4.
- Scope note: `ProviderServiceErrorCode.STORAGE` required a small exhaustive
  `when` update in `OnboardingErrorCopy.kt`, and the onboarding provider-option
  test now reflects M2 availability. Onboarding `connect()` still creates
  OpenRouter only; preset selection in onboarding is left for M2-05.4.
