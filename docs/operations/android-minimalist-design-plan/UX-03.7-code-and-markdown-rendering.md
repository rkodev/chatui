# UX-03.7 - App-themed code and rendering reuse

- Phase: UX-03 - Chat readability and resources
- Status: Not started
- Order: 19
- Depends on: UX-03.1
- Output folder: `docs\operations\android-minimalist-design-plan`
- Parallel-safe: No with code/Markdown rendering edits; coordinate UX-03.5.

## Goal

Make code colors follow the resolved application theme and avoid redundant
expensive rendering without changing supported Markdown or exact content.

## Read first

Read the [execution contract](README.md), source-plan sections 5.1 and
7, UX-01.4's theme contract, UX-00.3's rendering baseline,
`Chat\ChatCodeBlock.kt`, `Chat\ChatMarkdown.kt`, existing highlight/parser
helpers, and `ChatCodeBlockTest.kt`/`ChatMarkdownTest.kt`.

## Owns

Code-theme resolution and tightly scoped rendering reuse in the two named
files/existing rendering helpers, plus their focused regressions.

## Deliverables

Correct explicit-app-theme code rendering and bounded reuse of unchanged
parsed/highlighted results where redundant work is demonstrated.

## Implementation steps

1. Replace code rendering's system-only dark-mode lookup with the resolved
   app-theme contract. Test both directions of app/system theme disagreement.
2. Keep language labels, exact-text copy, code selection, wrap/horizontal
   scrolling, readable monospace size, and contrast in both themes.
3. Identify repeated parse/highlight work on unchanged content using the
   baseline and existing renderer boundaries. Reuse results keyed by actual
   content/language/resolved theme as needed; avoid an unbounded global cache.
4. If profiling shows long live-code highlighting blocks the UI, move only
   that computation off the UI thread, preserving visible raw text while
   pending and rejecting stale results after content/theme changes.
5. Preserve safe Markdown/GFM, links/tables/reasoning, raw-source math fallback,
   all message text, and streaming final/error/cancel flush behavior.
   Do not introduce a new renderer or skip code to improve timing.
6. Add focused cases for theme mismatch/change, unchanged-result reuse,
   stale asynchronous results if introduced, long code copy/wrap/selection,
   and retained Markdown safety/content behavior.

## Acceptance criteria

- [ ] Code follows applied app theme even when system theme differs.
- [ ] Exact code content and all existing rendering controls remain.
- [ ] Reuse is bounded/correctly keyed; any background work cannot show stale output.
- [ ] Performance changes have evidence and do not alter protocol/persistence.
