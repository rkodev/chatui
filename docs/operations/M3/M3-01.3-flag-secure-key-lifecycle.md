# M3-01.3 - FLAG_SECURE, key lifecycle, and logging audit

- Milestone: M3
- Status: Complete
- Order: 7
- Depends on: M3-01.1
- Parallel-safe: yes, with M3-01.2 and M3-01.4
- Owns: `android/core/designsystem/`, `android/feature/onboarding/`, `android/feature/providers/`, security tests and source audit notes
- Read first: [M3 plan](../M3-android-depth-implementation-plan.md) sections 3.1 and 4.2; spec sections 9.7 and 12.3

## Goal

Prevent secret-entry and provider-key screens from leaking through recents/screenshots, and prove key rotation/forget paths and redacted logging.

## Preconditions

- M3-01.1 is complete.
- Do not add biometrics; that is explicitly deferred.
- Do not reveal a stored key in any new UI.

## Deliverables

- A reusable `SecureScreen` composable that adds and removes `WindowManager.LayoutParams.FLAG_SECURE`.
- `SecureScreen` applied to onboarding key entry and provider key detail/rotation.
- A Robolectric or instrumentation check that the window flag is present on those screens.
- Tests confirming provider key rotation, remove key, forget key, and forget all remain correct.
- A logging audit record confirming no raw secret headers or key values are logged.

## Implementation steps

1. Read `OnboardingScreen.kt`, `OnboardingRoute.kt`, `ProviderDetailScreen.kt`, `ProviderDetailViewModel.kt`, `ProviderService.kt`, `SecretStore.kt`, and `Redaction.kt`.
2. Add a `SecureScreen` composable in `android/core/designsystem/`:
   - obtain the current `Activity`/`Window` from `LocalView`;
   - in `DisposableEffect`, add `FLAG_SECURE`;
   - remove the flag on dispose only if this composable added it.
3. Wrap the onboarding key-entry step or route and the provider detail/key-rotation screen with `SecureScreen`. Keep the welcome/onboarding catalog screen usable.
4. Add a test that resolves the hosting window and asserts `FLAG_SECURE` is set when the secure screen is composed. Use Robolectric if reliable; otherwise add an instrumentation assertion.
5. Verify the existing key lifecycle tests cover:
   - provider key rotation (`ProviderService.rotateKey`);
   - remove key (`ProviderService.removeKey`);
   - `SecretStore.forgetKey`;
   - `SecretStore.forgetAll`.
   Add any missing assertions without changing storage behavior.
6. Audit `Log.*`, exception construction, request/response dumps, and any debug interceptor. Record that no logging interceptor is installed and no raw secret header is logged.
7. Record the result in `M3-verification.md` under the security section.

## Acceptance criteria

- [x] `SecureScreen` adds and removes `FLAG_SECURE` correctly.

## Out of scope

- Backup proof (M3-01.2).
- Network security config (M3-01.4/M3-01.5).

- Changing the secret cipher format.

## Handoff notes

- Added `SecureScreen` in `android/core/designsystem/` and applied it to the
  onboarding `KEY_ENTRY` step and the whole provider detail surface. The
  welcome/provider-picker step is intentionally left unsecured.
- `SecureScreen` only clears `FLAG_SECURE` when it added the flag, so a host
  that already set the flag keeps it.
- Window-flag coverage is Robolectric: `SecureScreenTest` (2 tests),
  `OnboardingScreenTest` (2 new tests), and `ProviderDetailScreenTest` (1 new
  test). No instrumentation-only assertion was needed.
- Key lifecycle paths were already covered by `ProviderServiceTest` and
  `SecretStoreTest`; no storage behavior changed.
- Logging audit is recorded in `M3-verification.md` section 11.4. The only
  production log is the content-free startup-recovery warning in
  `MainActivity`; no logging interceptor is installed.
- No biometric gate was added. No stored key is rendered; key inputs use
  `PasswordVisualTransformation`.
- Verification: `make android-test` passed with 786 tests, 0 failures;
  `:app:connectedDebugAndroidTest` passed with 7 tests, 0 failures, 2 skipped
  (manual restart/backup phases).
