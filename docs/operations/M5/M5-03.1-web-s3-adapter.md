- Milestone: M5
- Status: Complete

- Depends on: M5-02.1
- Parallel-safe: yes, with `M5-03.2` and `M5-03.3`

## Goal

Implement the first storage backend on web: S3-compatible object storage with
SigV4, conditional writes, a connectivity test, and documented bucket CORS. The
adapter must only ever receive encrypted bytes.

## Preconditions

- `M5-02.1` is `Complete` and the manifest/payload code exists.
- Do not add a cloud SDK. Implement SigV4 with WebCrypto.
- Do not add a server proxy.

## Deliverables

- `web/src/features/backup/storage/types.ts`:
  - `StorageAdapter` interface: `testConnection`, `getObject`, `putObject`,
    `headObject`, `deleteObject`, `listObjects`.
  - `StorageObject { key, bytes, etag?, lastModified? }`.
  - `StorageError` with typed codes (`auth`, `permission`, `not_found`,
    `conflict`, `network`, `server`).
- `web/src/features/backup/storage/sigv4.ts`:
  - Canonical request, string to sign, signing key, and `Authorization` header.
  - Support `GET`, `PUT`, `HEAD`, `DELETE`.
  - Support custom endpoints for AWS, Contabo, Cloudflare R2, MinIO, and
    Backblaze B2.
- `web/src/features/backup/storage/s3.ts`:
  - `S3StorageAdapter` implementing the interface.
  - Path-style and virtual-hosted-style URLs.
  - `If-Match`/`If-None-Match` conditional writes where supported.
  - ETag capture and return.
  - Conservative handling of eventual consistency: re-read after write when
    needed.
- `docs/operations/M5/web-s3-cors.md`:
  - Required CORS methods, headers, exposed headers (`ETag`), and example
    bucket policy.
  - Notes for each target provider.
- Tests:
  - SigV4 known-answer test from AWS documentation or a fixed vector.
  - Adapter tests with a mocked `fetch` for GET/PUT/HEAD/DELETE.
  - Conditional write conflict returns `conflict`.
  - Connectivity test returns typed errors.
  - No plaintext is passed to the adapter in tests.

## Implementation steps

1. Read the envelope codec and the manifest/payload code.
2. Define the `StorageAdapter` interface and error types.
3. Implement SigV4:
   - Hash the payload with SHA-256.
   - Build the canonical request with sorted headers and query.
   - Derive the signing key with HMAC-SHA256.
   - Build the `Authorization` header.
4. Implement `S3StorageAdapter`:
   - Build the object URL from endpoint, bucket, and key.
   - Sign every request.
   - Send `If-Match` on manifest rewrite and `If-None-Match: *` on create.
   - Parse `ETag` and map HTTP status to typed errors.
5. Implement `testConnection` with a `HEAD` on the bucket or a small probe
   object. Do not write plaintext.
6. Write the CORS documentation with a concrete example.
7. Add tests with a mocked `fetch`. Use synthetic encrypted bytes only.
8. Run the web gates.

## Handoff notes

- Implemented `StorageAdapter`, `StorageError`, SigV4, and `S3StorageAdapter`
  under `web/src/features/backup/storage/`.
- SigV4 uses WebCrypto only. No cloud SDK and no server proxy were added.
- Known-answer tests cover the AWS documentation GET and PUT object vectors.
- Conditional writes send `If-Match` or `If-None-Match`; HTTP `409`/`412` map
  to `StorageError` code `conflict`.
- ETags are returned raw, including quotes, so callers can pass them back as
  `If-Match`. If a `PUT` response omits `ETag`, the adapter re-reads with
  `HEAD` (up to three attempts) before returning.
- Path-style URLs are the default for non-AWS endpoints; AWS endpoints default
  to virtual-hosted-style. `forcePathStyle` overrides either default.
- `testConnection` performs `HEAD` on the bucket and writes nothing.
- `putObject` accepts only `Uint8Array`; tests use synthetic envelope-shaped
  ciphertext and never pass plaintext.
- CORS and provider notes are in `docs/operations/M5/web-s3-cors.md`.
