- Milestone: M6
- Status: Not started
- Order: 17
- Depends on: M6-05.2
- Parallel-safe: no
- Owns: `docs/operations/M6/evidence/config-review.md`, `docs/operations/M6/evidence/rollback-drill.md`
- Read first: [M6 plan](../M6-managed-hosting-implementation-plan.md) sections 3.1 (T-07), 3.5 (D-09), 3.6 (V-03, V-08), 7, and 9; `scripts/validate-tenant-config.mjs`; `docs/hosting/rollback.md`; `docs/operations/M6/evidence/staging/`

## Goal

Review the deployed tenant configuration for secrets and contract violations, and
exercise the rollback runbook against the staging tenant. Record both as evidence
without storing secrets or real user data.

## Preconditions

- `M6-05.2` is `Complete` and the staging tenant is live.
- The rollback runbook and previous release/config are available.
- Use synthetic data and disposable credentials only.
- If the operator cannot provide a previous release or rollback access, mark this
  task `Blocked`.

## Deliverables

- `docs/operations/M6/evidence/config-review.md`:
  - Date, tenant URL, commit, release version, artifact digest, and config hash.
  - The public `config.json` content or a function-free excerpt. It is public by
    design, but still verify it contains no secrets.
  - Validator command and output:
    `node scripts/validate-tenant-config.mjs <deployed-config.json> --origin <tenant-origin>`.
  - Checks: schema shape, exact OpenRouter attribution origin, `telemetry:
    false`, no unknown fields, no forbidden key names, no secret-shaped values,
    and preset validity.
  - Result: pass/fail and every issue found.
  - Confirmation that the deployed config hash matches the tenant manifest.
  - Evidence that the deployed build serves this config with `no-cache`.
- `docs/operations/M6/evidence/rollback-drill.md`:
  - Date, tenant URL, operator, previous and current release versions and
    artifact digests, and previous/current config hashes.
  - Trigger used for the drill and the approval to execute it.
  - Steps performed from `docs/hosting/rollback.md`, with any deviation.
  - Verification before and after rollback:
    - `scripts/verify-hosted-deployment.mjs` output for the tenant and custom
      domain.
    - `/`, `/config.json`, `/healthz`, one asset, and a deep route.
    - TLS and custom-domain behavior.
    - Config hash matches the rolled-back manifest.
  - Confirmation that browser data, provider keys, storage credentials, and
    backup objects were not restored or deleted by roksky.
  - Result: pass/fail, duration, and any follow-up.
  - Re-deploy the current release after the drill if the drill rolled staging
    back, or record the final state.
- Update `docs/operations/M6/evidence/README.md` with links to both records.

## Implementation steps

1. Download the deployed public config and compute its hash.
2. Run the tenant config validator with the exact origin.
3. Scan the config for secret patterns and forbidden keys.
4. Compare the config hash and artifact digest to the tenant manifest.
5. Confirm the config is served with `Cache-Control: no-cache`.
6. Record the current release/config, then execute the rollback runbook.
7. Run the hosted verification script before and after the rollback.
8. Confirm no server-side user data was involved.
9. Restore the staging tenant to the intended current release if needed.
10. Write both evidence records and link them from the index.

## Acceptance criteria

- [ ] The config review is recorded and passes, or every issue is a blocker.
- [ ] The exact origin, `telemetry: false`, no-secret, and unknown-field checks
      are recorded.
- [ ] The deployed config hash matches the tenant manifest.
- [ ] The rollback drill is recorded with before/after verification.
- [ ] The rollback restores a working tenant and headers/health/SPA checks pass.
- [ ] The evidence states that no roksky-side user data was rolled back.
- [ ] Evidence contains only synthetic data and no secrets or personal data.
- [ ] The evidence index is updated.

## Verification

```bash
node scripts/validate-tenant-config.mjs <deployed-config.json> --origin <tenant-origin>
node scripts/verify-hosted-deployment.mjs <tenant-url> --origin <tenant-origin>
node scripts/verify-hosted-deployment.mjs <custom-domain-url> --origin <custom-domain-origin>
```

Plus the recorded rollback steps and before/after output.

## Out of scope

- Fixing config or deployment defects. Create a follow-up task and block the
  exit gate.
- Final security review (`M6-06.1`).
- Self-host/export portability (`M6-06.2`).
- Changing the rollback runbook without updating `M6-02.4`.
