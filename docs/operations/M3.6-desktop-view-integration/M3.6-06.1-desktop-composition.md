## Goal

Compose the real services, controllers, and feature views into
`chatui-desktop`: onboarding gate, lazy controller creation, destination
navigation, menus, shortcuts, deep links, window state, settings application,
and the Models overlay.

## Preconditions

- Every dependency task is complete and its handoff notes list the constructors
  and public methods to call.
- Do not duplicate business logic already owned by controllers.
- Do not add a second runtime, pool, or secret backend.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Desktop startup:
  - open the database through `ServiceRuntime`;
  - read `Settings::onboarding_completed`;
  - show onboarding when incomplete and the shell when complete;
  - persist completion and switch to the shell after a successful connect or
    skip.
- Shell composition:
  - build the settings, providers, models, data, history, chat, and onboarding
    controllers;
  - install their window handles into the shell factory properties;
  - lazily create a controller on first navigation and sync it on every visit.
- Navigation and actions:
  - sidebar navigation syncs the active controller;
  - New Chat, Search, Attach File, Export, Import, Copy Last Response, Stop,
    Previous/Next Conversation, Documentation, and About call real controllers;
  - settings changes apply to the shell, composer, and message list;
  - the Models overlay opens from Settings and closes back to the previous
    destination;
  - deep links open the target conversation when onboarding is complete and
    show the safe not-found state otherwise.
- Error handling:
  - database or secret-backend failures show a user-safe startup error instead
    of panicking;
  - no placeholder copy remains in the normal navigation flow.
- A manual smoke that visits every destination.

## Implementation steps

1. Read every dependency handoff note and list the constructors to call.
2. Replace the `--onboarding-incomplete` flag path with the persisted setting.
3. Build `ServiceRuntime` and the adapters, then the controllers.
4. Install factory properties on `ShellWindow` using the embedding pattern from
   `M3.6-01.1` and the property names from `M3.6-03.1`.
5. Add a lazy `ensure_controller(destination)` helper and call `sync()` on
   navigation.
6. Route menu and shortcut commands to the controllers; remove notice-only
   placeholders for implemented actions.
7. Apply settings to shell/composer/message-list after each settings change.
8. Wire onboarding completion, skip, and failure paths.
9. Wire deep links and the Models overlay.
10. Keep window-state, single-instance, theme polling, and clipboard behavior.
11. Run the smoke on Linux and record results and blockers.

## Out of scope

- New views or adapters.
- Packaging and release changes.
- New menus or shortcuts beyond the existing map.
- Multi-window support.

## Blockers

- **Live message-list settings.** `SettingsController::apply_to_message_list`
  needs a `MessageListState`, but `ChatController` owns its message list
  privately and exposes only `messages_window()`. There is no public
  `set_show_token_usage` or `message_list()` accessor on `ChatController`
  (`rust/crates/chatui-ui/src/chat/view.rs`). Applying the live token-usage
  toggle therefore requires a small `chatui-ui` change outside this task's
  owned paths. The shell theme/density/font and the composer send-key hint do
  apply live; the message list is created with the default token-usage value.
  Decision needed: either widen `M3.6-06.1` to own
  `rust/crates/chatui-ui/src/chat/view.rs` and add a pass-through
  `set_show_token_usage` method, or create a follow-up task for that change.

## Completion record

- Status: Blocked (one acceptance criterion; implementation and verification
  otherwise complete)
- Commands and results:
  - `cd rust && cargo fmt --all --check` - passed.
  - `cd rust && cargo clippy -p chatui-desktop --all-targets -- -D warnings` -
    passed.
  - `cd rust && cargo nextest run -p chatui-desktop` - 112 passed, 0 skipped.
  - `cd rust && cargo run -p chatui-desktop -- --smoke --no-single-instance` -
    passed; printed `smoke: chat`, `history`, `providers`, `settings`, `data`,
    `models overlay`, `close models`, `done`.
- Smoke environment: Linux, Wayland session (`XDG_SESSION_TYPE=wayland`,
  `DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`), Slint 1.18.1 winit backend. The
  smoke uses a temporary profile and the session-only secret store so it does
  not touch the real database or OS keyring.
- Decisions:
  - `ServiceRuntime::open()` is the production entry point; `--smoke` uses
    `ServiceRuntime::open_at` with a temporary profile and seeds
    `onboarding_completed = true`.
  - The onboarding gate reads `Settings::onboarding_completed`. A successful
    connect persists completion through `OnboardingService`; a successful skip
    is persisted by the desktop after the onboarding window closes.
  - `default_secret_store()` is used in normal mode. `FallbackRequired` is
    surfaced as a user-safe startup error because this task does not add a
    fallback-choice prompt. `--smoke` uses `session_only_secret_store()`.
  - Controllers are created lazily by `ensure_controller` and reused; the
    shell factories return the controller's own handle.
  - `RuntimeSpawner` implements `ChatRuntime` and `HistoryRuntime` over the
    shared `ServiceRuntime` bridge; it does not create a second runtime.
  - Menu Export/Import call `SqliteDataService` directly and write/read through
    the native dialogs. New Chat uses the History controller's new-chat action.
    Previous/Next Conversation uses a bounded conversation query. Copy Last
    Response reads the newest page and uses the existing clipboard helper.
  - Documentation and About navigate to Settings -> About instead of showing a
    notice-only placeholder.
  - The onboarding controller's catalog load and connect remain synchronous on
    the Slint thread because `OnboardingController::new` and its callbacks are
    synchronous. The adapters keep the 30 second network timeout. This is a
    known limitation of the current onboarding controller API.

## Handoff notes

- Controllers and factory properties installed by `M3.6-06.1`:
  - `ChatController` -> `chat-messages-factory` (`MessageListWindow`) and
    `chat-composer-factory` (`ComposerWindow`).
  - `HistoryController` -> `history-factory` (`HistoryWindow`).
  - `ProviderManagementController` -> `providers-factory`
    (`ProviderManagementWindow`).
  - `SettingsController` -> `settings-factory` (`SettingsWindow`).
  - `DataController` -> `data-factory` (`DataWindow`).
  - `ModelManagementController` -> `models-factory`
    (`ModelManagementWindow`), opened by `show-models`.
- Startup sequence for `M3.6-07.1`:
  1. Parse args and acquire the single-instance guard.
  2. Load window state and probe the system theme.
  3. `DesktopServices::open` opens `ServiceRuntime`, selects the secret store,
     and loads settings.
  4. If `onboarding_completed` is false, run `OnboardingController`; persist
     completion on connect or skip.
  5. Create `ShellController`, install shortcut lines, and create
     `DesktopComposition`.
  6. Create and sync the Chat controller, then wire menu, drop, close,
     navigation, single-instance, theme, poll, and draft-flush timers.
  7. Route any cold-start deep link through `handle_deep_link`.
- `poll_controllers` runs every 50 ms and calls `ChatController::poll` and
  `HistoryController::poll`; `poll_settings` applies shell appearance and the
  composer send-key hint when the settings view model changes.
- `flush_drafts` runs every 2 seconds and flushes the shared
  `PersistentDraftStore`.
- Placeholder copy: the primary destination placeholders are gone. The
  Data/Settings backup sections still show the existing M5 "backup is not
  available in this release" copy; that is a feature-availability notice, not a
  destination placeholder, and is out of scope for this task.
- Known limitation: the live message-list token-usage toggle is blocked by the
  missing `ChatController` accessor described in `## Blockers`.
- Onboarding network calls remain synchronous on the Slint thread because the
  controller API is synchronous; the adapters keep the 30 second timeout.
