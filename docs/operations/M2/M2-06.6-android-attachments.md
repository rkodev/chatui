## Goal

Deliver the complete Android attachment flow from picker to provider content parts, including local storage, downscale, EXIF stripping, cleanup, and capability warnings.

## Preconditions

- Attachment entity/DAO exist.
- Provider adapters support shared content parts or capability helpers.

## Deliverables

- Photo picker, SAF document picker, clipboard image paste, and drag-and-drop.
- Type/size validation.
- Downscale to 2048 px longest edge, EXIF stripping except orientation, and content-addressed storage under `filesDir/attachments/<sha256>`.
- Transactional metadata persistence.
- Composer chips/thumbnails, removal, and message rendering.
- Provider-specific content parts: OpenAI data URLs, Anthropic base64 blocks, Gemini inline data, and text-file headers.
- Capability warnings and model-switch confirmation.
- Orphan cleanup after delete/edit/startup.
- Tests for input, processing, persistence, reload, and request serialization.

## Implementation steps

1. Read the attachment DAO/entity, chat request builder, and composer.
2. Add an attachment service for validation, hashing, processing, and storage.
3. Add pickers, clipboard paste, and drag-and-drop.
4. Add image downscale and EXIF stripping.
5. Persist metadata transactionally and render chips/messages.
6. Extend request construction with provider content parts.
7. Add capability warnings and cleanup.
8. Add tests.
9. Run Android gates.

## Handoff notes

- Size/type limits: images 20 MB (PNG/JPEG/WebP/GIF), text files 2 MB (text/*, JSON, XML, JavaScript, and the shared source-extension list). Names are sanitized and capped at 255 characters.
- Storage and cleanup behavior: bytes are written atomically to `filesDir/attachments/<sha256>` before metadata; metadata batches commit in one Room transaction. Draft rows are bound to the user message after it persists. Startup cleanup removes unbound rows created before the cleanup started and any unreferenced bytes; edit-and-resend removes attachments for the edited message and every truncated later message.
- Provider content-part mapping: `ChatRequestBuilder` preserves image/file parts and resolves bytes through `AttachmentService`. OpenAI-compatible adapters emit data URLs, Anthropic emits base64 image blocks and text-file headers, Gemini emits `inlineData` and text-file headers, and Ollama emits base64 `images` plus text-file headers. Existing request-vector tests cover the adapters; `ChatRequestBuilderTest` covers the new part plumbing.
- Image processing: `AndroidImageProcessor` decodes with `BitmapFactory`, applies EXIF orientation to pixels, scales the longest edge to 2048 px, and re-encodes to JPEG/WebP, which drops all EXIF tags. Undecodable input falls back to the original bytes.
- Inputs: Compose photo picker (`PickVisualMedia`), SAF `OpenMultipleDocuments`, clipboard image URIs, and Compose drag-and-drop all feed the same `AttachmentInput` path.
- Capability warnings: `attachmentSupport` compares pending attachments with the model's input modalities. The composer shows a warning, send opens a confirmation dialog, and the chat observes conversation changes so a model switch updates the warning immediately. The conversation settings sheet itself remains owned by M2-06.5.
- Verification: `make android-lint`, `make android-test`, and `make android-assemble` all pass. Manual picker, clipboard, drag, and reload checks were not possible in this headless environment; the equivalent paths are covered by unit/Compose tests and the shared URI reader.
- Tests added: `AttachmentRulesTest`, `AttachmentServiceTest`, `AndroidImageProcessorTest`, `AttachmentSupportTest`, plus composer, message-item, screen, request-builder, and ViewModel attachment cases.
