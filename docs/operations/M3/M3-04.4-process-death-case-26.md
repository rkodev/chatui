## Goal

Prove that killing the process during streaming preserves partial content, marks the message interrupted, and allows regeneration.

## Preconditions

- M3-04.3 is complete.
- Existing recovery code (`ChatRunner`, `StreamingRecoveryService`, `AppStartup`, `InterruptedMessageNotice`) is the implementation; do not rewrite it unless a real defect is found.
- Use a local fixture server or a disposable test provider, never a real personal key in evidence.

## Deliverables

- A repeatable device/emulator procedure in `docs/operations/M3/case-26-process-death.md`.
- Case 26 evidence in `M3-verification.md`: device/API, build, partial text preserved, interrupted status/explanation, regenerate result.
- A test fix if the procedure exposes a recovery gap.

## Implementation steps

1. Read `ChatRunner` persistence, `StreamingRecoveryService`, `AppStartup`, `InterruptedMessageNotice`, and `StreamingRecoveryServiceTest`.
2. Create a local SSE fixture server on the host or use the existing test fixture approach. Expose it to the emulator with `adb reverse tcp:<port> tcp:<port>` and configure a Custom provider using `http://localhost:<port>/v1` (allowed by M3-01.4).
3. In the app, start a long streaming response.
4. Wait until partial text is visible, then background the app and kill the process:
   ```bash
   adb shell am kill dev.chatui
   ```
   Do not use `am force-stop` if it removes the saved state needed for this test; use the kill that models process death.
5. Relaunch the app and open the same conversation.
6. Verify:
   - partial content is still present;
   - the message is not stuck at `streaming`;
   - the interrupted explanation is visible;
   - regenerate/retry works and does not branch or duplicate history.
7. If the last partial write is stale, record the maximum text loss from the 1-second persistence cadence.
8. Record the procedure and result without prompts or keys. Use synthetic fixture text.
9. If a defect is found, fix only the recovery/persistence code and add a regression test.

## Handoff notes

- The fixture model entry uses OpenRouter-shaped metadata
  (`architecture.modality`, `input_modalities`, `output_modalities`,
  `supported_parameters`) because the current custom-provider catalog path
  routes through the OpenRouter catalog mapper. A minimal OpenAI-shaped
  `/models` entry is discovered but stored with empty modalities, so the
  conversation service reports "No model is available". This is a provider
  catalog behavior outside this task's recovery scope; the procedure documents
  the fixture shape that works.
- `am kill` only kills a background process. Background the app and wait about
  two seconds before running `adb shell am kill --user 0 dev.chatui`; otherwise
  the process can remain in the previous state. Do not use `am force-stop` for
  this case.
- No real key, prompt, conversation content, personal data, or signing material
  is recorded in the procedure or evidence.
