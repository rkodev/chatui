# M3.5 - Rust multiplatform client (optional, parallel)

- Status: Optional / parallel
- Target: 3-4 weeks
- Depends on: M0 (contracts), M1 (OpenRouter reference behavior)
- Blocks: nothing in the phase 1 web/Android gate; M4 when the Rust client ships
- Platforms: Rust desktop (tier 1: Linux, macOS, Windows), Android (tier 2), iOS future, WASM optional preview
- Spec: sections 4, 5, 6, 7, 10.1-10.12, 11, 12.6, 14.5, 15.1-15.2, 17 (M3.5), 18

## Objective

Build an optional but first-class multiplatform Rust client with one Cargo workspace, a headless core, a shared UI shell, and thin platform apps. The client consumes the same `contracts/` artifacts as web and Android and must pass the same OpenRouter conformance suite before it is published. It is not a WebView wrapper and must never delay the web or Android milestones.

## Entry criteria

- M0 contracts exist and validate.
- M1 proves the OpenRouter reference behavior on at least one platform, giving Rust a conformance target.
- The UI framework spike is scheduled and budgeted; the milestone must not start feature UI before the framework choice is locked.
- Web and Android milestone leads agree that Rust work is parallel and non-blocking.

## Scope by workstream

### 1. Workspace and UI framework spike

Deliver:

- Cargo workspace with Rust stable, edition 2024, `resolver = "3"`, and a pinned `rust-toolchain.toml`.
- Crates: `chatui-domain`, `chatui-contracts`, `chatui-providers`, `chatui-storage`, `chatui-secrets`, `chatui-ui`.
- Apps: `apps/desktop`, `apps/android` (placeholder until packaging), `apps/ios` (future placeholder), `apps/wasm` (optional preview placeholder).
- `tests/conformance` fixture-driven conformance suite.
- UI framework spike comparing Dioxus, Slint, Iced, and a Tauri shell. Consider desktop plus Android without a WebView, accessibility, high-DPI, binary size, and build complexity. Lock the choice and record the decision before feature UI.
- Core crates remain UI-framework-agnostic. Platform integrations are feature-gated. A desktop build must not require the Android or iOS SDK.

Boundaries:

- No provider logic in `apps/*`; business logic belongs in crates.
- No WebView-based production client.
- No iOS shipping in phase 1.

### 2. Domain and contracts

Deliver:

- `chatui-domain`: serde structs/enums mirroring section 6 with matching JSON field names, UUIDv7 IDs, RFC 3339 timestamps, `StreamEvent`, `FinishReason`, `ChatError`, and `Settings`. No I/O dependencies.
- `chatui-contracts`: load `contracts/providers.json` and schemas at build time or runtime; strict serde types plus `jsonschema` validation for imports; tests that deserialize every fixture.
- No second serialization shape. No duplicated provider presets in Rust source.

### 3. Storage

Deliver:

- SQLite via `sqlx` (preferred) or `rusqlite`, with WAL, `foreign_keys = ON`, and a busy timeout.
- Versioned migrations, tested from an empty database, non-destructive in release builds.
- Repositories for conversations, messages, attachments, providers, models, secret metadata, settings, and future backup/sync tables.
- FTS5 virtual table over message text, kept in sync by repository writes or triggers.
- Content-addressed attachments under the platform app-data directory using the same layout as web and Android.
- Startup recovery: mark `streaming` messages cancelled, preserve partial content, clean orphan attachments.
- Export/import using `chatui.export`, validated with `jsonschema`; import merges by default and is non-destructive.
- UI code never issues SQL.

### 4. Secrets

Deliver:

- `keyring` integration: Linux Secret Service (libsecret) with documented fallback, macOS Keychain, Windows Credential Manager.
- Android Keystore-backed storage through a small JNI/`android-activity` bridge, or an encrypted file wrapped by a Keystore key.
- Explicit encrypted-file fallback when the credential store is unavailable: AES-256-GCM or XChaCha20-Poly1305 with an Argon2id-derived key and random salt. Never plaintext.
- Session-only mode that clears keys on exit.
- Redaction of `Authorization`, `x-api-key`, `x-goog-api-key`, and custom secret headers in logs and panic messages; zeroization of sensitive buffers.
- "Forget key" and "Forget all keys". Exclude secret stores and databases from cloud backup/sync where the platform supports it.

### 5. Networking and providers

Deliver:

- `ProviderAdapter` trait with async methods, `ProviderContext`, `ProviderKeyInfo`, `NormalizedChatRequest`, `StreamEvent`, cancellation via `CancellationToken`, and event delivery via `mpsc` or `futures::Stream`. The trait must be object-safe or use small enum dispatch.
- Shared `reqwest` client with `rustls-tls`, connection pooling, consistent user agent, connect timeout 30 s, no total timeout during streaming, and a 120 s inactivity watchdog that cancels with a retryable `timeout` error.
- SSE parser matching section 7.6 and appendix 21.1: CRLF normalization, multi-line data, comments, bounded buffer, final flush, keep-alive tolerance, and no JSON parsing in the transport. NDJSON parser for Ollama.
- OpenRouter adapter: `/key` validation, public `/models` with 24-hour cache and last-known-good snapshot, catalog mapping, `/chat/completions` streaming, reasoning deduplication, usage/cost, in-stream errors, attribution headers, curated routing controls, and protected fields.
- Registry loading presets from `contracts/providers.json`.
- Retry policy from section 7.9 with jitter, `Retry-After`, and no retry after partial output.
- Additional providers after OpenRouter passes: OpenAI-compatible presets, Anthropic, Gemini, and Ollama. Do not fork provider logic per platform.
- Wiremock/httpmock tests for SSE chunking, keep-alives, mid-stream errors, cancellation, and `Retry-After`.

### 6. UI shell and product surfaces

Deliver:

- Shared UI shell using section 11.12 tokens, themes, density, chat font size, reduced motion, and focus-visible states. Desktop uses a persistent sidebar; narrow windows and mobile use a drawer/navigation stack.
- Onboarding: welcome, OpenRouter preselected/recommended, key entry, test connection, default model.
- Provider and model management: provider list, add/edit custom, key rotation/removal, model refresh, model picker with search, pinned/hidden, capability chips, context, modalities, price per million, free badge, manual add.
- Chat: virtualized/windowed message list, stable keys, pagination, scroll anchoring, isolated streaming message, stop button, auto-scroll near bottom.
- Composer: auto-grow, Enter/Mod+Enter behavior, per-conversation drafts, attachment picker, drag-and-drop, clipboard paste, chips, disabled states, preserve text on failure.
- Markdown: `pulldown-cmark` GFM, tables, task lists, links, inline/fenced code; `syntect` or equivalent highlighting with copy; math renderer or sanitized raw fallback; no raw HTML; remote images blocked by default; incomplete fences render as code.
- Attachments: image/text selection, downscale with `image`, store via `chatui-storage`, capability warnings.
- Conversations: date groups, search, pin/archive/rename/delete, new chat, drafts, last-active restore.
- Settings: appearance, chat defaults, data/storage usage, clear data, export/import, backup placeholder, about/privacy. Wire settings to behavior.
- Export/import UI for `chatui.export`, per-conversation JSON/Markdown, attachment opt-in, plaintext warning.
- Platform integration: native menu bar, keyboard shortcuts, window-state persistence, drag-and-drop, optional multi-window, system theme, native file dialogs, clipboard copy, `chatui://chat/<id>` deep links, Android touch/safe-area/pickers/share target.
- Accessibility: keyboard navigation and focus rings on desktop, platform semantics on mobile, one desktop screen-reader smoke test per tier-1 OS, TalkBack on Android.
- No hidden network destinations.

### 7. Packaging, updater, and release

Deliver:

- Release profile: `lto = "thin"` or `"fat"`, `codegen-units = 1`, `strip = "symbols"`, and `panic = "abort"` where compatible with crash reporting. Keep a debug-symbol artifact.
- Desktop packaging via `cargo-dist` or equivalent: Windows MSI or portable zip, macOS signed/notarized DMG or app bundle, Linux AppImage and/or `.deb`/`.rpm`, plus checksums.
- Auto-update: signed manifests over HTTPS, signature verification before apply, pinned update public keys, stable/beta channels, and no auto-update during an active stream without asking.
- Android signed APK/AAB with the project signing policy when in scope; no WebView-only build.
- `cargo-deny` and `cargo-audit` clean of new advisories; unsafe isolated in platform bindings with documented invariants.
- Performance: cold start under 1.5 s on mid-tier desktop and under 2 s on mid-tier Android; installer under 40 MB and Android APK under 30 MB if feasible. Record actuals.
- CI matrix: Linux x86_64, macOS Apple Silicon, Windows x86_64; Android build/smoke on a Linux runner.
- Release artifacts published to GitHub Releases with checksums; signing keys only in CI secrets.

### 8. Conformance, parity, and release gate

- Fixture conformance for every shared stream, model catalog, and error fixture.
- OpenRouter conformance checklist from section 7.4.
- Critical test cases from section 15.2 that apply to Rust.
- Rust release gate from section 10.12: contracts consumed, OpenRouter suite passes, persistence across restart/process death, secure secret storage, required parity entries complete, signed artifacts and update manifests.
- Update `contracts/parity.md` Rust column honestly. It stays `Optional` until the client is enabled for release; after that, required rows must meet the same bar as web and Android.

## Out of scope

- Any change that delays M2, M3, or M4. If the Rust track competes for shared contracts or release engineering, the web/Android path wins.
- Replacing the web or native Kotlin Android client.
- iOS shipping and App Store distribution.
- WASM as the production web client. It may exist as an optional preview/embedding target.
- Backup/sync (M5) and managed hosting (M6).
- A second streaming event model or provider-specific serialization in the UI.

## Exit gate

- The OpenRouter conformance suite passes on Rust.
- Desktop builds run on all tier-1 operating systems; Android builds when in scope.
- Conversations persist across restarts and process death, and partial content survives cancellation.
- Keys are never stored in plaintext; OS credential stores or the explicit encrypted fallback are used, and backups exclude secrets.
- Shared contracts validate and Rust consumes them without duplicating provider metadata.
- Desktop artifacts are signed, update manifests are signed, and the Android artifact uses the project signing policy.
- The parity checklist is updated and the release gate in section 10.12 is satisfied.
- No web or Android milestone slip is attributable to this track.
- `cargo fmt`, `cargo clippy`, tests, and release builds pass in the CI matrix.

## Verification

```bash
make contracts-check
cd rust && cargo fmt --all --check
cd rust && cargo clippy --workspace --all-targets -- -D warnings
cd rust && cargo nextest run --workspace
cd rust && cargo build --release --workspace
cd rust && cargo deny check && cargo audit
```

Plus the chosen framework's UI test harness, packaging commands, and cross-platform smoke-test evidence.

## Task-generation guidance

Expect 7-10 tasks; this milestone may be split into M3.5a (core + OpenRouter) and M3.5b (UI + release) if needed. Suggested slices:

1. Workspace skeleton and UI framework spike/decision.
2. Domain and contract loading.
3. SQLite storage, migrations, attachments, and export/import.
4. Secret storage, keyring, encrypted fallback, and redaction.
5. OpenRouter adapter, SSE/NDJSON parsers, registry, retry, and conformance fixtures.
6. UI shell, onboarding, provider/model management, and chat.
7. Conversations, settings, rendering, attachments, and export/import UI.
8. Desktop/Android platform integration and accessibility.
9. Packaging, auto-update, signing, and CI matrix.
10. Additional providers, fixture conformance, and parity/release gate.

Do not generate Rust tasks that modify `web/` or `android/`. Contract changes must be separate shared tasks with cross-milestone approval.

## Risks and decisions to confirm

- UI framework maturity is the main schedule risk. Run the spike first and keep core crates UI-agnostic.
- Multiplatform secret-storage variance can produce insecure fallbacks. Require an explicit encrypted fallback and test each OS storage path.
- Binary size and build time can grow quickly. Tune the release profile, gate features, and cache CI targets.
- Android Rust builds add toolchain complexity. Keep Android packaging optional until desktop is stable.
- The Rust track can distract from the phase 1 web/Android preview. Treat it as optional with no release-gate dependency.
- Auto-update compromise is a serious threat. Verify signed manifests and pin update public keys.
