## Goal

Implement first-run onboarding with OpenRouter preselected, secure key entry, connection validation, default model selection, and clear error states.

## Preconditions

- The shell, secret store, OpenRouter adapter, and provider registry exist.
- Do not store keys in provider records, logs, or plaintext.
- Do not accept a key when `GET /key` fails.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Welcome screen with OpenRouter recommended and preselected.
- Key-entry form with masked input, validation state, and test-connection action.
- Success path:
  - validate with `/key`;
  - load `/models`;
  - select the default model;
  - store the key securely;
  - complete onboarding.
- Failure path:
  - show an actionable auth/network error;
  - preserve the form;
  - do not accept the key.
- Default-model selection using the shared fallback rules.
- Ability to skip onboarding only where the spec allows, with sending disabled until a provider/key exists.
- Tests with fake adapters and secret stores; no real keys.

## Implementation steps

1. Read spec sections 3.1, 3.4, 7.4, 11.3, and 11.5, plus `web/src/features/onboarding/*`.
2. Build the onboarding view model with states: welcome, key entry, validating, validating-failed, catalog-loading, model-selection, complete.
3. Preselect OpenRouter. Load the public catalog even before the key is entered if the adapter allows it.
4. On test connection:
   - call `validate_key`;
   - on success, store the key through `SecretStore`;
   - load the catalog;
   - choose the default model;
   - persist the provider record and default settings.
5. On failure, show the normalized error copy and keep the form values. Never echo the key.
6. Implement the default-model rule from the request-vector README: preset default when present, otherwise first non-hidden text model, otherwise fallback with a notice.
7. Wire completion to the shell and persist `onboardingCompleted`.
8. Add tests for invalid key, valid key, catalog failure with cached/fallback models, default-model missing, and no key leakage.
9. Document the onboarding state machine and error copy.

## Handoff notes

### Onboarding states

`OnboardingStep` is framework-independent and maps to a stable Slint index:

| Step | Index | Behavior |
| --- | --- | --- |
| `Welcome` | 0 | OpenRouter label, `Recommended` badge, public catalog count, connect CTA |
| `KeyEntry` | 1 | Password field, optional label, remember-key checkbox, connect action |
| `Validating` | 2 | `GET /key` in flight; connect action disabled |
| `ValidatingFailed` | 3 | Actionable error; key and label values are preserved |
| `CatalogLoading` | 4 | `/models` is loading |
| `ModelSelection` | 5 | Catalog summary/notice and selected default model |
| `Complete` | 6 | Persisted provider/model, optional notice, route to the shell |

Transitions are `Welcome -> KeyEntry -> Validating -> CatalogLoading ->
ModelSelection -> Complete`. A validation failure goes to `ValidatingFailed`
and keeps the form. Catalog failures during connect are non-blocking when a
cached or preset fallback exists; failures after connect remain a
`ValidatingFailed` error because setup could not finish. Loading the public
catalog before key entry is non-blocking: a failure leaves the welcome screen
usable and shows catalog copy.

### Connect and rollback flow

1. Trim and reject an empty key with `InvalidInput`.
2. Validate with `KeyValidator::validate_key` (`GET /key`). A failure stops
   before anything is written.
3. Store the key through the injected `SecretStore` under `provider-<id>`.
4. Load the public catalog. On failure, use `ModelStore::cached_models`, then
   the preset fallback IDs, then fail.
5. Select the default model with the shared fallback rule.
6. Persist the provider record (non-secret `/key` metadata only), models, and
   the settings defaults plus `onboarding_completed = true`.
7. Emit `Complete`.

Any failure after step 3 deletes the provider, models, and secret and restores
the previous settings, so a rejected or incomplete setup stores nothing.

### Default-model behavior

The service uses `chatui_providers::select_fallback_model` with
`preset.default_model_id` and `fallback_model_ids_for(preset_id, preset)`:

1. Use the preset default when it exists in the catalog.
2. Otherwise use the first preset fallback ID present in the catalog.
3. Otherwise use the first non-hidden text-output model ordered by `remote_id`.
4. Otherwise return `OnboardingError::NoModel` and roll back.

Fallback-only catalogs are treated as an empty catalog so the result reports
`Discovery unavailable; using fallback model <id>.` instead of pretending a
placeholder was discovered. The selected default is persisted in
`Settings.default_model_id` and `ConnectResult.model_remote_id`.

### Error copy

`describe_onboarding_error` maps normalized `ChatErrorCode` values to the spec
11.8 copy, including auth ("Your API key was rejected. Check the key and
try again."), permission, quota, rate limit, model unavailable, context length,
content filter, invalid request, network/CORS, timeout, cancellation, parse,
storage, and provider/unknown. `describe_catalog_error` returns the non-blocking
"You can still connect; models will load after validation." copy.

The typed key is redacted from messages and details, never shown outside the
password field, and `ConnectInput`/`OnboardingViewModel` `Debug` output prints
`[REDACTED]`. Loading the catalog before entry never sends a key.

### Skip and sending

First-run setup cannot be skipped. `OnboardingViewModel::skip` returns
`NotConfigured` unless `set_can_skip(true)` was set for re-entry where a
provider/key already exists. Even when skip completes onboarding,
`can_send()` stays false until a provider ID and model ID are persisted, which
keeps the composer disabled without a provider/key.

### Deviations and constraints

- `ConnectInput.remember_key` is carried from the form for parity with web and
  Android, but per-key session persistence is not selected here. The injected
  `SecretStore` decides persistence (OS keyring, encrypted fallback, or
  session-only) per the M3.5-04 lifecycle, so the flag does not switch stores.
- `OnboardingController::new` loads the public catalog synchronously, matching
  the slint-first shell in this task. Production callers should run it on a
  worker thread or provide a non-blocking service.
- Unlike the web onboarding service, this task does not create the first
  conversation. Completion persists the provider/model defaults and exposes
  `OnboardingRoute::Shell`; conversation creation belongs to the chat tasks.
- Slint markup is inline in `view.rs` so the task stays inside its owned source
  paths. Headless tests use `i-slint-backend-testing` with
  `init_no_event_loop()`.
- No `web/`, `android/`, or `contracts/` files were modified. No provider or
  model management screens were added.
