## Goal

Define the request-side conformance vectors and the M1 evidence template. Both adapters must serialize OpenRouter requests the same way and must reject attempts to override protected fields.

## Preconditions

- M1-01.1 is complete.
- Contracts validate.

## Deliverables

- `contracts/fixtures/requests/openrouter-basic.json`: normalized request with a system prompt, one user message, model, and streaming parameters, plus the expected OpenRouter JSON body.
- `contracts/fixtures/requests/openrouter-routing.json`: curated `allow_fallbacks`, `sort`, and `data_collection` mapping.
- `contracts/fixtures/requests/openrouter-advanced-protected.json`: advanced JSON that attempts to override `model`, `messages`, `stream`, and `stream_options`, plus the expected validation result.
- `contracts/fixtures/requests/openrouter-attribution.json`: expected `HTTP-Referer` and `X-Title` headers from app config.
- A documented default-model fallback rule.
- `docs/operations/M1/M1-verification.md` skeleton with sections for commands, CORS matrix, OpenRouter conformance checklist, fixture conformance, critical cases, and manual smoke.
- Validator support for request vectors.

## Default-model rule to record

Use `defaultModelId` from `contracts/providers.json` when it exists in the loaded catalog. Otherwise select the first non-hidden model with text output, ordered by `remoteId` ascending. If the preset default is missing from the catalog, surface a non-blocking unavailable notice and do not invent a model.

## Implementation steps

1. Read the OpenRouter request example and routing rules in spec 7.4.
2. Write the request vector files with both normalized input and expected provider payload.
3. Include an unsupported-parameter case: an unsupported generation control must be omitted, not sent.
4. Include a protected-field case where `params.extra.openrouter` contains a forbidden key; expected result is a normalized `invalid_request` error.
5. Write the M1 verification skeleton with empty evidence tables. Do not claim results before tests run.
6. Extend the validator to check request vectors and to reject fixture files with no expected result.
7. Run the contract gate.

## Handoff notes

- Final request-vector shape: `{ name, kind, providerId, request,
  supportedParameters, expected }` for `chat-request` and `protected-fields`;
  `{ name, kind, providerId, appConfig, expected }` for `attribution`; and
  `{ name, kind, providerId, cases }` for `default-model`. `name` must match the
  file name. `kind` is one of `chat-request`, `protected-fields`, `attribution`,
  or `default-model`.
- The normalized request uses the spec 7.3 shape. Text parts are concatenated
  into one OpenRouter `content` string. `stream_options` is always
  `{ "include_usage": true }` for streaming requests. Optional controls are
  emitted only when present and listed in `supportedParameters`.
- Protected fields are `model`, `messages`, `stream`, and `stream_options`.
  A protected-field vector must expect an `invalid_request` error with
  `details.protectedFields` sorted ascending, and must not contain an expected
  body.
- Default-model decision: use `defaultModelId` when it exists in the catalog;
  otherwise select the first non-hidden text-output model by `remoteId`
  ascending and surface a non-blocking unavailable notice. The exact notice
  strings are encoded in `openrouter-default-model.json` and documented in the
  request-vector README.
- OpenRouter ambiguity: the spec allows advanced JSON to supply `order`, `only`,
  `ignore`, `models`, and `route`, but M1 only requires curated `provider`
  routing. The validator accepts `provider`, `models`, `route`, and `reasoning`
  under `params.extra.openrouter` and rejects the protected keys. Adapters
  should keep the curated `provider` object as the M1 path and treat the other
  advanced keys as pass-through only when explicitly supplied.
- The verification skeleton intentionally records no results. M1-10 owns filling
  the evidence tables and updating `browserCors`.
