- Milestone: M3.5
- Status: Not started

- Depends on: M3.5-05.1, M3.5-05.2
- Parallel-safe: yes, with M3.5-05.3
- Owns: `rust/crates/chatui-providers/src/retry.rs`, `rust/crates/chatui-providers/src/cancel.rs`, `rust/crates/chatui-providers/tests/network/`
- Read first: [M3.5 plan](../M3.5-rust-desktop-implementation-plan.md) sections 3.5 and 4.7; spec sections 7.9, 10.7, 15.2

## Goal

Implement the shared retry, inactivity-watchdog, and cancellation behavior and create the network mock harness later provider tasks will reuse.

## Preconditions

- The HTTP client and SSE parser exist.
- Do not retry after partial output.
- Do not add provider-specific logic here.
- Do not modify `web/`, `android/`, or `contracts/`.

## Deliverables

- Retry policy:
  - at most 3 attempts including the first;
  - exponential backoff with jitter;
  - base 800 ms, cap 8 seconds;
  - `Retry-After` honored when present;
  - no retry after text or reasoning has been emitted.
- Cancellation via `tokio_util::sync::CancellationToken` or equivalent.
- A 120-second inactivity watchdog that cancels a stalled stream with a retryable `timeout` error.
- A reusable `wiremock` or `httpmock` harness for:
  - SSE chunking;
  - keep-alives;
  - mid-stream errors;
  - cancellation;
  - `Retry-After`;
  - connection and timeout failures.
- Tests for retry counts, jitter bounds, abort-aware sleep, watchdog firing, and no-retry-after-partial.

## Implementation steps

1. Read `web/src/providers/retry.ts` and spec section 7.9.
2. Implement `compute_retry_delay(attempt, policy)` with a deterministic jitter injection point for tests.
3. Implement `retry_delay_for(retry_after, attempt, policy)` where provider `Retry-After` wins.
4. Implement an abort-aware sleep using `tokio::select!` and the cancellation token.
5. Implement a retry loop helper that accepts a closure or adapter call, tracks whether text/reasoning was emitted, and stops retrying when partial output exists.
6. Implement the inactivity watchdog around the response stream. Reset it on every received chunk. On 120 seconds of inactivity, cancel the request and return a retryable `timeout`.
7. Build the network mock harness under `tests/network/`. Keep it reusable by later adapter tests.
8. Add tests:
   - 3 attempts max;
   - jitter within the documented range;
   - `Retry-After` overrides local backoff;
   - cancellation interrupts sleep and stream reads;
   - no retry after partial output;
   - watchdog fires with a retryable timeout.
9. Document the harness API in `docs/operations/M3.5/conformance.md` or a small provider test note.

## Acceptance criteria

- [ ] Retry policy matches section 7.9.
- [ ] Jitter and `Retry-After` are implemented.
- [ ] Sleep and stream reads honor cancellation.
- [ ] The inactivity watchdog cancels after 120 seconds with a retryable `timeout`.
- [ ] No retry happens after partial output.
- [ ] The network harness covers chunking, keep-alives, mid-stream errors, cancellation, `Retry-After`, and timeouts.
- [ ] Tests pass.
- [ ] No provider-specific adapter logic is added.
