## Handoff notes

### Provider UI states

The framework-independent state lives in `providers::state`; `providers::view`
is the Slint controller. `ProviderManagementViewModel` holds:

| Field | Meaning |
| --- | --- |
| `list` | Rows with label, preset label, enabled state, recommended badge, key presence, CORS, docs URL |
| `detail` | Selected provider: base URL, auth style, non-secret `/key` metadata (label, usage, limit, free tier, rate limit), CORS, headers, cleartext warning, model count |
| `form` | Custom-provider create/edit form; key held in a `SecretValue` whose `Debug` prints `[REDACTED]` |
| `pending_confirmation` | One of `ForgetKey`, `ForgetAllKeys`, `DeleteProvider` awaiting a second click |
| `notice` / `error` | Non-blocking success copy and `ProviderManagementErrorCopy` |

The window shows the list on the left and either a detail panel or the custom
form on the right. Details are opened by `select_provider`; the form opens from
`add-provider` or by editing a custom provider. `sync_window` pushes the whole
view model into the window after every action.

### Key lifecycle

All keys live only in the injected `SecretStore`. A provider record stores just
`secret_id`; the list checks presence with `SecretStore::get`, and the detail
shows only the non-secret `/key` metadata cached under `metadata.key`.

| Action | Behavior |
| --- | --- |
| Create custom | Validate URL/auth/headers/key, optionally validate the key, store under `provider-<id>`, save the provider; a failed save removes the new secret |
| Edit custom | Empty key keeps the existing secret; a supplied key is validated before it replaces the old one; switching to `none` auth forgets the key |
| Rotate | Require a non-empty key, validate it, store under a new `provider-<id>-<new_id>`, save, then delete the old secret |
| Failed rotation | Validation runs before any write, so the old key and record are untouched |
| Forget key | Requires confirmation; removes the secret and clears `metadata.key`/`validatedAt` |
| Forget all | Requires confirmation; calls `SecretStore::forget_all_keys` and clears `secret_id` plus key metadata on every provider |
| Delete provider | Requires confirmation; deletes models, forgets the secret, clears conversation `provider_id`/`model_id` while keeping `model_label`, clears matching global defaults, then deletes the record |
| Test connection | Requires a stored key; validates with `GET /key`-style validator and refreshes the cached metadata |

`rotate_key`, `update_custom_provider`, and `create_custom_provider` create a
new secret ID rather than overwriting the old value, so a failed provider save
can remove the new secret and leave the old one intact.

### Validation rules

- HTTPS is always allowed.
- Cleartext HTTP is allowed only for localhost, `.local`, and private-range
  hosts; it always carries an explicit warning in the form and detail.
- Public cleartext HTTP is rejected before any write.
- Base URLs must not include credentials, a query string, or a fragment.
- Query-string API keys are not supported; choose bearer, x-api-key, or none.
- A key is required for bearer/x-api-key on create; an empty key on edit keeps
  the stored key; a key with `none` auth is rejected.
- Non-secret headers must use valid HTTP names and non-empty single-line
  values. `authorization`, `x-api-key`, `cookie`, and similar authentication
  headers are rejected because the auth style owns them.
- Labels default to `Custom OpenAI-compatible` on create and to the existing
  label on edit; duplicate labels are rejected case-insensitively.

### Error copy and redaction

`describe_provider_error` maps `ChatErrorCode` to actionable copy mirroring the
spec (auth, permission, quota, rate limit, network/CORS, timeout, cancellation,
parse, storage, provider/unknown). The typed key is redacted from both the
message and details before the copy reaches the view. Service-level chat errors
are also scrubbed with `redact_chat_error` before they are wrapped.

### Deviations and constraints

- The service is injected with traits for provider, model, conversation,
  settings, secret, and key-validation access. Persistence adapters are not
  constructed here; production wiring belongs to the desktop integration task.
- Slint markup is inline in `view.rs` so the task stays inside its owned source
  paths. Headless tests use `i-slint-backend-testing` with
  `init_no_event_loop()`.
- Provider metadata and docs links come from `chatui_contracts::provider_catalog`;
  recommended is true for the contract default or `openrouter`, matching the
  onboarding recommendation.
- Controller actions call the service synchronously, matching the slint-first
  shell in this task. Production callers should move validation and connection
  tests to a worker thread.
- `providers/{state,validation}.rs` carry the same
  `#![allow(clippy::result_large_err)]` used by the onboarding modules because
  `ProviderManagementError::Chat` wraps the larger normalized `ChatError`.
- No model discovery, picker, pinned/hidden, or manual model management was
  added; that remains M3.5-08.4.
