# M5-07.3 - Rust Azure Blob, GCS, Google Drive, and WebDAV adapters

- Milestone: M5
- Status: Not started
- Order: 23
- Depends on: M5-03.3, M5-04.3
- Parallel-safe: yes, with `M5-07.1` and `M5-07.2`
- Owns: `rust/crates/chatui-backup/`, `rust/crates/chatui-ui/`
- Read first: [M5 plan](../M5-backup-and-sync-implementation-plan.md) sections 3.4 and 5.3; spec section 13.6

## Goal

Add the remaining storage backends on Rust behind the existing `StorageAdapter`
trait: Azure Blob, Google Cloud Storage, Google Drive, and WebDAV. Enable them in the backup
settings UI. The adapters must only ever receive encrypted bytes.

## Preconditions

- `M5-03.3` and `M5-04.3` are `Complete`.
- The `StorageAdapter` trait and typed errors exist.
- Rust is required for M5 (`M5-decisions.md` `DEC-M5-03`).
- Use `reqwest`; do not add a cloud SDK or a server proxy.

## Deliverables

- `rust/crates/chatui-backup/src/storage/azure.rs`:
  - Account name + key or SAS token.
  - Block blob PUT/GET/HEAD/DELETE.
  - ETag/`If-Match` conditional writes.
  - Connectivity test.
- `rust/crates/chatui-backup/src/storage/gcs.rs`:
  - Service account JSON (JWT -> OAuth2 token) initially.
  - JSON or XML API operations.
  - Generation/`If-Match` conditional writes where available.
  - Connectivity test.
- `rust/crates/chatui-backup/src/storage/google_drive.rs`:
  - OAuth access token; app data folder or user-selected folder.
  - Drive v3 file create/update/get/delete; no ETag/`If-Match`.
  - Conservative consistency handling; re-read after write and retry on
    conflict.
  - Connectivity test.
- `rust/crates/chatui-backup/src/storage/webdav.rs`:
  - URL + username + password (Basic auth).
  - PUT/GET/HEAD/DELETE and `PROPFIND` for list.
  - Conservative consistency handling.
  - Connectivity test.
- Backup settings UI: enable the four backends with backend-specific fields.
- Tests with a local mock server:
  - Auth header construction.
  - PUT/GET/HEAD/DELETE for each backend.
  - Conditional write conflict handling.
  - Connectivity test success and typed errors.
  - No plaintext is passed to any adapter.

## Implementation steps

1. Read the `StorageAdapter` trait, S3 adapter, and backup settings UI.
2. Implement Azure Blob:
   - Build the shared-key signature or SAS URL.
   - Use block blob PUT.
   - Parse `ETag` and send `If-Match` on rewrite.
3. Implement GCS:
   - Build and sign a JWT with the service account key.
   - Exchange it for an OAuth2 access token.
   - Use the JSON API for object operations.
   - Use generation preconditions for conditional writes.
4. Implement Google Drive:
   - OAuth access token; app data folder or user-selected folder.
   - Drive v3 file create/update/get/delete.
   - No ETag/`If-Match`; re-read after write and retry on conflict.
5. Implement WebDAV:
   - Basic auth header.
   - PUT/GET/HEAD/DELETE and `PROPFIND`.
   - Re-read after write; never assume read-after-write.
6. Update the backup settings UI to show backend-specific fields.
7. Add tests with a local mock server. Use synthetic encrypted bytes only.
8. Run the Rust gates.

## Acceptance criteria

- [ ] Azure Blob, GCS, Google Drive, and WebDAV adapters implement `StorageAdapter`.
- [ ] Each adapter has a connectivity test with typed errors.
- [ ] Conditional writes are used where supported and handled conservatively.
- [ ] Backend-specific settings fields exist in the UI.
- [ ] No cloud SDK or server proxy is added.
- [ ] No adapter receives plaintext.
- [ ] Tests pass.
