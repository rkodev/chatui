## Goal

Demonstrate the redesigned app's actual entry-level startup, frame, feedback,
and memory behavior against the controlled pre-redesign baseline.

## Read first

Read the [execution contract](README.md), source-plan section 7,
UX-00.2's fixtures, UX-00.3's baseline/protocol/budget decisions,
UX-03.4 through UX-03.7 handoffs, and UX-06.3's generated-profile/build record.

## Owns

Measurement/evidence in this task's Handoff notes and narrowly scoped timing scenarios
in the existing `android\baselineprofile` test module if the current producer
has no timing tests. Its existing macrobenchmark dependency may be reused;
no dependency/toolchain upgrade or new performance module.

## Deliverables

Comparable distributions/traces and a pass/fail budget table covering
entry-level and mid-tier hardware, with no unsupported performance claims.

## Implementation steps

1. UX-00.3 was deferred by the owner before a complete AVD baseline was
   accepted; preserved pilots are not a performance pass. Obtain and name
   actual entry-level and mid-tier physical devices;
   missing hardware blocks this task. Run both UX-00.3's frozen pre-redesign
   build and the candidate on the same physical devices, reusing its seed/reset
   recipe and usable-screen marker. Record matching build/compilation/profile
   configuration and actual power/thermal conditions for both builds; if using
   a different optimization configuration, rebuild and remeasure both. Keep
   AVD-to-AVD comparison separate; never compare emulator numbers to phones.
2. Measure at least 30 cold starts to first usable local screen and report
   distributions/p95. Activity launch completion or profile generation alone
   is not a substitute for the agreed usable-screen marker.
3. Measure local typing/taps, history/chat scrolling, deterministic streaming/
   Stop, large code, and supported images. Separate provider/network latency
   from UI latency and retain raw trace/report references.
4. Use existing platform profiling and available macrobenchmark tools for
   startup/frame timing. If a missing timing scenario must be added, keep it
   fixture-driven in the existing producer and record its actual instrumentation
   selector; do not run the profile generator and relabel its output a benchmark.
5. Compare ordinary feedback <=100 ms, mid-tier cold-start <1.5 s, entry-level
   p95 startup <2.5 s and p95 frames <=32 ms, no >700 ms frozen frames/ANRs,
   no OOM with 10,000 messages/images, and steady/peak PSS change. Investigate
   >10% growth or retained growth after repeated navigation.
6. Inspect image decode sizes, background URI reads, idle animation work,
   duplicate observers, and rendering reuse when a scenario fails. Return
   measured defects to the bounded owning task; rerun affected measurements
   after a fix rather than reducing features/text/quality or changing budgets.
7. Record offline/slow-provider local responsiveness and equal supported
   actions across resource tiers. Missing hardware or unmet budgets block this
   acceptance; emulator results may supplement but not replace physical proof.

## Acceptance criteria

- [ ] Baseline/redesign conditions, builds, profiles, and fixtures are comparable.
- [ ] Required sample sizes, distributions, frame/memory traces are recorded.
- [ ] Agreed budgets pass or the task remains explicitly blocked with an owner.
- [ ] No feature/content/model/privacy behavior was reduced to improve numbers.

## Verification

Execute UX-00.3's exact timing/memory protocol using the redesigned build.
If adding a timing class, run the existing
`:baselineprofile:connectedBenchmarkReleaseAndroidTest` task with that actual
class selector and record it; collect platform traces/PSS separately as needed.
Verify sample counts/percentiles and link raw artifacts plus summarized results.

## Out of scope

Network throttling, lowered attachment/draft limits, hiding expensive content,
model substitution, new benchmark dependencies, or invented device results.
