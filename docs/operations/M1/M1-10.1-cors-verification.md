## Goal

Verify browser-direct OpenRouter access for `/key`, `/models`, and `/chat/completions`, record the result, and update the preset CORS status. A blocker must stop the web release rather than be hidden behind a proxy.

## Preconditions

- Web adapter and onboarding paths can issue the three requests.
- Use a disposable OpenRouter test key. Never commit or screenshot the key.

## Deliverables

- CORS matrix in `docs/operations/M1/M1-verification.md` with endpoint, origin, preflight result, status, response headers observed, timestamp, and conclusion.
- Evidence for `/key` with a valid and invalid key.
- Evidence for `/models` without a key.
- Evidence for `/chat/completions` with a short streaming request.
- Updated `browserCors` in `contracts/providers.json` to `supported` or `unsupported`.
- A clear release-stop note if any endpoint is blocked.

## Implementation steps

1. Read spec 7.7 and the preset `browserCors` field.
2. From a normal browser profile, open the built web app on the intended origin.
3. Run `/models` without a key and record the result.
4. Run `/key` with a disposable valid key and with an invalid key. Record auth behavior.
5. Run `/chat/completions` with `stream: true` and a tiny prompt. Confirm chunks arrive.
6. Inspect DevTools network details for preflight, status, and CORS errors.
7. Record results with the key redacted.
8. Set `browserCors` to the observed value and run `make contracts-check`.
9. If blocked, write the release-stop note and do not implement a proxy.

## Acceptance criteria

- [x] All three endpoints have evidence or a documented blocker.
- [x] The result is reproducible from the recorded origin and browser.
- [x] No key appears in the document, screenshots, or logs.
- [x] `browserCors` matches the observed result.
- [x] A blocker is recorded as a web release stop.
- [x] `make contracts-check` passes.
