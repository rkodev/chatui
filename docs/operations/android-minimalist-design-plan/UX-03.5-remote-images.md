# UX-03.5 - Bounded remote Markdown images

- Phase: UX-03 - Chat readability and resources
- Status: Complete
- Order: 17
- Depends on: UX-03.1
- Output folder: `docs\operations\android-minimalist-design-plan`
- Parallel-safe: No with ChatMarkdown image/rendering edits.

## Goal

Replace full-source remote-image decoding with display-sized loading while
preserving image consent, URL safety, readable fallback, and cached behavior.

## Read first

Read the [execution contract](README.md), source-plan sections 2, 5.2,
7, and 8, `Chat\ChatMarkdown.kt`, existing local attachment image requests,
the current safe URL/loading policy, and `ChatMarkdownTest.kt`.
The local Coil thumbnails are already bounded; target the remote decode path.

## Owns

Remote-image loading/rendering in `ChatMarkdown.kt`, a small private loader
helper beside it if needed, and related Markdown regressions. Reuse the
existing image stack and client/policy; no new image dependency.

## Deliverables

Target-sized remote image requests/caching, distinct pending/failure states,
and no image-policy or preference-default changes.

## Implementation steps

1. Trace `BitmapFactory.decodeStream` and existing network/URL restrictions.
   Identify which request path enforces consent; preserve those checks before
   any fetch, including cache-backed presentation.
2. Use actual available display constraints to request a bounded decode through
   the existing image-loading stack, preserving aspect ratio and safe limits.
   Avoid a new unrestricted loader/client bypassing established policy.
3. Ensure request identity/cache keys and cancellation respond to URL/size/
   conversation changes without refetching on ordinary recomposition.
4. Show a neutral pending state while loading, not "Image unavailable".
   Preserve alt text/filenames, explicit blocked/consent state, real failure
   fallback, and existing retry/recovery.
5. Keep local attachment request sizing and `loadRemoteImages` values/default
   unchanged. Do not make a visual optimization silently load previously
   blocked remote URLs.
6. Add tests using a fake loader/response for pending versus failure, denied
   image policy, safe/unsafe URLs, bounded requested size, retry, and request
   cancellation/reuse. Include a large-aspect-ratio fixture.

## Acceptance criteria

- [x] Remote display paths no longer decode full source images unnecessarily.
- [x] Loading, blocked, failed, and successful states are distinguishable.
- [x] Existing privacy/URL policy and local image limits remain intact.
- [x] Recomposition does not create redundant downloads/unbounded caches.

## Verification

```powershell
Set-Location .\android

```

Record request-size evidence and review image states. UX-06.4 verifies actual

## Out of scope

Changing remote-image defaults, allowing new URL schemes/hosts, replacing all
local image loading, or discarding supported images.

## Handoff notes

- Remote Markdown display now uses the existing Coil stack, not raw
  `BitmapFactory.decodeStream`. Requests use actual display constraints,
  bounded to 760 dp width/320 dp height and `Scale.FIT`, preserving aspect
  ratio and existing shared caching.
- URL/policy/owner consent gates run before composing the loader, including
  cached presentation. Owner keys include conversation/message identity;
  URL, owner, size, retry and disposal control request lifetime. Retry does
  not cache-bust URLs. Pending, blocked/Load, failure/Retry and ready states
  retain alt/fallback text.
- Retained Markdown ASTs now render against their own parsed source via the
  existing success renderer, avoiding stale image offsets indexing newer,
  shorter text. The renderer and supported content are otherwise unchanged.
- All 16 `ChatMarkdownTest` cases passed within 170 chat tests; chat lint has
  no errors. Fake-loader evidence covers target dimensions/FIT, an 8000 x 100
  source, denied/unsafe URLs, pending/failure/retry, consent ownership,
  reuse and cancellation, without real network requests.
- Local image sizing and the persisted `loadRemoteImages = true` default are
  unchanged. Supported local-format candidates were reviewed in both themes/
  densities; see the
  [verification record](README.md#ux-012-through-ux-037-verification-record).
  UX-06.4 must still measure actual device decode memory/OOM budgets.
