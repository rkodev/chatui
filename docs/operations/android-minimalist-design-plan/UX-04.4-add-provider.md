## Goal

Make preset/custom setup a focused, scrollable form with progressive disclosure
while preserving authentication, custom headers, and connection safeguards.

## Read first

Read the [execution contract](README.md), source-plan sections 5.5 and
8, `Providers\ProviderListScreen.kt`, `Providers\ProviderRoutes.kt`,
`Providers\ProviderListViewModel.kt`, existing validation/service APIs,
`DS\SecureScreen.kt`, and provider list/route tests.

## Owns

Existing add-form content or private sibling extracted in UX-04.3, its route/
ViewModel presentation plumbing, and focused create-form tests. Do not change
provider preset data, validation policy, or secret persistence.

## Deliverables

Preset-first setup, focused Custom configuration, optional-field disclosure,
and usable error/IME/secure-entry behavior.

## Implementation steps

1. Show one preset choice followed by required connection/credential fields
   and one primary create/connect action; do not ask for the same preset twice.
2. Preserve enabled, disabled, and unsupported preset distinctions from the
   service. Use wrapping choices/a selector when chips would overflow.
3. For Custom keep base URL and Bearer/x-api-key/None selection visible.
   Preserve key show/hide, optional label, and add/edit/remove custom headers
   under clearly labeled optional sections.
4. Keep cleartext warnings and blocked-connection explanations beside the
   primary connection fields, not hidden under Advanced. Reuse all existing
   validation and secure-window behavior.
5. Preserve entered values after recoverable failure and distinguish pending,
   success, cancel, and error. Do not persist secrets in rememberSaveable or
   generic state bundles; keep safe existing memory/secret-store lifetimes.
6. Make the whole form/actions reachable with keyboard/large text on a 320 dp
   window and short landscape. Avoid same-axis nested scrolling forms.
7. Add regressions for each auth mode, custom headers, invalid/cleartext URL,
   unsupported preset, recoverable error retention, duplicate submit,
   dismissal, and secure/accessible key-entry behavior.

## Acceptance criteria

- [ ] Preset/custom setup exposes every existing option with one clear primary action.
- [ ] Optional fields are discoverable; warnings/required fields are not hidden.
- [ ] No-auth/custom-header flows and validation behavior are preserved.
- [ ] Keyboard/large-font layouts and sensitive input handling remain safe.

paid generation, or changing provider storage.
