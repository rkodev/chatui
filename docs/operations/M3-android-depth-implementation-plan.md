# M3 Android Depth Implementation Plan

- Source milestone: [M3-android-depth.md](../milestones/M3-android-depth.md)
- Task breakdown: proposed in [section 4](#4-proposed-work-breakdown); formal task records are not generated by this document
- Authoritative spec: [IMPLEMENTATION.md](../IMPLEMENTATION.md)
- Foundation baseline: [M1 verification evidence](M1/M1-verification.md)
- Status: Proposed
- Prepared: 2026-11-04
- Scope: Android platform completeness, lifecycle recovery, secure-storage hardening, UI and screenshot coverage, release configuration, performance, accessibility, device evidence, and parity updates
- Platforms: Android only
- Planning assumption: M3 starts only after the M2 exit gate is met on Android. The repository audit below was taken at the M1-complete/M2-not-started boundary and is deliberately explicit about which missing work belongs to M2 and must not be absorbed into M3.

## 1. Summary

M1 delivered the OpenRouter reference path on Android: Tink-backed ciphertext storage, streaming chat, conversation persistence, startup interruption recovery, provider/model management, and Robolectric component tests. M2 has not landed in the working tree. The M3 surface is therefore mostly a hardening and integration layer over code that does not yet exist, plus a set of platform features that are absent today.

| Area | Current completion | Assessment |
| --- | --- | --- |
| M2 Android prerequisite | 0% in this tree; M2 status is Planned | M3 blocked until M2 exit gate; the shell still renders provider and settings placeholders |
| Secret storage foundation | Present | Tink `AndroidKeysetManager` with Android Keystore, AES-256-GCM, ciphertext-only Room storage, redaction helper |
| Secret/privacy hardening | Partial | No production-keystore instrumentation test, no on-device backup proof, no `FLAG_SECURE`, no network security config, no key-rotation decision for the Tink keyset |
| Platform integration | Mostly missing | Copy message/code exists and provider docs open in an external browser. Share target, deep links, Custom Tabs, drag-and-drop, clipboard image paste, and tablet layout are absent |
| Lifecycle and recovery | Partial | Configuration changes are handled by ViewModel retention; startup recovery exists. Drafts are in-memory, process-death evidence is unit-level only, and orphan-attachment cleanup does not exist |
| Compose UI tests | Partial | Robolectric component tests exist for onboarding, chat, provider, and conversation screens; no `androidTest` source set and no device-level flow tests |
| Screenshot tests | Missing | No Roborazzi, Paparazzi, or equivalent screenshot harness |
| Release configuration | Missing | Release is unminified, unsigned, unshrunk, has no mapping artifact, no version policy, no baseline profile, and no release CI job |
| Performance and accessibility | Partial | Stable `LazyColumn` keys/content type, isolated streaming row, reduced-motion tokens, and 48 dp tokens exist. No baseline profile, cold-start measurement, size budget, TalkBack pass, or device matrix |
| Parity and evidence | Missing for M3 | `contracts/parity.md` records M1 only; no M3 verification file; critical cases 26-27 have no device evidence |
| M3 exit gate | Not met | No M3 deliverable is complete yet |

### 1.1 Critical path

```text
Preflight: confirm M2 exit gate and inventory M2-owned Android surfaces
   |
   +--> M3-01 Secret/privacy hardening ----------------------+
   |                                                        |
   +--> M3-02 Platform integration (intents, links, tabs) ---+--> M3-05 UI + screenshot tests
   |                                                        |
   +--> M3-03 Back, shortcuts, tablet, insets ---------------+
   |                                                        |
   +--> M3-04 Lifecycle, drafts, process death, cleanup -----+
   |
   +--> M3-06 Release, signing, baseline profiles, artifacts
   |
   +--> M3-07 Performance, accessibility, device matrix, parity, exit evidence
```

M3-06 can begin early because it is build configuration, but its release-artifact verification needs a stable feature surface. M3-05 depends on the screens and behaviors delivered by M3-01 through M3-04. M3-07 is the final evidence gate and must not start its exit review until every other task is complete.

### 1.2 Estimate

The milestone target is two weeks.

| Staffing | Estimate | Notes |
| --- | --- | --- |
| One Android implementer | 10-14 working days | Device/emulator work serializes with implementation; release and screenshot setup are the largest unknowns |
| Two implementers | 7-9 working days | Split platform integration from release/performance; keep one owner for test infrastructure |
| One implementer plus a device lab | 8-10 working days | Shortens case 26-27 plus device-matrix and baseline-profile recording |

The largest schedule risks are the M2 handoff, real process-death verification, arbitrary private-range cleartext support, and baseline-profile noise. Those are treated as explicit decisions in section 8 rather than hidden assumptions.

## 8. Decisions, Assumptions, and Open Questions

### 8.1 Decisions already made by the milestone

- M3 is Android-only and must not add new cross-platform product features.
- M2 must be complete before M3 implementation begins.
- Rust, web PWA, deployment, backup/sync, Play Store publishing, localization, and the full M4 audit are out of scope.
- Critical Android cases are 26 (process death preserves partial content) and 27 (backup exclusion prevents key restore), plus M1/M2 regressions.
- Configuration changes and process death must preserve or clearly interrupt streams with partial content.
- Release signing must never depend on committed material.
- Background streaming is best-effort and must not be presented as guaranteed.

### 8.2 Assumptions for this plan

- M2 will deliver attachments, pickers, clipboard image paste, drag-and-drop, settings screens, search, export/import, delete/undo, and clear data on Android.
- M2 will replace the provider and settings placeholders in the shell before M3 UI tests begin.
- M2 will leave `contracts/parity.md` truthful and current.
- The existing M1 Tink, secret store, recovery, chat runner, and `LazyColumn` structure are the baseline and should be extended rather than rewritten.
- A pinned emulator or Gradle Managed Device is available for connected tests and baseline-profile generation.
- `versionCode` and signing secrets can be supplied by CI without committing material.
- Screenshot tests run on Robolectric/Roborazzi or an equivalent JVM-backed harness, avoiding an emulator for every golden.
